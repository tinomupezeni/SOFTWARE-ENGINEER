# persons.roles GIN Index Missing from ORM Model (Alembic Drift)

**Date:** 2026-11-18
**Project:** MARITCHO
**Environment:** CI (GitHub Actions, Backend CI's "Alembic migrations apply cleanly and match models" step)
**Severity:** Medium
**Status:** Resolved

## Summary
Migration `5a7e2c9d4b13` creates a GIN index (`ix_persons_roles`) on `persons.roles` for the array-containment lookups `person_can_act_as()` runs, but `PersonModel` never declared that index via `__table_args__`. Alembic's `check` command (which diffs the model metadata against the migrated schema) saw the index in the database but not in the model, and flagged it as drift to be removed on the next autogenerate — the same class of bug as a migration/model mismatch, just caught by CI instead of at runtime.

## Symptoms
- `alembic check` in CI failed with: `New upgrade operations detected: [('remove_index', Index('ix_persons_roles', ...))]`.
- This had been masked until now: the same CI job's earlier `Mypy` step was failing for unrelated reasons (see [[maritcho-2026-11-18-naive-utcnow-timestamps-remaining]] and the PR #13 review findings), so the pipeline never reached the Alembic step until those were fixed.

## Environment Details
- **Server/Host:** GitHub Actions `backend` CI job
- **Services Affected:** None at runtime — a future `alembic revision --autogenerate` would have silently generated a migration dropping a needed index
- **Related Components:** `backend/app/apps/accounts/infrastructure/models.py` (`PersonModel`), `backend/migrations/versions/5a7e2c9d4b13_add_person_role_capabilities.py`
- **Time First Observed:** 2026-11-18, after fixing unrelated mypy failures let the Alembic CI step run for the first time

## Investigation Steps

### 1. Initial Diagnosis
Backend CI's Alembic step failed with a clear drift message naming the exact index.

### 2. Root Cause Analysis
Compared the migration (which creates `ix_persons_roles` via `op.create_index(..., postgresql_using="gin")`) against `PersonModel`'s column definition (`roles: Mapped[list[str]] = mapped_column(ARRAY(String(16)), ...)`, no index declared). The migration was handwritten (not autogenerated from the model), so the two were never checked against each other until CI's explicit `alembic check` step ran.

### 3. Key Findings
- The migration and the model are two independent sources of truth for schema; nothing enforced they agree except this CI step, which was itself blocked by an unrelated earlier failure.
- This is exactly the kind of drift `alembic check` exists to catch — it worked as intended once it got to run.

## Root Cause
A handwritten migration added an index that was never mirrored onto the corresponding ORM model's `__table_args__`.

## Prevention / Rule
**Guardrail:** Keep the existing CI gate (`alembic check` as a required status check on `main`), and additionally require it to run as an early step (or a separate fast job) rather than after mypy/pytest, so a migration/model mismatch surfaces immediately instead of being hidden behind unrelated failures later in the pipeline.

This closes the gap in two parts: the check itself already catches this exact bug class; moving it earlier (or making it independent of other steps) ensures a failure here is never silently masked by something else failing first, which is exactly how this one went unnoticed.

## Solution

### Immediate Fix
Added `__table_args__ = (Index("ix_persons_roles", "roles", postgresql_using="gin"),)` to `PersonModel`. Verified locally with `alembic upgrade head && alembic check` against a fresh database → `No new upgrade operations detected.`

### Long-term Fix
Consider reordering CI steps per the Guardrail above so this class of drift fails fast in future PRs.
