# Initial Migration's `downgrade()` Never Dropped Its Own Enum Types — Full Round-Trip Was Broken

**Date:** 2026-09-11
**Project:** Maricho
**Environment:** Development
**Severity:** Low
**Status:** Resolved

## Summary
While verifying that reformatting the initial migration (for lint cleanup)
hadn't changed its behavior, ran a full `alembic downgrade base` followed by
`alembic upgrade head` as a sanity check — something no prior session had
actually done end-to-end. It failed: `upgrade head` errored with `type
"roleenum" already exists`. The initial migration's `downgrade()` dropped
all seven tables but never dropped the three Postgres enum types
(`roleenum`, `jobstatusenum`, `ledgerentrytypeenum`) that `upgrade()`
implicitly created alongside them, leaving them orphaned after a downgrade
to `base`.

## Symptoms
- `alembic downgrade base` succeeds (all tables dropped, no error).
- `alembic upgrade head` immediately after fails:
  `asyncpg.exceptions.DuplicateObjectError: type "roleenum" already exists`.
- `\dT` on the dev database confirms: after downgrading to `base`, all
  tables are gone but `roleenum`, `jobstatusenum`, and `ledgerentrytypeenum`
  are still present.

## Environment Details
- **Server/Host:** local dev, `/home/shadowe/Projects/MARITCHO/backend`
- **Services Affected:** Alembic migration `7165c54ce358` (initial schema)
- **Time First Observed:** 2026-09-11, running a full migration round-trip
  to verify a lint-only reformat of this file was behavior-neutral

## Investigation Steps

### 1. Initial Diagnosis
`alembic downgrade base` reported success with no errors, so the failure on
the subsequent `upgrade head` was surprising until checking `\dT` directly.

### 2. Root Cause Analysis
`op.create_table(...)` implicitly creates any named Postgres ENUM type
referenced by a column (that's how the original autogenerated migration got
away with never explicitly creating `roleenum` etc.) — but `op.drop_table(...)`
does **not** symmetrically drop those types. The migration's `downgrade()`
was hand-written (or left as autogenerated) without adding the matching
`DROP TYPE` statements, so it silently leaves the types behind. This exact
pattern was already fixed defensively in every migration *authored this
session* (each adds explicit `sa.Enum(name=...).drop(op.get_bind())` calls
in `downgrade()`) — but the original, pre-existing initial migration was
never round-trip tested and had the same latent gap.

## Root Cause
Alembic's autogenerate tooling creates enum types as a side effect of
`create_table` but was never told to reverse that in `downgrade()`; nobody
had run a full `downgrade base` before this session to notice.

## Prevention / Rule
**Guardrail:** A CI job that runs a full `alembic downgrade base` → `upgrade head` round-trip on every migration-touching PR — not just `alembic check`, which only diffs current DB state against the models and never exercises the downgrade path at all.

This is the exact gap that let the bug sit unnoticed since the initial migration: `alembic check` would never have caught it, and nobody had run the real round-trip until this session did it by hand.

## Solution

### Long-term Fix
Added the three missing `DROP TYPE` calls (via
`sa.Enum(name='...').drop(op.get_bind())`, matching the pattern already
used elsewhere) to `7165c54ce358_initial_schema.py`'s `downgrade()`,
in reverse dependency order. Verified with two full
`downgrade base` → `upgrade head` round-trips and `alembic check` reporting
no drift.

- [x] Verified via two consecutive full round-trips from a clean `base`
- [ ] Worth periodically re-running a full `downgrade base` / `upgrade head`
  as part of any migration-touching change, not just `alembic check` (which
  only compares current DB state to models, not the downgrade path)
