# Rsync'd Local Dev `bootstrap/cache/packages.php` Crash-Looped the Production Laravel Container

**Date:** 2026-10-06
**Project:** Attendance
**Environment:** Production (first deploy to smepulse-vm)
**Severity:** High
**Status:** Resolved

## Summary
The first production deploy of the admin dashboard crash-looped with `Class "Laravel\Pail\PailServiceProvider" not found`. The production image is built with `composer install --no-dev`, so dev-only packages like `laravel/pail` are correctly absent from `vendor/`. The crash happened because the locally-generated Laravel package-discovery cache file, `admin/bootstrap/cache/packages.php` — created on the developer's machine by an ordinary (non-`--no-dev`) `composer install` and listing `laravel/pail` as a provider to autoload — was copied verbatim into the production image via `rsync` + `COPY . .`, so the app tried to boot a service provider class that the production `vendor/` tree never installed.

## Symptoms
- `docker logs attendance-admin-1` showed a crash loop: `In Application.php line 969: Class "Laravel\Pail\PailServiceProvider" not found`, repeating every ~2 seconds as the dev server crashed and the container's restart policy loop retried it.
- `curl http://localhost:8080/login` returned no response (connection reset / HTTP 000) because the process never reached a state where it could serve requests.

## Environment Details
- **Server/Host:** smepulse-vm, container `attendance-admin-1`
- **Services Affected:** Laravel admin dashboard
- **Related Components:** `admin/Dockerfile.production`, `admin/bootstrap/cache/packages.php` (local, untracked), deployment rsync file list
- **Time First Observed:** 2026-10-06, first `docker compose up -d` of the production stack

## Investigation Steps

### 1. Initial Diagnosis
`docker ps` showed the container cycling through `Created`/`Restarting` states. `docker logs` pointed directly at a missing class belonging to a `require-dev` package (`laravel/pail`, a log-tailing dev tool), which should never be loaded in a `--no-dev` production build.

### 2. Root Cause Analysis
```bash
grep -i "bootstrap/cache" admin/.gitignore   # only the directory's own .gitignore is tracked by git
cat admin/bootstrap/cache/packages.php       # -> local file, untracked, lists laravel/pail, laravel/pao, etc.
```
`bootstrap/cache/packages.php` is Laravel's package-auto-discovery manifest, regenerated by Composer on every `install`/`update` based on whatever is actually in `vendor/`. On the developer's machine it was last regenerated by a full (dev-inclusive) `composer install`, so it lists `laravel/pail` as a provider. It is correctly gitignored (never committed), but the deployment's `rsync` command synced the whole working tree to the VM *except* for an explicit exclude list that did not yet include `bootstrap/cache` — so this stale, machine-local, dev-flavored cache file rode along in the rsync payload and was then baked into the image unmodified by `COPY . .`, while the image's `vendor/laravel/pail` was correctly absent (`--no-dev`). The cached manifest and the actual installed packages disagreed, and Laravel tried to instantiate a provider from a package that wasn't there.

### 3. Key Findings
- A file can be correctly `.gitignore`d and still leak into a deployment, if the deployment's *transport* (rsync, scp, a tarball) doesn't apply the same exclusion rules as git does. Git-ignore and deploy-ignore are two separate lists that must be kept in sync by hand when the deploy path isn't `git clone`.
- `composer install --no-dev` does not regenerate or sanity-check an already-present `bootstrap/cache/packages.php`; it trusts the file present in the build context unless something explicitly clears or regenerates it.
- `php artisan package:discover` deterministically regenerates this manifest from whatever is actually installed, so running it as part of container start is a correct, idempotent fix regardless of what shipped in the build context.

## Root Cause
A local, gitignored, developer-machine build artifact (`bootstrap/cache/packages.php`, reflecting a dev-inclusive `composer install`) was not excluded from the `rsync` deployment payload, got `COPY`'d into the production image, and disagreed with the production (`--no-dev`) `vendor/` tree it was shipped alongside.

## Prevention / Rule
**Guardrail:** Any deploy path that is not `git clone`/`git archive` (e.g. `rsync`, `scp`, a tarball) must explicitly mirror the project's own `.gitignore`-equivalent exclusions for generated/machine-local artifacts, not just secrets — `bootstrap/cache/*.php`, `node_modules`, `vendor`, `storage/framework/{cache,sessions,views}`, `*.sqlite` all apply here. Additionally, defensively clear and regenerate `bootstrap/cache/*.php` inside the Dockerfile itself (`rm -f bootstrap/cache/*.php` after `COPY`, then `php artisan package:discover` before the app serves traffic) so the image's correctness never depends on what happened to be in the build context.

This closes the gap on two layers: the rsync exclude list stops the stale file from being shipped at all, and the Dockerfile/entrypoint regeneration makes the image self-correcting even if a future deploy-transport change reintroduces a stale cache file.

## Solution

### Immediate Fix
1. Added `--exclude='bootstrap/cache/*.php'` to the deployment `rsync` command.
2. Added `RUN rm -f bootstrap/cache/*.php` to `admin/Dockerfile.production` right after `COPY . .`, so the image never ships a possibly-stale manifest regardless of build context.
3. Added `php artisan package:discover --ansi` as the first step of `admin/docker-entrypoint.production.sh`, run before `migrate`/`config:cache`, so the manifest is always regenerated from the image's actual (`--no-dev`) `vendor/` tree.

Rebuilt and recreated the `admin` container; the package-discovery step now correctly lists only `laravel/tinker`, `nesbot/carbon`, and `nunomaduro/termwind` (the production-relevant providers), and the dashboard serves successfully.

### Long-term Fix
None needed beyond the fix above.
