## The failure this prevents

A recurring failure on small teams is a bug that gets fixed on staging,
verified fixed, and then reappears in production days later. The root cause
is almost never the fix itself — it is that staging and production were
never proven to be running the same build. Both environments tag their
images `:latest` (or `:staging`), and that tag is a mutable pointer, not an
identity: it silently means "whatever the most recent build happened to
produce," which drifts the moment either environment rebuilds
independently. A rebuild that quietly fails to include one service (a
missing `build:` context, a stale cached layer, a partial CI run) leaves
that one service pointing at old code with no error raised anywhere. The
team ships the fix, watches staging behave correctly, and has no mechanism
to know production is running something else.

The fix is to tag every image by the identity of the commit it was built
from — a short git SHA is enough for a team without a container registry —
and to never treat `:latest`/`:staging` as anything but a convenience
alias. `sha-<commit>` is immutable by construction: the same commit always
produces the same tag, and a different commit always produces a different
one, so "is this the build I already verified?" becomes a string
comparison instead of an assumption.

## Promotion Without Rebuilding

The payoff of immutable tagging is that promotion can become "point the
next environment at the artifact that already passed the previous one"
instead of "rebuild from source and hope it comes out the same."

### Variant A: single host, no registry needed

If staging and production share one Docker daemon (the common case for a
one-to-four-person team on one VPS), the image staging just built is
already sitting in the local image store — nothing needs to leave the
host:

```bash
# Before rebuilding for production, check whether this exact commit
# was already built (typically because staging just built it).
GIT_SHA=$(git rev-parse --short HEAD)
if docker image inspect "myregistry/myapp:sha-${GIT_SHA}" >/dev/null 2>&1; then
  echo "sha-${GIT_SHA} already built — promoting the existing artifact, not rebuilding."
else
  echo "sha-${GIT_SHA} not found locally — this wasn't a promoted build, building fresh."
  docker build --build-arg GIT_SHA="${GIT_SHA}" -t "myregistry/myapp:sha-${GIT_SHA}" .
fi
export TAG="sha-${GIT_SHA}"
docker compose up -d --wait
```

The "not found" branch is not an error path — it correctly fires on a
hotfix pushed straight to production, or a promotion done as a fresh merge
commit rather than a fast-forward (which produces a new SHA the earlier
environment never built). **Log both branches explicitly.** The two cases
must never be silently indistinguishable, or the team loses the ability to
tell "this deploy reused a verified artifact" from "this deploy built
something new and unverified beyond CI passing."

Fast-forward promotion (`git merge --ff-only`, or just pushing the same ref
to the next environment's trigger branch) is what makes the "already
built" branch fire at all. A regular merge commit produces a new SHA the
earlier environment never built, so it safely-but-suboptimally falls
through to a fresh build — correct, just not free. If your team wants the
no-rebuild path to actually pay off, promotion needs to preserve the
commit identity, not just the content.

### Variant B: separate hosts, one registry

Once environments are on separate hosts, this needs a registry: push the
SHA-tagged image once at build time, and every later `docker compose up`
on any host pulls that same tag rather than rebuilding. The tagging scheme
and the rollback marker (below) are otherwise identical — only the
"already built?" check changes, from a local `docker image inspect` to a
registry manifest check (or simply attempting the pull and trusting the
registry to 404 on a tag that was never pushed).

### The trap that breaks both variants the same way

**Never let two environments' build steps be structurally uneven** — e.g.
one environment's compose file has a `build:` block for a service the
other lacks, or an explicit per-service build script omits a service the
other includes. `docker compose build` silently skips any service without
a build context — no error, no warning — and the next `up` then tries to
use whatever tag was left behind: either the previous stale local image,
or a registry tag that may not even exist yet. If a build step is supposed
to build N services, verify all N actually have somewhere to build from,
on *every* environment that runs that step — not just the one you tested
last.

## Fast Rollback via Last-Known-Good Marker

Immutable tagging also turns rollback from "rebuild the previous commit
and hope it still builds the same way" into a tag swap. After a deploy's
health check passes — **not before** — write the deployed identity to a
plain marker file:

```bash
if docker compose up -d --wait --wait-timeout 300; then
  echo "${GIT_SHA}" > /opt/app/.last_good_sha
else
  exit 1   # marker is untouched — it still names the last build that was actually healthy
fi
```

A failing deploy's rollback then tries the fast path first: read the
marker, confirm that identity's images are still available (locally, or in
the registry), and if so, just `export TAG=sha-<marker>` and `up -d`
again — seconds, no rebuild. Only fall back to a full rebuild-from-git-
history if the marker is missing or its images were already pruned. This
is also why the marker must be written strictly *after* the health check,
never before or unconditionally — a marker pointing at a build that was
never actually confirmed healthy defeats the entire mechanism.

## Retention

Since SHA tags are never overwritten, they accumulate forever unless
something prunes them. Keep the newest N (5 is a reasonable default for a
small team) per service/image, filtered strictly to your own tagging
scheme (`myregistry/myapp:sha-*`) so base images and anything still on a
mutable tag are never touched by accident:

```bash
# Keep the newest N sha-tagged images for one repo, delete the rest.
keep="${1:-5}"
repo="myregistry/myapp"
docker image ls --filter "reference=${repo}:sha-*" --format '{{.CreatedAt}}|{{.ID}}' \
  | sort -r | tail -n "+$((keep + 1))" | cut -d'|' -f2 | sort -u \
  | xargs -r docker rmi
```

Retention is a separate concern from build cache (`docker builder prune`).
Pruning old tagged images is a small, bounded multiple of one full image
set; build cache can grow much larger and is worth pruning on its own
schedule, out of band from every deploy's hot path.

## Case Study: the HBEC incident this guide was extracted from

HBEC (a multi-service platform: several Django/FastAPI backends, two React
frontends) ran staging and production as two independent Docker Compose
environments on one VPS, each rebuilding from source on every deploy and
tagging `:latest`/`:staging`. Two things went wrong at once, both entirely
hidden by the mutable-tag setup:

1. Staging's generated compose file (produced by a script from a shared
   base file plus an overrides file) was missing a `build:` patch for 2 of
   9 services. `docker compose build` silently skipped them — no error —
   and the subsequent `up` tried to pull their tag from a private
   registry and aborted the *entire* rollout, while the other 7 services
   quietly kept running their previous image the whole time.
2. A second, unrelated gap in the same overrides file: two other services
   had no `image:` key at all, so `docker compose build` tagged them with
   Compose's own default naming instead of the project's real tag scheme —
   meaning even a correct build for those two would never be found by an
   "already built?" check looking for the real tag.

Neither failure produced a clean, single error pointing at the cause. The
first surfaced as an "unauthorized" pull failure that looked like a
registry/credentials problem; the second was silent — the deploy
"succeeded," just not with the tag anything downstream expected. Both were
only caught by watching a live deploy end to end and checking the actual
running image IDs against what was supposed to be there — exactly the kind
of check this guide's promotion mechanism makes structural (`docker image
inspect`, `image-tags.sh exists`) instead of manual and occasional.

The fix, implemented in `.github/workflows/cd.yml` and
`scripts/deploy/image-tags.sh`:
- Every image tagged `sha-<gitsha>`, never `:latest`/`:staging` as the
  deployed reference.
- Production checks `image-tags.sh exists <sha>` before rebuilding — skips
  and logs "already built" on a fast-forward promotion, rebuilds and logs
  "not a promoted artifact" otherwise.
- `.last_good_sha` written only after `docker compose up --wait` reports
  healthy; rollback reads it and tries a tag-swap before falling back to a
  full rebuild.
- `image-tags.sh prune 5` keeps the newest 5 sha-tagged images per service.
- Both missing-`build:`/missing-`image:` gaps were fixed at their actual
  source (the overrides file the compose file is generated from), not by
  hand-editing the generated output — which would have been silently
  overwritten the next time anyone regenerated it.

## Checklist (copy into a project's own docs when applying)

- [ ] Every deployable image/artifact is tagged by an immutable build
  identity (git SHA at minimum), never only `:latest`/a branch name
- [ ] Promotion checks whether that identity's artifact already exists
  before rebuilding, and logs which branch it took (reused vs. built fresh)
- [ ] Every environment's build step builds the *same* set of
  services/artifacts — verified, not assumed, especially after any change
  to a generated/templated build config
- [ ] A last-known-good marker is written only after a deploy's health
  check passes, and rollback tries a tag-swap against it before falling
  back to a rebuild
- [ ] Old tagged artifacts are pruned on a retention policy, separately
  from build-cache pruning
- [ ] If environments span more than one host, a registry push/pull
  replaces the local-image-store check — same tagging scheme, same marker,
  same rollback logic
