Every guide in this library up to this point assumes the code under discussion was written by a human, or by an AI whose output a human already trusts. That assumption is no longer safe. Once a CLI coding agent can produce a working distributed system in an afternoon — shipwright is the proof — the bottleneck stops being "can this get written" and becomes "can this be trusted, and how do I know." This guide is about the loop that answers that question: how an engineer hands work to an agent, what "done" means when the agent says it's done, and how to keep that discipline from decaying back into hope.

## 1. The Builder → Architect Identity Shift

Legacy software engineering allocates an engineer's time roughly 90% to syntax and debugging and 10% to architecture. Agentic orchestration inverts that ratio: roughly 10% of the engineer's time goes to prompting and initial review, and 90% goes to systems design and verification. The work did not get easier — it moved. An engineer who keeps spending their time the old way (hand-checking syntax, hand-writing boilerplate) while an agent is available to do exactly that is not being careful, they are misallocating the one thing that didn't get automated: judgment.

| Dimension | Legacy Coding | Agentic Orchestration |
|---|---|---|
| Time on syntax/debugging | ~90% | ~10% |
| Time on architecture/verification | ~10% | ~90% |
| Primary artifact produced by the human | Code | Intent + verification proof |
| Bottleneck | Typing speed, language fluency | Requirements precision, audit depth |

### 1.1 Requirements Engineering: Precision Beats Vagueness

An AI coding agent is a precision tool, not a collaborator who fills in unstated intent the way a human teammate would. A vague instruction does not produce a vague-but-safe result; it produces "AI Spaghetti" — code that is locally plausible, technically executes, and is wrong in a way that only surfaces later, usually in production. "Fix the store-api crash" and "Fix the `NameError` in `store-api/app/main.py`; ensure `Depends` and `Session` are imported; follow the Zero-Zombie template" are not different phrasings of the same request — the first is a wish, the second is a directive with a verifiable outcome. Section 4 formalizes this distinction.

### 1.2 Verification as the Premium Skill

When code generation is nearly free, the scarce skill is proving correctness: observability (logging and traces), automated testing, and smoke testing against the real target environment. An engineer who cannot design a test that would catch their own agent's mistake has not actually delegated the task — they have outsourced the risk without outsourcing the accountability.

### 1.3 The Black Box Audit Principle

Never treat agent-generated code as a black box, no matter how clean the diff looks or how confidently the agent asserts it's correct. "It compiles" and "the agent said it works" are not verification — they are the absence of a caught error, which is a different thing. Section 2's Reverse Engineering Path is the concrete technique for turning "I trust this because I don't understand it well enough to distrust it" into "I trust this because I interrogated it and it held up."

## 2. The Reverse Engineering Path: Three Audit Lenses

Traditionally, an engineer learns a language or a system by reading a book and then writing code in it. When an agent is the one writing the code, that path is available in reverse: the engineer learns the system by auditing and challenging a system that already exists and already works. The goal is not to catch a bug on the first pass — it is to build the same intuition a language book would have given, but grounded in a real, running system instead of an exercise. Three lenses structure the interrogation:

| Lens | Question you are forcing the agent to answer | Worked example (verbatim from source) |
|---|---|---|
| **Security auditing** ("Malicious Actor") | Where is the trust boundary, and what happens if it's crossed? | "Show me where we handle the Docker Socket connection. How are we ensuring a malicious container can't take over the host?" |
| **Concurrency & performance** ("Mechanical") | What primitive did the agent choose, and why is it correct here specifically? | "Explain how we are using `Tokio`. Are we using `select!` or `join!` for the build tasks? Why is one better for this?" |
| **Failure injection** ("Resilience") | What does this do under the worst case, not the happy path? | "Write a failure-injection test. What happens if the VPS runs out of disk space in the middle of a build?" |

This is a technique to run repeatedly, not a one-time onboarding exercise: every non-trivial piece of agent-delegated work should get at least one pass through whichever lens is most relevant to what changed (a new endpoint gets the security lens; a new background worker gets the concurrency lens; a new deployment step gets the failure-injection lens). The point of asking the agent to answer its own audit questions is that a well-posed question it cannot answer convincingly is itself a finding — "I don't know why we chose `join!` over `select!` here" is a more useful answer than a fabricated justification, and pressing for the real reasoning is how you tell the two apart.

## 3. A Definition of Done for Agent-Delegated Tasks

"It works on my machine" — or worse, "the agent said it's done" — is not a Definition of Done. A delegated task is only Done when all four of the following hold:

| # | Criterion | What satisfies it | What does NOT satisfy it |
|---|---|---|---|
| 1 | **Behavioral Proof** | A test case or `curl`/equivalent command that exercises the fix in the actual target environment | "It should work now"; a description of what the code does; a passing unit test against a mock when the bug was in integration |
| 2 | **Structural Integrity** | No new instances of already-known-bad patterns (copy-paste imports, the shell-escaping trap in Section 6, silently-skipped Compose `build:` blocks) | A diff that fixes the reported symptom while introducing a pattern the team has already been burned by once |
| 3 | **Observability** | The service reports its own health via a real check (e.g. `/health/deep`) that exercises its actual dependencies, not just process liveness | A `/health` endpoint that returns `200 OK` unconditionally |
| 4 | **Knowledge Persistence** | A dev-log entry (or equivalent) explaining what broke and why, filed against the standard template | The fix lands with no record beyond the commit message; the next person hits the same failure with no prior art |

Criterion 4 is not bureaucracy — it is what prevents the same class of bug from being independently rediscovered by a different agent, on a different day, at full cost. SMEPulse's project adapter already practices criterion 1 without naming it: it explicitly marks an assumption about a webhook field name as "not yet empirically verified" and refuses to call that piece Done until it's tested against a real device tap.

## 4. The 3-Step Delegation Framework

When handing a task to another engineer (or another agent, or another engineer's agent), provide exactly three things. Withholding any one of them turns delegation back into hope.

### A. The Directive (the "What")

State the exact change, in terms specific enough that there is only one reasonable implementation.

- **Bad:** "Fix the store-api crash."
- **Good:** "Fix the `NameError` in `store-api/app/main.py`. Ensure `Depends` and `Session` are imported. Follow the Zero-Zombie template."

### B. The Verification Script (the "Prove It")

Give the exact command that must pass. Not "test it" — the command itself.

```bash
curl -f http://localhost:8001/api/v1/health/deep
```

### C. The Standard Reference (the "How")

Point at a written standard, and make violating it grounds for rejection — not a matter of taste. "If your solution violates Section 2 (Critical Rules) of `DEPLOYMENT-STANDARDS.md`, it will be rejected" is enforceable; "please follow best practices" is not, because it gives the reviewer nothing to point at when the answer is no.

With all three in place, the human reviewer's job stops being "read every line of the diff" and becomes "did the verification script pass, and does the standard reference hold" — which is what makes delegation actually scale past what one person can review by eye. This is also the mechanism underneath any PR-gated workflow that conditions merge on an attached verification report (see Section 5.4) — the gate only works if a report exists to check.

Automation should enforce the nagging, not the reviewer: a failing lint or a failing health check should reject work before it ever reaches a human's desk. The closing maxim for this whole framework:

> "If you have to do it twice, write a standard. If you have to do it three times, write a script. If you want to delegate it, provide the verification."

## 5. Directives Over Suggestions, and the Blueprint-Repo Pattern

### 5.1 Directives, Not Suggestions

In an agentic orchestration model, the guiding engineer's output is a directive — an exact code block and an exact verification step — not vague advice. "Consider using a health check" is advice; the artifact in Section 4.B is a directive. The difference matters because an agent (and a busy human) will satisfice against advice but will actually execute against a directive. As the source material for this pattern puts it: "An architect doesn't just draw the building; they specify the strength of the concrete."

### 5.2 The Blueprint Repo: A Source of Truth for Delegated Work

Once a team has more than one engineer-plus-agent pair working against the same codebase, directives and standards need a home that is itself version-controlled and auditable — not scattered across chat messages. The Blueprint pattern is a dedicated repository (or a well-organized subtree of an existing one) with this shape:

```text
blueprint/
├── standards/           # Immutable Engineering Standards
│   ├── deployment.md    # Vite Build Args, Nginx Reload, Registry Rules
│   ├── api-chassis.md   # Zero-Zombie API, Deep Health Check Specs
│   ├── identity.md      # UUID vs Name, Distributed Auth Rules
│   └── frontend.md      # HCI Standards, Optimistic UI, Asset Loading
├── directives/          # Active Task Definitions (LLM-Ready)
│   ├── active/          # Currently assigned tasks
│   └── completed/       # Historical directives (reference)
├── verification/        # Global Verification Protocols
│   ├── scripts/         # Standard check scripts (e.g., verify-deployment.ps1)
│   └── patterns.md      # "How to prove it" guide
└── README.md            # The "Prime Directive" and Repo Index
```

Each file in `directives/active/` follows a fixed shape so an agent can execute it without needing the surrounding conversation for context:

1. **Context** — project name, environment, relevant existing files.
2. **Standards Reference** — which files in `standards/` apply.
3. **The Directive** — concise, technical instruction (what, not how).
4. **Verification** — the exact command/output required for completion.
5. **Definition of Done** — checklist per Section 3, for the implementer (and their agent).

The workflow this enables: one engineer drafts a directive, commits it to `directives/active/`, and sends the link. The receiving engineer's agent pulls the file, follows the referenced standard, implements, and — on completion — commits both the `dev-logs` entry (Section 3, criterion 4) and the verification output. Nothing is delegated by conversation; everything delegated is a file, and every file that claims to be Done has a verification artifact attached to it.

> "If it's not in the Blueprint, it doesn't exist. If it's in the Blueprint, it must be verified."

### 5.3 A Concrete Application: Git Workflow

One specific way to apply this discipline to source control is to gate merges on an attached verification report rather than on manual line-by-line review — a PR is auto-blocked if the report is missing or shows any failure, and a reviewer's job on a passing report becomes a "snap review" of the report itself rather than the whole diff. This is a real proposal that was drafted for one specific project's implementer/reviewer pair and was, at time of writing, an open decision rather than settled practice — it is included here as one worked example of applying delegation discipline to branching strategy, not as a prescription to adopt verbatim. The pattern it proposes (verification-gated PRs) is the useful, generalizable part; the specific trunk-based-vs-feature-branch tradeoff table it works through is project-specific and should be re-derived for your own team's risk tolerance rather than copied.

## 6. Case Study: The Shell-Escaping Trap and Cascading Blindness

This section walks one real incident end to end, because the abstract remediation pattern in Section 6.2 is easy to nod along to and easy to apply wrong without a concrete anchor.

### 6.1 The Incident

A deployment script (`tese.ps1`) failed with `syntax error near unexpected token '('` during a `docker exec` health check. The command that triggered it looked, at the PowerShell layer, like a single string being passed through to a remote Python process:

```bash
docker exec my-container python -c "import sys; print('hi')"
```

The actual failing case embedded a `urllib.request` call with parentheses and semicolons. The command passes through four distinct interpreters before it runs, each of which reads and partially rewrites it:

```
PowerShell (local)  →  SSH (transport)  →  Bash (remote VPS)  →  Python (inside Docker)
```

Bash — layer 3 — saw the `(` in the Python source before Python ever got a chance to parse it, interpreted it as a subshell open, and threw a syntax error. The deployment script died at the health-check step with an error about Bash syntax.

### 6.2 Cascading Blindness

The health check existed to answer one question: is the service actually up? The service in this incident had a real bug — a `NameError` — that made it crash on startup. But the engineer investigating the failure saw a Bash syntax error from the *deployment script*, not a Python traceback from the *service*. The orchestrator's own failure mode was loud enough to fully obscure the thing it was trying to check. This is Cascading Blindness: a service is crashing, but you cannot see the crash because the layer meant to observe it is crashing first, in a different and more confusing way. Debugging effort went toward "why is Bash unhappy with this string" — the wrong problem — before anyone got far enough to ask "why is the service returning nothing at all."

### 6.3 Applying the Remediation Pattern

The four-step pattern is not "fix the bug that's visible" — it is explicitly structured to stop that reflex, because the visible bug (the Bash syntax error) was not the bug that mattered (the `NameError`).

**Step 1 — Decouple the failures.** Do not try to fix the script and the service in the same pass. First fix the service's actual code — the root cause, the "Zombie" that was crashing on startup — completely independently of the deployment tooling. Only once the service is provably healthy on its own does the orchestrator's behavior become diagnosable, because now a script failure can only mean the script is wrong, not "maybe the script, maybe the service, who knows."

**Step 2 — Standardize the solution.** The fix is not "patch `main.py`'s missing import." It is a standing rule: adopt a "Zero-Zombie" API chassis template that every service in the fleet uses, so the same class of startup crash cannot recur in a different service six months later under a different name.

**Step 3 — Verification as the bridge.** Replace the shallow health check (does the process respond to a TCP connection) with a deep health check that actually exercises the dependency the `NameError` had broken. The orchestrator must not just *run* a command and assume success on exit code 0 — it must *prove* the result, which is what closes the "Gulf of Evaluation" between "the script didn't crash" and "the service actually works."

**Step 4 — Directives over suggestions, applied to the escaping trap itself.** The remediation for the shell layer is not "be more careful with quoting" — that is advice, and it will fail again the next time someone writes a slightly different command through the same four-layer chain. The directive is structural: never pass complex multi-layer logic as an escaped string across a shell boundary at all. Put the health-check logic in a `healthcheck.py` file *inside* the version-controlled container image, and have the deployment script's only cross-boundary command be `docker exec my-container python healthcheck.py` — a string with no parentheses, no semicolons, nothing for any intermediate shell to misinterpret. The logic that used to be a fragile, un-versioned string now lives in the image, gets code-reviewed, and cannot drift out of sync with what the container actually runs.

The general lesson generalizes past this one incident: the more shell/language boundaries a piece of logic crosses as a string, the more likely it breaks, and the fix is always the same shape — collapse the logic into a single artifact that lives on one side of the boundary, and reduce the cross-boundary command to something trivial enough that no intermediate interpreter has anything to misparse.

## Checklist (copy into project's docs when applying)

- [ ] Every task handed to an agent (yours or another engineer's) states a Directive specific enough to have only one reasonable implementation — not a restated symptom
- [ ] Every Directive ships with an exact Verification Script (a real command against the target environment), not a description of expected behavior
- [ ] Every Directive names the Standard it must comply with, and violating that standard is treated as automatic rejection, not a discussion
- [ ] "Done" requires all four of: behavioral proof, structural integrity (no known-bad patterns reintroduced), observability (a real deep health check), and a persisted knowledge-log entry
- [ ] Agent-generated code for anything security-, concurrency-, or failure-sensitive has been walked through at least one Reverse Engineering Path lens before being trusted
- [ ] No command sequence passes multi-layer logic (semicolons, parentheses, quoting) as an escaped string across more than one shell/language boundary — collapse it into a version-controlled script inside the target instead
- [ ] Standards and active directives live in a version-controlled, auditable location (a Blueprint repo or equivalent) — not only in chat history or a person's memory
- [ ] If a PR/merge gate exists, it is gated on an attached verification report, not on manual full-diff review alone
