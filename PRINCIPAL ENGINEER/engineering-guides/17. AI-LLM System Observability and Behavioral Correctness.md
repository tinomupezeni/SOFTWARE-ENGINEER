## 0. The gap this guide fills

Guide `4. Site Reliability Engineering.md` answers one question: is the system
**up** — uptime, latency, error rate, saturation. Guide `11. SE Verification.md`
answers a second, different question: is the system's output **functionally
correct** — does the endpoint return the right shape of data, does the test
suite pass, does the contract hold.

Neither answers a third question, and for an LLM/AI-agent-backed system it is
not optional to leave unanswered: is the system's output **semantically or
behaviorally correct**? A chat endpoint can return HTTP 200 in 400ms (SRE:
green) with a response that matches its Pydantic schema (Verification: green)
while the model backing it produced worse content than the one it was
configured to use, the retrieval step it claims to run returned nothing, or
the agent ignored the last four turns of conversation. All three of those are
real, dated incidents in this codebase, documented below. None of them tripped
an alert, because nothing was watching for them — uptime and status-code
monitoring have no opinion on whether the *content* of a 200 response is any
good.

This is a distinct engineering discipline from the two guides above it, not a
subset of either:

| | Guide 4 (SRE) | Guide 11 (Verification) | This guide |
|---|---|---|---|
| Question | Is it up? | Is the output the right *shape*? | Is the output the right *substance*? |
| Signal | Uptime, latency, error rate | Schema match, test pass/fail, contract | Which model served it, did retrieval return anything, did the agent behave |
| Fails loud? | Usually (5xx, timeout) | Usually (assertion failure) | **No — this is the defining property.** A degraded model, an empty retrieval, and a routing bug all return 200 with well-formed JSON. |

## 1. Silent model-fallback degradation

**What happened (2026-07-21, `dev-logs/HBEC/2026-07-21-hbec-missing-diagrams-and-rollback-bug.md`):**
The VPS `.env` file had `GOOGLE_API_KEY=""` — blank, not missing. The harness's
diagram-generation path is tuned specifically for Gemini's ability to emit the
structured `plot spec` JSON the frontend's `InteractivePlot` component expects.
On every request, the blank key produced an `API key not valid` error from
Google, and the system did exactly what its fallback chain was designed to do:
it "intelligently fell back" to the Groq **`llama3.1-70b`** model. That model
is a perfectly healthy, perfectly available LLM — it answered every request,
fast, with no errors. It also has none of the prompt-tuning the diagram
feature depends on, so every diagram silently stopped rendering for students.
The fix was one environment variable; the reason it took time to *find* was
that nothing logged, metriced, or alerted on which model tier had actually
served any given request. From the outside — uptime probes, error-rate
dashboards, the LiteLLM proxy's own health check — the system was up the
entire time.

**Principle:** a fallback chain across model providers or tiers is not
self-observing just because it works. It needs its own, separate telemetry
axis, because "the request succeeded" and "the request succeeded *using the
model this feature was built and tuned for*" are different facts, and only
the first one shows up in standard error-rate monitoring.

Concretely:

- **Log which model actually served every request**, not just which model was
  requested. At minimum: `{request_id, feature, model_requested, model_served,
  fallback_reason}`. If `model_requested != model_served`, that is a fallback
  event and must be distinguishable from a normal, expected routing decision
  (e.g. a deliberate cost-based tier choice) — tag it explicitly.
- **Alert on fallback-tier usage crossing a threshold**, not only on total
  provider failure. A single fallback is often fine (the chain did its job).
  A sustained rate of fallback (e.g. >5% of requests to a given feature over
  15 minutes) means the primary is degraded in a way that total-failure
  alerting will never catch, because the system never actually goes down.
- **Treat feature-specific model dependencies as a first-class config
  invariant.** If a feature (diagram generation, in this case) was tuned
  against one specific model, a fail-fast startup check that the corresponding
  provider key is present and non-blank belongs next to it — this is the same
  "config drift with no fail-fast validation" throughline guide `5b. Secure
  Application Configuration.md` names as HBEC's most-repeated root cause
  across its incident history; a blank API key is exactly that class of bug,
  just surfacing through a model fallback instead of a crash.

```python
# app/shared/llm_client.py — log the served model, not just the request
async def call_llm(model: str, messages: list, feature: str, **kwargs):
    response, served_model, fallback_reason = await _route_with_fallback(model, messages, **kwargs)
    logger.info(
        "llm_call_completed",
        extra={
            "feature": feature,
            "model_requested": model,
            "model_served": served_model,
            "fallback_occurred": served_model != model,
            "fallback_reason": fallback_reason,  # None on the happy path
        },
    )
    # metrics: increment a counter labeled {feature, model_served, fallback_occurred}
    # alert: fallback_occurred rate > threshold over a rolling window, per feature
    return response
```

## 2. Provider single-point-of-failure and empty/ungrounded retrieval

**What the audit found (`SYSTEM-AUDIT.md`, §2.1 and §2.2):**

§2.1, "LLM Provider — Single Point of Failure": at the time of the audit,
`litellm_config.yaml` listed exactly one model (`ollama/llama3.1`, local-only,
no cloud fallback configured). The audit's own framing is direct: "If Groq
goes down, all chat functionality dies." — impact rated 🔴, complete chat
outage during provider issues. (Fallback breadth was later expanded, which is
precisely what created failure mode 1 above — a fallback chain fixes the
SPOF and introduces a new, unmonitored failure surface. The two findings are
not independent.)

§2.2, "Empty RAG Pipeline": Qdrant was running (🟢, healthy container) but held
zero vectors. The audit traces the consequence exactly:

```
User asks: "Explain photosynthesis"
    → Harness searches Qdrant
    → Returns: NOTHING (empty database)
    → LLM responds with generic knowledge (may hallucinate)
```

Every layer here reports healthy. Qdrant is up. The search call returns
200 with a well-formed (empty) result. The LLM call succeeds and returns a
fluent, confident answer. Nothing in that chain throws, and nothing in that
chain distinguishes "I retrieved three relevant curriculum chunks and grounded
my answer in them" from "I retrieved nothing and am answering from parametric
memory alone." The system *looks* like it is doing grounded retrieval — the
architecture diagram in `SYSTEM-AUDIT.md` §1 shows a RAG/Qdrant box sitting
right there in the harness — without actually doing it.

**Principle:** RAG is not a solved problem the moment the vector store is
wired up and returns 200. Two separate things need monitoring, and both are
currently invisible in HBEC's stack:

1. **Provider redundancy is a config fact, not a one-time task.** "Add a
   fallback provider" is a checklist item that can regress silently (a
   provider's API key expires, a config edit drops the second entry) unless
   something checks, at runtime, that the configured fallback chain still has
   more than one *reachable* member. A SPOF that was fixed once and never
   re-verified is not fixed.
2. **Retrieval must report whether it retrieved anything, and that fact must
   reach the generation step and the logs — not be silently absorbed.** An
   empty result set from the vector store is a legitimate outcome (the corpus
   genuinely has nothing on the topic), but it changes the trustworthiness of
   whatever the LLM says next, and a system that treats "0 hits" and "8 hits"
   identically is choosing not to know the difference.

Concretely:

- **Log retrieval hit/miss and result count on every RAG call**:
  `{query, collection, hit_count, top_score, latency_ms}`. A dashboard of
  `hit_count == 0` rate per collection turns "the RAG pipeline is empty" from
  a fact discovered by manual audit (as it was here) into a number that pages
  someone when it crosses zero-and-stays-there.
- **Gate generation on retrieval outcome, don't just pass through.** At
  minimum, when `hit_count == 0`, the system prompt or response metadata
  should say so explicitly (e.g. "no curriculum content was found for this
  query; answering from general knowledge") rather than letting the model
  present an ungrounded answer with the same confidence as a grounded one.
  This does not require blocking the response — it requires the response (and
  its logs) to carry the provenance honestly.
- **Treat hallucination risk as measured, not assumed-solved.** "We have RAG"
  is not a fact that stays true; it is a hypothesis that needs a standing
  metric (retrieval hit rate, grounding rate) to keep being true after launch.
- **Verify the fallback chain has ≥2 reachable providers on a schedule**, not
  only at deploy time — a scheduled health probe against each configured
  provider (not just the primary) catches the case where the fallback itself
  quietly stopped being usable (expired key, deprecated model ID, rate-limit
  band) long before an outage forces the discovery.

## 3. Agent behavioral-contract bugs

**What happened (`PROBLEM.md`, Bugs #9, #10, #11):** three separate agent bugs
in the harness's orchestration layer, none of which threw an exception or
failed a status-code check, all of which meant the agent did not do what it
was built to do.

- **Bug #9 — Stateless Chat: Agents Ignore Conversation History.** Every agent's
  `generate_response()`-family function (`learning_guide/nodes.py`,
  `project_guide/nodes.py`, `exam_grader/nodes.py`,
  `revision_generator/nodes.py`) read only `messages[-1]["content"]` and sent a
  single-turn prompt to the LLM, discarding the conversation history that had
  already been loaded into memory. The endpoint returned 200. The response was
  a well-formed chat message. It simply had no relationship to anything the
  student had said two turns earlier — the contract "this is a multi-turn
  conversation" was silently not honored.
- **Bug #10 — Wrong Agent Selected: Router Ignores Session Type.**
  `IntentClassifier.classify()` in `AGENTIC_HARNESS/app/core/router.py` only
  special-cased `active_session_type == "practice"`; a student on the Project
  Guide page saying "hi" (no keyword match) fell through to the
  `learning_guide` default instead of `project_guide`. The router returned a
  valid agent name every time — it just wasn't the *right* one whenever the
  active page was project or revision and the message carried no distinctive
  keyword.
- **Bug #11 — MemoryManager Bypassed: No Semantic Memory.**
  `HarnessOrchestrator` called `WorkingMemory` directly instead of going
  through `MemoryManager`, so the three-tier memory design (Redis working
  memory + Qdrant semantic memory + PostgreSQL structured memory) collapsed to
  one tier in practice. Conversations were never embedded or written to
  Qdrant. Nothing failed — `WorkingMemory` is a real, working component; it
  was simply the wrong one for what the orchestrator was supposed to be doing,
  so semantic recall silently didn't exist.

All three share the same shape: correct HTTP status, schema-valid payload,
zero exceptions, and a behavior that does not match the system's own
specification. Guide `11. SE Verification.md`'s functional/contract testing
would pass all three of these — the endpoint returns 200, the response body
matches the chat-message schema. That is exactly the point: "it runs without
error" and "it returns 200" are necessary conditions for an agent system, not
sufficient ones, and the gap between the two is where all three of these bugs
lived undetected until a manual audit found them.

**Principle:** agent/LLM-orchestration code needs behavioral assertions as a
distinct test category from functional/contract tests — assertions about
*what the system did*, not merely *what shape it returned*. "Does turn 2 of a
conversation actually reference turn 1's content" is a different test from
"does the endpoint respond with a 200 and a `message` field," and only the
first one would have caught Bug #9.

Concretely, each of the three maps to a test that a schema/status assertion
cannot express:

```python
# Bug #9 class: multi-turn continuity — NOT "does it return 200"
async def test_agent_references_prior_turn():
    reply1 = await send_chat("What is photosynthesis?", conversation_id="t1")
    reply2 = await send_chat("Can you explain more about the light reaction?", conversation_id="t1")
    assert "photosynthesis" in reply2.lower() or "light reaction" in reply2.lower()
    # A stateless agent (Bug #9's actual behavior) passes a naive schema/status
    # test on reply2 while failing this one.

# Bug #10 class: routing — NOT "does it return *an* agent"
async def test_sticky_routing_by_session_type():
    reply = await send_chat("hi", context={"activeSessionType": "project"})
    assert reply.agent_used == "project_guide"
    # The router returning learning_guide is a valid, schema-conforming response
    # that is nonetheless the wrong agent for this session.

# Bug #11 class: memory persistence — NOT "does the write call succeed"
async def test_conversation_is_semantically_recallable():
    await send_chat("My favorite topic is thermodynamics.", conversation_id="t2")
    point_count_before = await qdrant_client.count("student_memory")
    await send_chat("Remind me what I said my favorite topic was.", conversation_id="t2")
    point_count_after = await qdrant_client.count("student_memory")
    assert point_count_after > point_count_before  # actually reached Qdrant
    # WorkingMemory-only (Bug #11's actual behavior) would pass a "did the
    # request succeed" test while this assertion catches the bypass directly.
```

These are not replacements for guide 11's contract tests — they run alongside
them, against the same endpoints, asserting a different property.

## 4. What this domain needs that generic APM doesn't give for free

Standard APM (request traces, latency histograms, error-rate dashboards,
uptime probes) instruments the *transport* of a request through the system.
It has no vocabulary for the *content* of what came back. Three concrete,
buildable additions close that gap — none of them require a new platform,
all three are extensions of logging/metrics infrastructure that likely
already exists:

| Addition | What it captures | Built from |
|---|---|---|
| Per-request model/tier logging | Which model actually served each request, and whether that differed from what was requested (§1) | A structured log field + counter metric in `app/shared/llm_client.py`, keyed by `{feature, model_requested, model_served}` |
| Retrieval hit/miss + result count | Whether a RAG call returned anything, and how much, on every call (§2) | A structured log field + counter/histogram in `app/shared/embedding_service.py` or wherever the Qdrant query executes, keyed by `{collection, hit_count}` |
| Golden-transcript behavioral regression | Whether a small, fixed set of known conversation flows still behave correctly after a code change (§3) | A pytest suite that replays 5–10 fixed multi-turn transcripts (one per bug class: continuity, routing, memory) against the live agent stack and asserts on response *content/routing/side-effects*, not just status code — run in CI or on a schedule, same tier as a smoke test |

The third item is the most novel and the easiest to under-scope: it does not
need to be large. A handful of transcripts, each targeting one previously-real
bug (turn-2-references-turn-1, session-type routing, Qdrant write-after-chat),
re-run on every deploy or nightly, converts "an audit eventually finds this"
into "CI catches this before it ships." That is the entire discipline this
guide is arguing for, made concrete: don't wait for the next manual audit to
rediscover Bugs #9, #10, and #11's successors.

## Checklist (copy into project's docs when applying)

- [ ] Every LLM call logs `model_requested` vs. `model_served`; a metric
  distinguishes normal routing from fallback
- [ ] An alert fires when fallback-tier usage for any feature crosses a
  defined threshold over a rolling window — not only on total provider outage
- [ ] Any feature tuned against a specific model has a fail-fast startup check
  that the corresponding provider credential is present and non-blank
- [ ] The configured model-provider fallback chain has ≥2 reachable members,
  verified on a schedule (not just at initial setup)
- [ ] Every RAG/retrieval call logs hit/miss and result count, keyed by
  collection; a dashboard/alert exists on the zero-hit rate
- [ ] Generation responses carry (in logs, and ideally in the response itself)
  whether they were grounded in retrieved content or answered from parametric
  knowledge alone
- [ ] Agent/orchestration code has a behavioral test suite distinct from its
  functional/contract tests — assertions on conversation continuity, routing
  correctness, and memory persistence, not just status code and schema shape
- [ ] A small fixed set of golden conversation transcripts is re-run on a
  schedule (CI, nightly, or both) to catch behavioral regressions
