How to Use This Guide
This reference guide is a comprehensive operational manual for designing, deploying, monitoring, and recovering production-grade software systems on self-hosted Virtual Private Server (VPS) infrastructure. It is specifically optimized for small engineering teams (1–4 developers) operating without a dedicated SRE, DevOps, or QA function. The engineering recommendations throughout prioritize automation, simplicity, and low-overhead reliability.

Because modern development increasingly relies on CLI-based coding agents (such as Claude Code, Gemini CLI, Aider, etc.), the configurations, code examples, and processes in this guide are written with strict, explicit structures. AI agents reason more effectively over declarative files, clear folder paths, and well-documented runbooks than over "magic" dynamic behaviors or graphical dashboard interactions.

Branching by System Architecture
This manual contains distinct sections and implementation strategies depending on the system layer being built or evaluated:

Web Frontend (React/TypeScript/Vite): Focuses on CDN/Caddy static asset caching, browser metrics, and client-side error boundaries.

Mobile App (Flutter): Focuses on local storage migrations (Drift), state restoration, and offline-first degraded network resilience.

APIs & Backends (Django, FastAPI, Laravel): Details stateless container scaling, transaction-wrapped database configurations, and asynchronous task queues.

1. Production Readiness Fundamentals
To a mature engineering organization, a service is considered "production-ready" when its operational risks are systematically documented, bounded, and monitored. Reliability is not an accidental byproduct of writing clean code; it is an active architectural discipline designed to bound the blast radius of inevitable runtime failures.   

Core Reliability Engineering Metrics and Principles
In SRE, reliability and availability are mathematically distinct concepts:   

Availability: The probability that a system is capable of performing its required function at a given point in time. For a web service, this is typically measured as the ratio of successful requests to total requests:   

A= 
Total Requests
Successful Requests
​
 
Reliability: The probability that a system will perform its intended function without failure over a specified time interval. A system with high availability can have low reliability if it experiences frequent micro-outages that are quickly mitigated but disrupt active processes.

Scalability: The system's ability to handle increasing workloads by adding resources (horizontally or vertically) without degrading performance.

Operational risk management on a self-hosted single-node VPS requires a pragmatic approach to failure domain mapping. Because physical multi-region hardware clustering is typically cost-prohibitive for a small team, the primary objective is preventing a logical failure in one application from cascading and crashing the host's kernel.

2. Production Architecture for Small-Team VPS Deployments
To maximize resource efficiency on a self-hosted single VPS, production topologies must strictly isolate stateful databases from stateless web runtimes. This separation prevents application memory leaks from blocking database write transactions or saturating CPU cycles.

Stateful database containers utilize native Docker persistent volume binds to write to host-mapped SSD partitions, preventing data loss when containers are destroyed or updated.

3. Deployment Readiness
Deployment readiness ensures that environment configurations, secrets, and database structures are fully validated before exposing code to users. The following production-grade configuration defines a isolated multi-service Docker Compose blueprint:

YAML
# docker-compose.prod.yml - Multi-Service Production Deployment
version: "3.8"

networks:
  edge-net:
    external: true
  app-private-net:
    driver: bridge
    internal: true

services:
  app-api:
    image: company/backend-service:v2.4.1
    restart: unless-stopped
    networks:
      - edge-net
      - app-private-net
    environment:
      - NODE_ENV=production
      - DATABASE_URL=postgresql://app_user:${DB_PASSWORD}@app-db:5432/app_prod
      - REDIS_URL=redis://app-cache:6379/0
    deploy:
      resources:
        limits:
          cpus: '0.50'
          memory: 512M
        reservations:
          cpus: '0.10'
          memory: 128M
      restart_policy:
        condition: on-failure
        delay: 5s
        max_attempts: 3
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/api/v1/health"]
      interval: 10s
      timeout: 5s
      retries: 3

  app-db:
    image: postgres:16-alpine
    restart: unless-stopped
    networks:
      - app-private-net
    volumes:
      - pg-prod-data:/var/lib/postgresql/data
    environment:
      - POSTGRES_USER=app_user
      - POSTGRES_PASSWORD=${DB_PASSWORD}
      - POSTGRES_DB=app_prod
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 1024M

volumes:
  pg-prod-data:
    driver: local
Managing Runtime Secrets
To avoid configuration drift, secrets must never be committed to version control. On a self-hosted single VPS, secrets are injected via an encrypted, version-controlled vault wrapper (e.g., Ansible Vault or Mozilla SOPS), or managed securely directly within Coolify's environment variable matrix.

5. Observability
Observability relies on the interaction of three core pillars: structured logs, system metrics, and distributed request tracing.   

Structured Logging and Correlation IDs
Production log output must be formatted as structured JSON to allow automated parsing and prevent log injection vulnerabilities. Every inbound HTTP request must be assigned a unique X-Request-ID at the Caddy reverse proxy layer. This identifier must be propagated across all application threads, database queries, and background queues.

JSON
{"timestamp":"2026-07-18T13:04:13Z","level":"INFO","request_id":"req_8f12ac49b7e","trace_id":"tr_9918bc22a","service":"api-backend","message":"Order creation completed successfully","context":{"user_id":"usr_441","cart_id":"cart_928","duration_ms":142}}
System Performance Metrics: RED vs. USE
Quality engineering monitoring is split into consumer-facing metrics (RED) and resource-facing metrics (USE):

                   [ INBOUND SERVICE TRAFFIC ]

       RED Metrics             ▼             USE Metrics

   │ • Errors (Qty)  │   │ Container │   │ • Saturation %  │

RED (Rate, Errors, Duration): Measures service health from the client's perspective (Requests per second, error rate, request duration).   

USE (Utilization, Saturation, Errors): Measures host hardware health (CPU utilization, queue saturation, resource errors).

7. Incident Management Protocols
When outages occur, response coordination must follow a structured, predictable timeline.   

Incident Response Severity Levels
P1 - Emergency (Outage): Critical production components are offline, causing severe business impact (e.g., database connection pool exhaustion).

P2 - Degradation (High Risk): Core user flows are functional but experiencing high latencies or intermittent errors (e.g., API response times >500 ms).

P3 - Minor (Low Risk): Isolated, non-blocking bugs with functional workarounds (e.g., admin dashboard layout shifts).

9. Reliability Engineering: SLIs, SLOs, and Error Budgets
To keep development speed aligned with system stability, teams should define clear reliability metrics:   

Service Level Indicator (SLI): A quantifiable metric that measures the real-time performance of a service (e.g., the percentage of HTTP responses returned in less than 200 ms).   

Service Level Objective (SLO): A target reliability range specified for an SLI (e.g., SLI must be met 99.5% of the time over a 30-day window).   

Service Level Agreement (SLA): A contractual commitment to users that defines the financial or operational penalties if the system fails to meet the specified SLO targets.   

SRE prioritizes defining achievable reliability targets. An error budget represents the acceptable level of system downtime within a given period, calculated as:   

Error Budget=100%−SLO
If a service has an availability SLO of 99.9%, its error budget is 0.1%. If a high-volume feature release consumes the error budget, subsequent deployments are paused to focus development resources on system stability and reliability.   

10. Disaster Recovery and Business Continuity
Offsite backup strategies are critical for recovering from severe system failures. Backups should be automated, encrypted, stored offsite, and regularly tested.

The database backup process should stream compressed database dumps directly to an S3-compatible cloud storage destination, avoiding storage-intensive temp files on the primary host disk:

Bash
# automated-S3-postgres-backup.sh - Stateful Replication Pipeline
set -euo pipefail

DB_CONTAINER="production-postgres-db"
DB_USER="app_user"
DB_NAME="app_prod"
S3_ENDPOINT="https://your-r2-endpoint-id.r2.cloudflarestorage.com"
S3_BUCKET="s3://production-cold-backups"

TIMESTAMP=$(date +"%Y%m%d_%H%M%S")
BACKUP_FILE="/tmp/db_snapshot_${TIMESTAMP}.dump"

# Export compressed custom-format binary database archive (-Fc)
docker exec -t "${DB_CONTAINER}" pg_dump -U "${DB_USER}" -d "${DB_NAME}" -Fc > "${BACKUP_FILE}"

# Encrypt the exported file before transmitting offsite
gpg --encrypt --recipient "security@company.com" "${BACKUP_FILE}"

# Sync the backup to offsite S3-compatible cloud storage
aws s3 cp "${BACKUP_FILE}.gpg" "${S3_BUCKET}/db_snapshot_${TIMESTAMP}.dump.gpg" --endpoint-url "${S3_ENDPOINT}"

# Prune local database files older than 7 days
find /tmp -name "db_snapshot_*.dump*" -mtime +7 -delete

11. Security Operations and Vulnerability Management
Securing self-hosted systems requires enforcing strict operational boundaries. Administrators should harden host servers, restrict open ports, configure secure firewalls, and use SSH key-only authentication to prevent unauthorized access.

## 16. Common Operational Mistakes on Self-Hosted VPS

Hosting applications on a self-managed VPS is prone to specific, repeatable operational failures. The table below lists these common pitfalls and outlines strategies for preventing them:

| Mistake | Operational Risk | Actionable Prevention Strategy |
| :--- | :--- | :--- |
| **No Automated Backups** | Catastrophic data loss due to hardware degradation or software issues. | Implement daily S3 database backups with automated retention and encryption checks. |
| **Missing Monitoring** | Slow diagnostic timelines during service outages. | Configure Uptime Kuma for heartbeat checks, and Prometheus for resource metrics. |
| **Shared Production Credentials** | Unauthorized access and security vulnerabilities. | Use unique SSH keys, restrict access via UFW, and rotate secrets regularly. |
| **Unbounded Container Resources** | Memory leaks in one container crash adjacent services on the VPS. | Enforce strict memory and CPU resource ceilings on all Docker containers. |
| **Manual System Changes** | Configuration drift makes restoring servers difficult [cite: 12]. | Manage configurations using Infrastructure-as-Code and commit all Dockerfiles to git. |

## Appendix C: Pre-Release Production Readiness Checklist

Ensure all criteria are met before deploying updates to production:

### Infrastructure & Configuration
*   [ ] Application runs in stateless containers, with sessions stored in Redis.
*   [ ] CPU and memory resource ceilings are configured in `docker-compose.yml`.
*   [ ] Host firewall (UFW) restricts access to custom SSH and web traffic ports.

### Secrets & Configuration Management
*   [ ] Production secrets are stored securely in environment variables, never committed to git.
*   [ ] Configuration properties are versioned, and a `.env.example` template is maintained.

### Database Parity & Readiness
*   [ ] Schema migrations are tested and follow the expand-and-contract pattern.
*   [ ] Daily automated PostgreSQL backups stream compressed dumps directly to S3.
*   [ ] Eager-loading and strict relationship constraints are checked to prevent N+1 queries.

### Observability & Monitoring
*   [ ] JSON logging is formatted using standard request correlation IDs.
*   [ ] Prometheus monitoring metrics are enabled, and alert rules are validated.
*   [ ] Heartbeat and SSL metrics are monitored using Uptime Kuma.

### Security & Vulnerability Audits
*   [ ] Inputs are validated at system boundaries using schemas (such as Pydantic).
*   [ ] Outbound connections are restricted using secure bridge networks.
*   [ ] System dependencies are scanned for vulnerabilities before building images.

### Incident Management & SRE
*   [ ] Documented emergency runbooks are accessible in the project repository.
*   [ ] P1 alert routings are configured to reach responders via emergency channels [cite: 8].
*   [ ] Rollback scripts are verified and ready to execute immediately if deployments fail.

## Appendix D: Health Check Design — Shallow vs. Deep Verification

A `healthcheck:` block in `docker-compose.prod.yml` and a health probe in a rollout script are only as trustworthy as the endpoint they poll. Not every endpoint answering `/health` is asking the same question, and conflating the two is a recurring source of incidents that look, from the orchestrator's point of view, exactly like a healthy deploy.

### The Shallow Health Check
A shallow check (e.g. `/health/shallow`) answers a narrow question: is the web server process alive and accepting connections? It returns `HTTP 200 OK` immediately, without touching any dependency. This is the correct endpoint for a Caddy or load-balancer liveness probe running every few seconds — it is cheap, fast, and cannot itself cause cascading load on the database.

Its risk is exactly its cheapness: a shallow check returns 200 even when the database connection pool is exhausted, Redis is unreachable, or a required upstream service is down. The process is "up" and responding, but functionally dead — a **Zombie Service**. A load balancer routing traffic to it will keep sending users into a service that cannot do any work.

### The Deep Health Check
A deep check (e.g. `/api/v1/health/deep`) answers the question an orchestrator actually needs answered before it retires the old instance: is the system functional? It exercises the service's real dependencies rather than trusting that the process merely exists:

1. Database connectivity — a real query (`SELECT 1`), not a pooled-connection existence check.
2. Cache connectivity — a `PING` against Redis.
3. Disk space — enough headroom for logs, temp files, and writes.
4. Upstream dependency reachability — any service this one calls to do its job.

This is the endpoint deployment and rollout scripts (Shipwright, `tese.ps1`, a GitHub Actions deploy job) must poll before marking a new instance healthy and shifting traffic to it. Waiting on the shallow check instead is a common mistake, and it is a silent one: the deploy reports success, the container passes its liveness probe, and the rollout script exits 0 — while the service is quietly serving errors because its database or cache dependency never came up. The failure only surfaces downstream, in user-facing errors or a P2 page, well after the deployment has already been called "done."

### Implementation Blueprint (FastAPI)
```python
@app.get("/api/v1/health/deep")
async def health_check_deep(
    db: AsyncSession = Depends(get_db),
    cache: Redis = Depends(get_redis),
):
    health_status = {"status": "healthy", "components": {}}

    # 1. Database — a real query, not just a pooled connection
    try:
        await db.execute(text("SELECT 1"))
        health_status["components"]["database"] = "up"
    except Exception as e:
        health_status["status"] = "unhealthy"
        health_status["components"]["database"] = f"down: {e}"

    # 2. Cache
    try:
        await cache.ping()
        health_status["components"]["cache"] = "up"
    except Exception as e:
        health_status["status"] = "unhealthy"
        health_status["components"]["cache"] = f"down: {e}"

    # 3. Disk space
    free_pct = shutil.disk_usage("/").free / shutil.disk_usage("/").total * 100
    health_status["components"]["disk"] = f"{free_pct:.1f}% free"
    if free_pct < 10:
        health_status["status"] = "unhealthy"

    # 4. Upstream dependency (optional, add per service)
    # try:
    #     resp = await httpx_client.get(f"{UPSTREAM_URL}/health/shallow", timeout=2)
    #     resp.raise_for_status()
    #     health_status["components"]["upstream"] = "up"
    # except Exception as e:
    #     health_status["status"] = "unhealthy"
    #     health_status["components"]["upstream"] = f"down: {e}"

    if health_status["status"] == "unhealthy":
        raise HTTPException(status_code=503, detail=health_status)

    return health_status
```

### Orchestrator Integration
The container's `healthcheck:` directive (used by Docker to decide whether to route traffic and whether a restart policy should fire) should still target the shallow endpoint — it needs to run every few seconds without generating database load. The deployment script's post-rollout gate is a separate concern and must target the deep endpoint instead, polling `/api/v1/health/deep` until it returns 200 before it considers the new instance ready to receive production traffic and retires the old one. Using the same endpoint for both jobs — or worse, using the shallow endpoint for the rollout gate because it's the one already wired into `docker-compose.prod.yml` — is what lets a dependency-down state ship labeled "healthy."
