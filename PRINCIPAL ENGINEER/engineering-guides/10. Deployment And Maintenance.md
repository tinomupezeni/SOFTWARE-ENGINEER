Operating a self-managed Virtual Private Server (VPS) to host multiple independent applications simultaneously requires a shift in engineering discipline. Unlike managed Platform-as-a-Service (PaaS) environments where infrastructure orchestration, edge routing, and isolation are handled by a cloud provider, self-hosted multi-tenancy puts the responsibility of platform reliability directly on the engineering team. For a small team of one to four developers without a dedicated Site Reliability Engineering (SRE) department, the operational goal is to minimize administrative overhead by adopting standardized, robust, and automated procedures.

Using an orchestration layer like Coolify simplifies the developer experience by providing Git-driven deployment workflows, automatic SSL certificate provisioning, and pre-packaged database templates. However, the control plane itself is a Laravel-based application running as a suite of Docker containers that consumes approximately 500 to 700 MB of system memory at idle. While Coolify abstracts away basic container configurations, a deep understanding of the underlying Docker, Caddy, and Linux kernel mechanics remains necessary to prevent a resource spike or configuration failure in one project from destabilizing adjacent applications.

## Container Isolation and Host Resource Allocation

To run multiple distinct projects on a single Ubuntu-based VPS, physical system resources must be partitioned to prevent a single compromised or misbehaving application from starving others. Under standard Linux operations, a process that consumes excess memory triggers the host kernel's Out-Of-Memory (OOM) killer, which terminates processes based on heuristics—often taking down critical reverse proxies or databases instead of the leaking application.

Docker manages resource isolation through the Linux kernel's control groups (cgroups). Modern Docker Compose deployments utilize the `deploy.resources` schema to set hard limits and soft reservations.

The table below outlines the core resource isolation parameters supported in the Docker Compose v3 schema and their corresponding host-level mechanisms:

| Docker Compose Parameter | Host Linux Kernel Mechanism | Primary Operational Role | Production Heuristic / Guideline |
|---|---|---|---|
| `limits.memory` | Memory cgroup hard limit | Sets an absolute ceiling on physical RAM consumption. Exceeding this triggers the container-level OOM killer. | Set to 1.5x to 2x of the application's benchmarked peak memory footprint. |
| `reservations.memory` | Memory cgroup soft limit | Guarantees a minimum memory allocation. Under host resource contention, the kernel reclaims memory above this threshold first. | Set to the minimum memory required for application initialization and basic idle execution. |
| `limits.cpus` | Completely Fair Scheduler (CFS) quota | Limits the maximum CPU core allocation (e.g., `'0.50'` guarantees a maximum of 50% of a single core). | Limit background workers and non-critical services to fractional cores to protect edge routing. |
| `reservations.cpus` | CFS CPU weight shares | Determines relative CPU priority weight (default: 1024 shares) under heavy compute contention. | Assign higher relative weight to primary HTTP ingress API endpoints over asynchronous queues. |
| `limits.memory-swap` | Virtual swap-space cgroup | Controls total memory plus disk swap allocation. If omitted, default configurations may double the memory limit. | Set equal to `limits.memory` to disable swapping, avoiding disk I/O bottlenecks on shared VPS hardware. |

If resource allocations are left unconfigured, a single tenant application can consume all available host resources, impacting adjacent containers. The following production-grade Docker Compose manifest implements strict resource caps, ensuring that a memory leak or CPU spin lock in an application backend is isolated:

```yaml
version: "3.8"

networks:
  tenant_network_prod:
    driver: bridge
    attachable: true

services:
  tenant_app_api:
    image: node:20-alpine
    restart: unless-stopped
    networks:
      - tenant_network_prod
    environment:
      NODE_ENV: production
      DATABASE_URL: postgresql://tenant_user:${DB_PASSWORD}@tenant_postgres:5432/tenant_db
    deploy:
      resources:
        limits:
          cpus: '0.50'
          memory: 512M
        reservations:
          cpus: '0.10'
          memory: 128M
      restart_policy:
        condition: on-failure
        delay: 5s
        max_attempts: 3
        window: 120s

  tenant_postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    networks:
      - tenant_network_prod
    volumes:
      - tenant_postgres_data:/var/lib/postgresql/data
    environment:
      POSTGRES_USER: tenant_user
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: tenant_db
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 1024M
        reservations:
          cpus: '0.25'
          memory: 256M

volumes:
  tenant_postgres_data:
    driver: local
```

## Edge Routing, SSL Termination, and Reverse Proxy Engineering

Caddy acts as the unified edge gateway for the multi-tenant VPS. While Coolify automates route generation and handles SSL certificate renewals via Let's Encrypt, the underlying reverse proxy mechanics require careful configuration to ensure security and application compatibility.

A common issue in reverse-proxied environments is the infinite redirect loop. When a client establishes an HTTPS connection to Caddy on port 443, Caddy terminates the TLS layer and forwards the unencrypted HTTP request to the target container over the internal Docker bridge network. If the upstream application framework—such as Django, Laravel, or Symfony—is configured to enforce secure connections (e.g., `SECURE_SSL_REDIRECT = True` in Django), it will inspect the raw incoming request. Because Caddy communicates with the container via HTTP, the framework perceives the connection as unencrypted and issues an HTTP 301 redirect to HTTPS, creating an infinite routing loop.

To prevent redirect loops, Caddy automatically appends proxy headers, including `X-Forwarded-For` and `X-Forwarded-Proto`, to identify the original client protocol. The upstream application must be explicitly configured to trust and parse these headers to recognize that the client's connection to the edge proxy is secure.

```python
# Django settings.py production reverse-proxy configuration
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
SECURE_SSL_REDIRECT = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
USE_X_FORWARDED_HOST = True

# Explicitly declare origin trust to satisfy Django's CSRF verification checks
CSRF_TRUSTED_ORIGINS = ['https://project-alpha.production-domain.com']
ALLOWED_HOSTS = ['project-alpha.production-domain.com', 'localhost', '127.0.0.1']
```

For rate limiting, Caddy can utilize external modules like `caddy-ratelimit` or delegate downstream blocking to a host-level service like Fail2ban. The `caddy-ratelimit` module implements a token bucket algorithm to enforce constraints directly in the proxy layer. Fail2ban, alternatively, monitors Caddy's structured JSON access logs, identifying IPs that trigger high volumes of HTTP 4xx or 5xx codes and modifying the host firewall (iptables) to drop traffic from those sources.

The following configuration file details a production-ready Caddyfile with global configurations, explicit security headers, and an active rate-limiting policy:

```caddy
{
    # Global options block
    admin localhost:2019 {
        # Limit administrative access to the loopback interface
    }
    
    # Configure custom non-standard module execution order
    order rate_limit before basicauth
}

# Reusable security configuration snippet
(production_security_policies) {
    header {
        # Restrict rendering inside frames to prevent Clickjacking
        X-Frame-Options "DENY"
        # Enforce strict transport security for a year including subdomains
        Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"
        # Prevent MIME type sniffing
        X-Content-Type-Options "nosniff"
        # Control referrer policy
        Referrer-Policy "strict-origin-when-cross-origin"
        # Enable XSS filtering protection in legacy browsers
        X-XSS-Protection "1; mode=block"
    }
}

# Project Alpha Ingress Target
project-alpha.production-domain.com {
    import production_security_policies
    
    # Enforce request limits: maximum of 30 requests per minute grouped by client IP
    rate_limit {
        zone rate_limit_zone_alpha {
            key {http.request.remote_ip}
            events 30
            window 1m
        }
    }
    
    # Forward traffic to the project's internal Docker network endpoint
    reverse_proxy project_alpha_backend:8000 {
        header_up Host {http.request.host}
        header_up X-Real-IP {http.request.remote_ip}
    }
}
```

## Multi-Tenant Database Architectures (PostgreSQL and MySQL)

When hosting multiple independent projects, selecting the appropriate database topology is critical for balancing system performance against isolation. The database design must accommodate various database engines, primarily PostgreSQL and MySQL/MariaDB.

The table below contrasts the two primary database topologies:

| Evaluation Dimension | Shared DB Instance (Logical Databases) | Isolated Containers (DB Instance Per Project) |
|---|---|---|
| System Resource Allocation | Minimal memory overhead (~150MB-200MB base RAM total). Connection pools are shared. | High memory overhead (~150MB-300MB RAM per container). Consumes system resource limits. |
| Tenant Isolation & Security | Low. A single runaway query or lock in one database can saturate shared host resources. | High. A failure or resource leak inside one container has no operational impact on adjacent containers. |
| Backup and Recovery Workflow | Complex. Restoring a logical database requires manual drop-and-rebuild routines. | Simple. Volume isolation allows for clean backup scripts and granular disaster recovery. |
| Performance Constraints | Poor. Database engines cannot natively restrict memory or I/O at the logical database level. | Excellent. Docker resource limits can cap container performance individually. |

For a production VPS running more than three independent applications, the isolated container topology is recommended, provided the physical host has sufficient RAM to avoid resource contention.

### Database Engine Specifics and Management Mechanics

PostgreSQL and MySQL/MariaDB have different operational patterns that must be accounted for in a self-managed environment:

#### PostgreSQL

- Requires logical backups via the `pg_dump` utility. Creating a logical backup using the compressed binary format (`-Fc`) allows for parallel restores and selective table recovery during disaster scenarios.
- When executing migrations under high traffic, administrators must use the `CONCURRENTLY` modifier for index creation and configure an explicit `statement_timeout` to prevent blocking database transactions.

#### MySQL/MariaDB

- Uses the `mysqldump` utility to generate SQL dump files. Under high write load, performance tuning (such as adjusting `innodb_buffer_pool_size` to fit within allocated container memory reservations) is critical to prevent the container from being terminated by the cgroup controller.
- Because native `ALTER TABLE` operations in MySQL can lock tables for write operations, zero-downtime schema modifications on large tables with millions of rows require online schema change tools like `gh-ost` or `pt-online-schema-change`.

## Zero-Downtime Deployment and Migration Strategies

Achieving high availability on single-node VPS environments requires a structured deployment strategy. The team should target a recovery time objective (RTO) of near-zero seconds and a recovery point objective (RPO) of zero data loss for the stateless web tier.

On a single host, two primary paradigms achieve these availability targets: Blue-Green deployments via container routing manipulation and Directory-Level Atomic Symlink switching.

In the directory-level symlink paradigm, deployment files are unpacked into a uniquely timestamped directory. Persistent configurations (e.g., `.env` files) are mapped from a shared repository directory on the host. Once dependencies are compiled and smoke tests pass inside the new release directory, the active target symlink is swapped using an atomic operation: `ln -nfs /var/www/app/releases/<new_timestamp> /var/www/app/current`. The upstream process runner (such as PHP-FPM or Gunicorn) is then gracefully reloaded.

In containerized environments, the Blue-Green paradigm uses concurrent running instances of the application (referred to as the blue and green environments). When an update is initiated, the passive environment is constructed using the updated image. After validating that the new instance is healthy, Caddy's routing targets are dynamically reconfigured, directing all subsequent traffic to the new container. Once the connection draining window completes, the legacy container is safely terminated.

Alternatively, the `docker-rollout` utility acts as a lightweight Docker Compose plugin that performs rolling deployments. It deploys an updated image by spinning up a new container instance, waiting for its health check to pass, updating the proxy routing rules, and then gracefully stopping the deprecated container.

To support this pattern, applications must be completely stateless. Session states, transient files, and system uploads must be exported to external databases (such as Redis) or shared host volumes.

The following Bash script automates a zero-downtime blue-green container deployment cycle on a single VPS using Docker Compose and Caddy reloads:

```bash
#!/bin/bash
set -euo pipefail

# Configuration parameters
PROJECT_NAME="multitenant_app"
CADDY_CONTAINER_NAME="caddy_edge"
CADDYFILE_PATH="/etc/caddy/Caddyfile"
HEALTH_CHECK_PATH="/health"
HEALTH_TIMEOUT=30
DRAIN_DELAY=10

# Step 1: Identify currently active deployment target
# We inspect which container is running and routed.
ACTIVE_ENV=""
if docker ps --format '{{.Names}}' | grep -q "${PROJECT_NAME}_blue"; then
    ACTIVE_ENV="blue"
    PASSIVE_ENV="green"
    PASSIVE_PORT="8002"
else
    ACTIVE_ENV="green"
    PASSIVE_ENV="blue"
    PASSIVE_PORT="8001"
fi

echo "Active environment: ${ACTIVE_ENV}. Deploying to passive target: ${PASSIVE_ENV}..."

# Step 2: Build and pull updated image, then initialize the passive container
docker compose pull "app_${PASSIVE_ENV}"
docker compose up -d "app_${PASSIVE_ENV}"

# Step 3: Run health check validation loop against the newly spawned container
echo "Initiating health checks on port ${PASSIVE_PORT}..."
HEALTHY=false
for i in $(seq 1 ${HEALTH_TIMEOUT}); do
    if curl -s -f "http://localhost:${PASSIVE_PORT}${HEALTH_CHECK_PATH}" > /dev/null; then
        echo "Passive environment ${PASSIVE_ENV} is healthy."
        HEALTHY=true
        break
    fi
    sleep 1
done

if [ "$HEALTHY" = false ]; then
    echo "Error: Deployment failed. Healthy threshold not reached in passive container." >&2
    docker compose stop "app_${PASSIVE_ENV}"
    exit 1
fi

# Step 4: Perform Atomic Traffic Switch at the Proxy Layer
# We update the environment variable used by Caddy and reload.
echo "Updating Caddy routing configuration..."
sed -i "s/app_${ACTIVE_ENV}:[0-9]*/app_${PASSIVE_ENV}:${PASSIVE_PORT}/g" ${CADDYFILE_PATH}

# Gracefully reload Caddy without dropping connections
docker exec ${CADDY_CONTAINER_NAME} caddy reload --config /etc/caddy/Caddyfile

# Step 5: Connection Draining and Old Service Teardown
echo "Traffic switched. Waiting ${DRAIN_DELAY} seconds for active connection drain..."
sleep ${DRAIN_DELAY}

echo "Stopping legacy environment: ${ACTIVE_ENV}..."
docker compose stop "app_${ACTIVE_ENV}"
echo "Deployment successful."
```

### The Expand and Contract Schema Migration Pattern

Deploying code and running database migrations concurrently can result in deployment-window downtime if older application processes attempt to query a schema that has already been altered. To prevent this, teams must design backward-compatible schema changes.

The Expand and Contract pattern breaks structural database migrations into incremental phases:

```
Phase 1: EXPAND (Add new nullable column)
┌─────────────────────────────────┐
│ Database: [old_col] [new_col]   │
│ Code (V1): Reads/Writes old_col │
└─────────────────────────────────┘
                 │
                 ▼
Phase 2: DUAL WRITE (App writes to both)
┌───────────────────────────────────────────────┐
│ Database: [old_col] [new_col]                 │
│ Code (V2): Reads old_col, Writes both columns │
└───────────────────────────────────────────────┘
                 │
                 ▼
Phase 3: BACKFILL (Copy historical data)
┌──────────────────────────────────────────────────┐
│ Database: [old_col] [new_col]                    │
│ Background Task: Syncs old_col to new_col values │
└──────────────────────────────────────────────────┘
                 │
                 ▼
Phase 4: CUT-OVER (Switch reads to new column)
┌───────────────────────────────────────────────┐
│ Database: [old_col] [new_col]                 │
│ Code (V3): Reads new_col, Writes both columns │
└───────────────────────────────────────────────┘
                 │
                 ▼
Phase 5: CONTRACT (Remove deprecated database column)
┌─────────────────────────────────┐
│ Database: [new_col]             │
│ Code (V4): Reads/Writes new_col │
└─────────────────────────────────┘
```

The table below outlines the operational workflow for rename or split migrations across release cycles:

| Sequence Phase | Target Database Schema State | Application Code Execution State | Rollback Action |
|---|---|---|---|
| 1. Expand | Execute migration to append the new target column (must be nullable or have a safe default value). | Reads and writes only to the old column. | Execute schema migration rollback to drop the new column. |
| 2. Dual Write | Database contains both columns. | Writes to both columns during every INSERT and UPDATE. Reads remain on the old column. | Revert application code. No data is lost, as the legacy column is up to date. |
| 3. Backfill | Background worker copies historical values from the old to the new column. | Continues dual-writing active traffic and reading from the old column. | Safe to pause or stop the background execution process. |
| 4. Cut-over | Both columns contain identical datasets. | Update application code (wrapped in a feature flag) to read from the new column. Dual-writes continue. | Revert feature flag state to read from the old column, avoiding application redeployments. |
| 5. Contract | Execute database migration to drop the old column. | Reads and writes only to the new column. | None. Requires point-in-time snapshot database restoration. |

## Resilience, Backups, and Control Plane Disaster Recovery

A robust multi-tenant platform requires a unified disaster recovery and offsite backup plan. Backups must be automated, encrypted, stored offsite, and regularly tested.

For database backups, using native tools like `pg_dump` or `mysqldump` is preferred over copying physical volume directories. Copying volume directories on a running database container can result in corrupted backups if a transaction is committed during the file transfer.

The `pg_dump -Fc` command creates a custom, compressed binary archive that allows for parallel restores and selective table recovery during disaster scenarios.

The following Bash script automates the backup of an isolated PostgreSQL container, streams the compressed payload to an S3-compatible object storage repository (such as Cloudflare R2 or MinIO), and enforces a local retention policy of 7 days:

```bash
#!/bin/bash
set -euo pipefail

# Environment overrides or defaults
DB_CONTAINER_NAME="app_database"
DB_USER="db_user"
DB_NAME="app_prod"
S3_BUCKET_NAME="company-backups-production"
S3_ENDPOINT_URL="https://your-r2-endpoint-id.r2.cloudflarestorage.com"
BACKUP_LOCAL_DIR="/var/backups/postgres"

TIMESTAMP=$(date +"%Y%m%d_%H%M%S")
BACKUP_FILENAME="${DB_NAME}_backup_${TIMESTAMP}.dump"
LOCAL_FILE_PATH="${BACKUP_LOCAL_DIR}/${BACKUP_FILENAME}"

echo "[$(date)] Starting PostgreSQL logical backup execution..."

# Ensure target directory exists on the host
mkdir -p "${BACKUP_LOCAL_DIR}"

# Step 1: Perform pg_dump inside running container and write to host
# We use custom archive format (-Fc) which incorporates internal zlib compression.
if ! docker exec -t "${DB_CONTAINER_NAME}" pg_dump -U "${DB_USER}" -d "${DB_NAME}" -Fc > "${LOCAL_FILE_PATH}"; then
    echo "Error: Database pg_dump failed." >&2
    exit 1
fi

# Step 2: Validate backup file size and integrity
FILE_SIZE=$(du -h "${LOCAL_FILE_PATH}" | cut -f1)
echo "[$(date)] Local backup successfully generated: ${BACKUP_FILENAME} (${FILE_SIZE})"

# Step 3: Stream payload to S3-compatible remote storage
echo "[$(date)] Syncing backup to offsite storage: s3://${S3_BUCKET_NAME}..."
if ! aws s3 cp "${LOCAL_FILE_PATH}" "s3://${S3_BUCKET_NAME}/postgres/${BACKUP_FILENAME}" --endpoint-url "${S3_ENDPOINT_URL}"; then
    echo "Error: Upload to S3-compatible endpoint failed." >&2
    exit 1
fi

# Step 4: Enforce a strict 7-day local retention policy to protect local disk space
echo "[$(date)] Pruning local backups older than 7 days..."
find "${BACKUP_LOCAL_DIR}" -name "${DB_NAME}_backup_*.dump" -type f -mtime +7 -delete

echo "[$(date)] Backup lifecycle process completed successfully."
```

For MySQL or MariaDB instances, a similar script should be implemented utilizing `mysqldump` to generate backup files, routing the output to compressed files before uploading to S3.

### Coolify Control Plane Backup

When running Coolify, backing up individual application volumes is not sufficient. The core orchestrator state must be backed up to allow for rapid reconstruction of the VPS environment.

Coolify stores all its configurations, environment variable matrices, server SSH connection keys, and platform layouts under the host directory `/data/coolify`. To back up the orchestrator configuration, the system must compress this directory and upload the resulting archive to offsite storage:

```bash
# Compress the Coolify configuration directory while keeping services running
tar -czf /var/backups/coolify_core_backup_$(date +%F).tar.gz /data/coolify
```

### Disaster Recovery Runbook

In a total host failure scenario, the recovery team must execute the following structured recovery workflow:

```
                                  DISASTER OCCURS
                                         │
                                         ▼
                        1. Provision New Clean Ubuntu VPS
                                         │
                                         ▼
                        2. Restore Coolify Config Directory
                           • Untar backup to /data/coolify
                                         │
                                         ▼
                        3. Initialize Coolify Stack Services
                           • Run: docker compose up -d in source directory
                                         │
                                         ▼
                        4. Reconstruct Application Volumes
                           • Retrieve volume dumps from S3
                           • Restore using helper containers
                                         │
                                         ▼
                        5. Restore Tenant Database Schemas
                           • Use: pg_restore --clean --if-exists
                                         │
                                         ▼
                        6. Update Global DNS Records
                                         │
                                         ▼
                                SYSTEM FULLY ONLINE
```

- **New OS Provisioning:** Deploy a new clean Ubuntu VPS instance.
- **Restore Control Plane State:** Copy the latest system-level backup to the host, and unpack it to rebuild `/data/coolify`.
- **Restart Orchestration Stack:** Inside `/data/coolify/source`, execute `docker compose up -d` to restore the Coolify dashboard and its API connections.
- **Restore Docker Persistent Volumes:** Retrieve persistent application files from S3, create target Docker volumes on the new host, and unpack the archives:

```bash
docker run --rm -v app_volume_target:/target -v /tmp/restore:/source alpine sh -c "cd /target && tar -xzf /source/volume_backup.tar.gz"
```

- **Database Reconstruction:** Retrieve the latest database dump from S3 and restore it using the native command line tools:

```bash
docker exec -i target_db_container pg_restore -U db_user -d app_prod --clean --if-exists < /tmp/db_backup.dump
```

- **DNS Update:** Point domain zone records to the new VPS IP address.

### Single VPS Scaling Limits

A single VPS infrastructure has inherent scaling ceilings. The most critical failure vector is the Single Point of Failure (SPOF): if the hypervisor or hardware layer crashes, all tenant applications on that machine immediately go offline.

Additionally, multiple databases running concurrently can saturate host disk input/output operations per second (IOPS), generating CPU wait states that degrade web tier response times. When tenant traffic outgrows single-node limits, the architecture must scale horizontally by adding worker nodes and using Coolify to orchestrate containers across the cluster via SSH.

## Centralized Observability and Monitoring for Small Teams

A critical limitation of self-hosted PaaS solutions like Coolify is the absence of a built-in production observability stack. Without centralized monitoring, a small engineering team has no visibility into system metrics, and errors can go unnoticed until reported by end-users.

To maintain single-node stability, engineers must build a lightweight telemetry loop alongside their applications.

```
┌──────────────────────────────────────────────────────────────┐
│                      Host Linux Server                       │
│                                                              │
│  ┌───────────────────────┐        ┌───────────────────────┐  │
│  │   Caddy Edge Proxy    │        │  App Containers       │  │
│  │  • SSL Termination    │        │  • API / Worker       │  │
│  │  • Subpath Routing    │        │  • Log to stdout      │  │
│  └───────────┬───────────┘        └───────────┬───────────┘  │
│              │                                │              │
│              ▼ (Access Logs)                  ▼              │
│  ┌───────────────────────┐        ┌───────────────────────┐  │
│  │   JSON Logging        │        │ Docker Logging Driver │  │
│  │ • /var/log/caddy/...  │        │ • JSON-file / Local   │  │
│  └───────────┬───────────┘        └───────────┬───────────┘  │
│              │                                │              │
└──────────────┼────────────────────────────────┼──────────────┘
               │                                │
               ▼                                ▼
┌──────────────────────────┐        ┌──────────────────────────┐
│ Central Telemetry System │        │ External Telemetry       │
│ • Uptime Kuma Alerts     │        │ • Sentry (Error Trace)   │
│ • Heartbeat Validation   │        │ • PostHog (Analytics)    │
└──────────────────────────┘        └──────────────────────────┘
```

The telemetry architecture incorporates four core workflows:

### Heartbeat Validation (Uptime Kuma)

Deploying an isolated monitoring daemon like Uptime Kuma allows the team to perform continuous endpoint verification. Uptime Kuma should be run as a container separate from the main application environments to monitor service response times and SSL certificate expiration windows.

The container should be configured to dispatch alerts through team communication channels (e.g., Discord or Slack) immediately when an application registers an HTTP status code other than 200:

```yaml
# Uptime Kuma service definition
services:
  uptime-kuma:
    image: louislam/uptime-kuma:1
    volumes:
      - kuma_data:/app/data
    ports:
      - "3001:3001"
    restart: unless-stopped
```

### Centralized Logging and Rotation

Docker containers should write all error logs directly to standard output (stdout) and standard error (stderr). This allows the host engine's native logging drivers to manage log ingestion.

Without constraints, Docker's default logging driver will write JSON logs to the host disk indefinitely, which can eventually fill the partition and halt the server. The systems administrator must configure host-wide log rotation policies in the Docker daemon configuration file `/etc/docker/daemon.json`:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

### Upstream Error Tracking

The application code should be instrumented with error tracking libraries (such as Sentry). Sentry intercepts unhandled runtime exceptions, captures the local stack trace, and sends the diagnostic payload to an external dashboard, bypassing the local container lifecycle.

### Proxying Analytics Through Caddy

Ad-blockers frequently block analytics scripts (such as PostHog) when loaded from their default domains, which can lead to incomplete application telemetry.

To resolve this issue, the engineer can configure Caddy to proxy telemetry payloads through a trusted subpath on the primary application domain. This masks the analytics traffic from ad-blockers and ensures reliable event tracking:

```caddy
# Caddyfile subpath proxying for PostHog Integration
production-domain.com {
    # Reverse proxy application traffic
    reverse_proxy localhost:8000
    
    # Route analytics payloads through a custom subpath
    handle_path /telemetry-proxy* {
        # Strip the subpath before forwarding the request
        rewrite * /batch{path}
        
        reverse_proxy https://us.i.posthog.com {
            header_up Host us.i.posthog.com
            # Clear internal headers to prevent CORS configuration issues
            header_up -Origin
        }
    }
}
```

## Maintenance Discipline and Operational Lifecycle Protocols

For a small team of one to four engineers operating without a dedicated SRE team, maintaining platform reliability requires a structured approach to systems administration. Adopting a "boring tools" policy restricts the production environment to stable, well-maintained software.

```
       DAILY                     WEEKLY                    QUARTERLY
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│ • Check Alerting│       │ • Review Metrics│       │ • Dependency    │
│   Dashboards    │       │ • OS Patching   │       │   Audit         │
│ • Verify Backup │       │   & Security    │       │ • Test Disaster │
│   Logs          │       │ • Verify Backups│       │   Recovery Run  │
└─────────────────┘       └─────────────────┘       └─────────────────┘
```

The operations schedule should be divided into distinct, manageable intervals:

### Daily Operations Checklist

- Review active alerts on monitoring dashboards.
- Verify that backup execution logs confirm successful uploads to offsite storage.

### Weekly Operations Checklist

- **Operating System Patching:** High-risk security vulnerabilities (CVEs) should be patched promptly. Apply security-focused package upgrades weekly:

```bash
sudo apt update && sudo apt-get install --only-upgrade -y unattended-upgrades
```

- **Performance Telemetry Review:** Analyze key metrics—including CPU saturation, memory utilization, and network latency—to identify resource trends and address anomalies before they cause service degradation.
- **Backup Restorability Drills:** Download a random database backup file from offsite S3 storage, restore it onto a temporary container, and verify data integrity.

### Quarterly Operations Checklist

- **Dependency Audits:** Update container base images to their latest stable patch releases. Audit transitive dependencies and deprecate unmaintained or single-maintainer packages to minimize security vulnerabilities.
- **Active Recovery Simulations:** Execute a mock infrastructure recovery drill based on the Disaster Recovery Runbook to ensure the team can reliably rebuild the environment.

## Backup Scope Completeness Before Destructive Host Operations

Any deployment or rollback procedure that runs a destructive wipe against a host directory — `rm -rf`, `docker system prune -a --volumes`, a fresh archive extraction over an existing directory — must treat its own backup step as a manifest problem, not a memory problem. The failure mode is not "we forgot to back something up because we didn't think of it"; it is "we backed up the things that looked sensitive and missed the thing that was equally load-bearing but didn't look the part."

This happened on HBEC's own CD pipeline on 2026-07-21 (`HBEC/2026-07-21-hbec-missing-diagrams-and-rollback-bug.md`, Issue 2). The `rollback-vps` job in `.github/workflows/cd.yml` backed up `.env` and `docker/secrets/` before executing `sudo rm -rf /opt/hbec/*` — a reasonable-looking list, since both directories are unambiguously secret-shaped. It omitted `docker/keys/`, which held the JWT RS256 signing keys (`jwt_private.pem`), because a directory of keys doesn't register as "a secret" the way an `.env` file or a directory literally named `secrets/` does. The wipe deleted `docker/keys/` outright. `docker compose up -d` then ran, found nothing at the expected mount path, and Docker's own bind-mount behavior created an empty directory in its place — which is why the resulting container crash presented as `IsADirectoryError: [Errno 21] Is a directory: '/run/secrets/jwt_private.pem'` rather than a missing-file error. The keys had been restored to the VPS that same morning as the fix for an earlier, unrelated crash; the rollback silently undid the fix by deleting exactly what it had just repaired, and the next deployment's file extraction laid the codebase on top of the now-empty key directory without ever detecting the mismatch.

The general rule: before trusting a destructive step, enumerate every top-level directory under the path it will remove — derived from listing the actual target directory, not from a mental list of "the sensitive-looking ones" — and confirm each one has an explicit backup line before the wipe executes. `docker/keys/` did not look like `docker/secrets/` to whoever wrote the rollback job, but `rm -rf /opt/hbec/*` doesn't discriminate between them; it deletes both identically. A backup step is correct only if its file list was derived from the destructive step's actual scope:

```bash
# Before writing (or trusting) a destructive rollback step, enumerate
# every directory it will touch and diff against what the backup step covers.
comm -23 \
  <(find /opt/hbec -maxdepth 1 -mindepth 1 -type d -printf '%f\n' | sort) \
  <(echo -e ".env\ndocker/secrets\ndocker/keys" | sort)
# Any line printed here is a directory the wipe will delete
# that the backup step does not mention. Treat non-empty output as a
# release blocker, not a follow-up ticket.
```

The fix HBEC applied — patching `cd.yml` to explicitly back up and restore `docker/keys/` — closes this one instance. The durable fix is the enumeration habit: verify backup scope against the destructive step's actual target list every time either one changes, not against memory of what's secret-shaped.

## Triage Checklist: Service Unreachable Through the Gateway

A service reported as unreachable through the reverse proxy — 502, 404, or a browser-level connection error — can have root causes that look identical from the outside and require entirely different fixes. HBEC hit four distinct causes of this exact symptom class within an eleven-day span:

| Date | Symptom | Actual Root Cause |
|---|---|---|
| 2026-07-10 | admin-frontend → admin-backend 502; Caddy logged "aborting with incomplete response" | admin-backend was recreated onto `hbec_hbec-network` instead of `hbec_app-net`; Docker DNS could not resolve `admin-backend` from the frontend's network |
| 2026-07-13 | student-frontend → student-backend/harness 502; Nginx logged "could not be resolved (2: Server failure)" | Same class as above: student-backend and harness landed on `hbec_hbec-network` after a Redis/PgBouncer-triggered restart, while student-frontend stayed on `hbec_app-net` |
| 2026-07-14 | admin.hbca.tech 502; Caddy logged "lookup hbec-admin-frontend on 127.0.0.11:53: server misbehaving" | The container never actually started — it was stuck in Docker's `Created` state after an interrupted deploy; Docker DNS cannot resolve a container that was never running |
| 2026-07-21 | Both frontends threw `ERR_NETWORK_CHANGED` in-browser; backends showed `(unhealthy)` in `docker ps` | The Dockerfile `HEALTHCHECK` and a hardcoded compose override still probed the retired `/health/` path after the app split into `/health/live/` + `/health/ready/`; Docker marked healthy containers unhealthy and the gateway correctly refused to route to them |

The checklist below runs through cheapest-to-check first, and each item is grounded in the specific incident it would have caught:

1. **`docker ps -a`, not `docker ps`.** Confirm the container is actually `Up`, not `Created` or `Exited`. A container stuck in `Created` state produces the exact same "server misbehaving" gateway log line as a genuine DNS failure — this is what a bare `docker ps` misses (2026-07-14).
2. **If the container is `Up`, compare its attached networks against what the compose file declares**: `docker inspect <container> --format '{{range .NetworkSettings.Networks}}{{.NetworkID}} {{end}}'`. A `docker compose up -d` recreate that doesn't cleanly merge dev and production network overrides can land a service on the project's default network instead of the shared app network — same "502, DNS can't resolve" symptom as a stopped container, distinguishable only by actually inspecting networks rather than assuming the container is simply down (2026-07-10, 2026-07-13).
3. **If reattaching a container to a network manually, always pass `--alias`**: `docker network connect --alias <service-name> <network> <container>`. A bare `docker network connect` attaches the container to the network but does not register the DNS alias the other services depend on, so the "fix" silently accomplishes nothing (2026-07-10).
4. **Check whether a healthcheck or routing path changed recently without every reference to the old path being updated in lockstep.** HBEC's healthcheck split (`/health/` → `/health/live/` + `/health/ready/`) was applied to the application but missed in two other places pinning the same literal string: the Dockerfile's `HEALTHCHECK` instruction and a hardcoded compose override. Grep the whole tree for the retired path, not just the file you remember changing (2026-07-21).
5. **Read the gateway's own log line before touching anything downstream.** The specific wording distinguishes a DNS failure ("server misbehaving", "SERVFAIL") from a healthcheck-driven route refusal (container shows `(unhealthy)` in `docker ps`, no DNS error at all) from a container that never started. All three present identically as "502 from the gateway" to a user; they are diagnosed and fixed differently, and the log line is what separates them (all four incidents above).
6. **Confirm the fix from inside the Docker network, not just from the host.** `docker exec <upstream-container> curl -s -o /dev/null -w '%{http_code}' http://<target-service>:<port><health-path>` is the exact check that separated "the target container is healthy" from "the depending container can actually reach it" in the 2026-07-10 incident, where the admin-backend answered `200` locally while remaining completely unreachable from admin-frontend.

## Deployment Verification Strategy: Choosing a Pattern and Avoiding the False-Positive Trap

Verifying that a deployment is actually healthy — not merely that a process started — requires choosing a verification strategy deliberately rather than defaulting to whichever check is easiest to write. Three patterns cover most needs, and they trade off differently:

| Pattern | Goal | Cost | Risk |
|---|---|---|---|
| **Staging environment** | Environment parity — catch bugs before they reach production | High: doubles infrastructure, and every environment-specific detail (DNS, SSL, secrets) must be replicated | "Works on staging, fails on production" — usually a DNS or SSL mismatch staging never reproduced |
| **Smoke testing** | Immediate vital-signs check immediately post-deploy | Low: a handful of scripted HTTP calls against the freshly deployed release | The bug is live in production for the seconds-to-minutes between deploy and smoke-test completion |
| **Blue-green** | Zero-risk traffic switch (mechanics covered under "Zero-Downtime Deployment and Migration Strategies" above) | Medium: doubles the running footprint of the service being replaced for the duration of the switch | State or database-version conflicts between the outgoing and incoming environment if either writes to shared storage |

For a team running a single VPS with Docker Compose and no dedicated staging host, smoke testing is usually the right starting point: it delivers most of the verification value for a fraction of the infrastructure cost of a full staging environment, and it composes cleanly with the health-check-then-tag-marker rollback flow described earlier in this guide. Blue-green is the natural next step once the team can afford to run two copies of a service simultaneously — at that point smoke testing becomes the gate the *passive* environment must clear before the traffic switch executes, rather than a check run against an already-live production after the fact. A full staging environment is worth its doubled infrastructure cost primarily once DNS or SSL configuration has already caused a "passed on staging, failed on production" incident at least once — before that, it is optimizing for a failure mode the team has not yet actually hit.

### The False-Positive Trap

The most common mistake in smoke testing is checking only for HTTP 200. A 200 confirms the process is listening and returned *a* response; it does not confirm the response is correct, complete, or safe to serve. Three checks catch what a bare status-code check misses:

1. **Asset integrity.** Does the delivered HTML actually point to CSS and JS files that exist and return 200 themselves? A build that succeeds but ships a stale asset manifest — pointing the index page at a hashed bundle filename from the *previous* build — returns HTTP 200 for the page and 404 for every asset it references. A status-code-only smoke test reports the deployment healthy while every user sees an unstyled or broken page.
2. **Environmental leaks.** Does the delivered JS bundle contain the string `localhost` or `127.0.0.1`? A build that inlined a development-environment API base URL instead of the production one still returns HTTP 200 for the page load — the failure only surfaces once the bundle tries to call an API that doesn't exist from the client's network. Grepping the built bundle for these strings before serving it catches this before a user does.
3. **Dependency health.** Can the API actually reach its own dependencies — database, cache, downstream services — or does it only prove it can accept a TCP connection and answer `/health`? A shallow health check that returns 200 unconditionally, and a "deep" one that was never actually wired to the database connection, both report healthy while every real request fails. This is the same distinction this guide's own health-check split (`/health/live/` vs. `/health/ready/`) exists to make: liveness proves the process is running; readiness proves it can actually serve traffic.

One prior engagement — an internal marketplace project referred to as Tese-Marketplace — adopted smoke testing as its first verification layer specifically because it delivered roughly 80% of the value for roughly 20% of the effort relative to a full staging environment, then hardened that smoke test by grepping the delivered frontend bundle for `localhost`, closing exactly the environmental-leak gap in item 2 above. As the platform's availability requirements grew, the intended evolution was toward blue-green: using the passive environment as a private validation target the smoke test runs against *before* the reverse-proxy switch flips, rather than validating against production after the fact.

## Host-Level Failure Modes Beneath Docker

Not every "the containers are unreachable" incident is a Docker or application problem. On at least one occasion, HBEC's VPS lost its `systemd` daemon entirely — the process manager Docker itself, `sshd`, and every other host service depend on to start, stop, or restart — and the failure sat beneath the entire container stack rather than inside it (`VPS_SYSTEMD_LOCKUP_DIAGNOSIS.md`).

The symptom is distinctive: any command that asks systemd to manage a service (`sudo systemctl restart docker`, `sudo dpkg --configure -a`) hangs or fails immediately with `Failed to restart <service>.service: Transport endpoint is not connected`. This means the communication channel between the kernel/user-space tools and systemd itself is dead — typically caused by a zombie mount (a corrupted Docker volume or network filesystem that locked up the kernel's virtual filesystem layer) or a prior soft-reboot attempt that sent SIGTERM/SIGINT to a systemd that was already unresponsive and therefore never actually rebooted.

Two consequences follow directly from systemd being the actual failure point rather than Docker:

- **`docker restart` / `docker compose up` are not diagnostic tools here.** Both depend on the same systemd-managed `docker.service` that is unreachable; running them reproduces the same hang or the same "transport endpoint" error rather than yielding new information.
- **`sudo reboot` will not recover the host.** A terminal-issued reboot is itself a request routed through systemd — the exact channel that is dead. It must be treated as a no-op, not a legitimate recovery attempt that "didn't work this time."

Recovery requires going outside the host entirely: from the hosting provider's control panel (Contabo, DigitalOcean, etc.), issue a **Power Off / Force Stop** — not the panel's "Reboot" button, which frequently just relays the same soft signal the terminal already sent — wait 30–60 seconds for the VM to fully de-allocate, then power it back on. Only once systemd is confirmed responding normally again is it safe to resume the work that was interrupted; in HBEC's case that meant finishing a package-manager repair (`dpkg --configure -a`) and an NVIDIA Container Toolkit install that the lockup had cut off mid-sequence. Do not attempt an OS upgrade (`do-release-upgrade`) while systemd is in this state — layering a major upgrade on an already-unstable service manager is more likely to compound the corruption than fix it.

This is a single incident, not a recurring class the way the network-mismatch and healthcheck-path failures above are — but it belongs in this guide precisely because none of the Docker-layer or application-layer remediation described elsewhere in this document (network reattachment, healthcheck fixes, rollback procedures) is reachable at all until the host's own service manager is confirmed to be responding.
