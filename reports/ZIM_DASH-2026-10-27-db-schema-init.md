# ZIM DASH Database Bootstrap: iam/catalog/orders Schemas (ZD-M1-01)

**Date:** 2026-10-27
**Project:** ZIM DASH
**Type:** Feature (database bootstrap)
**Status:** Completed

## Summary
Implemented ZD-M1-01: the first real Postgres schema for ZIM DASH via
Alembic — `iam.users`, `catalog.{restaurants,menu_items,promo_codes}`, and
`orders.{orders,order_items,favorites}`, backed by SQLAlchemy 2.0 async
models as the source of truth. Deliberately excludes the geospatial
(ADR-008) and composite-address (ADR-011) columns per the repo's own
documented migration sequencing — those arrive with ZD-M1-10 and ZD-M1-15
respectively.

## Context / Trigger
Direct follow-on to ZD-M1-02 (FastAPI boilerplate, same session). Read
`docs/architecture/database_design.md` in full before writing any model —
it's an unusually complete, already-reviewed design doc (down to exact
column types, constraint names, and an explicit "Section 6: Gap Found"
noting the task's original scope had been corrected to include the
reference-data tables).

## Scope
In scope: exactly the 7 tables `database_design.md` Section 5 assigns to
migration 1, plus `payment_status`/`payment_reference` on `orders.orders`
(explicitly called out in both the doc and the ProjectFlow task). Out of
scope, by the same doc's own sequencing: `postgis` extension + spatial
columns (ZD-M1-10), the `ledger` schema (ZD-M1-13), composite-address
columns (ZD-M1-15).

## Method
Defined SQLAlchemy models first (the normal Alembic workflow: models are
the source of truth, migrations are generated from them, not hand-authored
independently) and used `alembic revision --autogenerate`, then reviewed
and corrected what autogenerate cannot produce on its own — schema
creation, enum-type cleanup — rather than trusting the raw output.
Verified the whole thing empirically: upgrade, downgrade, re-upgrade,
`alembic check` for zero drift, and a real constraint-violation test,
against an actual local Postgres (torn down afterward), not just a
read-through of generated SQL.

## Decisions & Findings
- **Autogenerate noise from the PostGIS image itself.** Setting
  `include_schemas=True` (needed because none of our tables live in
  `public`) also reflects the `postgis/postgis` Docker image's bundled
  `postgis_tiger_geocoder` extension — hundreds of tables, many installed
  directly into `public`, not a separate schema. Without an `include_name`
  filter scoped to the app's own schemas (`iam`/`catalog`/`orders`/
  `ledger`), every autogenerate run proposed dropping all of them. This is
  a known gotcha with PostGIS-bundled images + Alembic autogenerate, not
  specific to this schema design — worth remembering for ZD-M1-10, which
  will be the first migration to actually touch PostGIS types.
- **Schema/enum-type lifecycle isn't autogenerate's job.** Alembic's
  autogenerate correctly emits `CREATE TABLE ... schema=X`, but never
  emits `CREATE SCHEMA` (schemas aren't part of SQLAlchemy table metadata),
  and `DROP TABLE` never drops the Postgres `ENUM` type a column used — a
  bare autogenerate-then-run would have failed on the second
  upgrade/downgrade cycle with "type already exists". Added explicit
  `CREATE SCHEMA IF NOT EXISTS` at the top of `upgrade()` and `DROP TYPE`/
  `DROP SCHEMA` at the bottom of `downgrade()`, verified by actually
  running the round trip twice.
- **Alembic runs sync; the app runs async.** Settings expose one
  `DATABASE_URL` (asyncpg, for the app); `alembic/env.py` derives the sync
  URL by swapping the driver (`+asyncpg` → `+psycopg`) rather than keeping
  a second URL that could drift from the first.

## Changes Made
- `backend/app/db/base.py` — the declarative `Base`, with an explicit
  naming convention so Alembic's constraint names stay readable.
- `backend/app/models/{iam,catalog,orders}.py` — the 7 tables, 3 Postgres
  ENUM types (`identity_type`, `discount_type`, `order_status`).
- `backend/alembic/` (`env.py`, `alembic.ini`, the generated migration
  under `versions/`) — schema-filtered autogenerate, sync driver
  derivation, date-prefixed migration filenames.
- `backend/tests/test_migrations.py` — new `pytest -m db` integration
  suite (3 tests), excluded from the default fast test run.
- `backend/pyproject.toml` — added `psycopg[binary]`; a per-file Ruff
  ignore for autogenerated migration files; `UP042` ignored project-wide
  (the `class X(str, enum.Enum)` pattern SQLAlchemy's `Enum` column type
  expects — ruff's own suggested `enum.StrEnum` fix is flagged unsafe by
  ruff itself and changes `str()`/formatting behavior, so left as-is
  rather than auto-applied).
- `backend/README.md` — migration commands and the DB-test marker
  documented.
- Commit `421fb12`, pushed to `origin/main`.

## Verification
- `ruff check .`, `black --check .` — clean.
- `pytest` (default, no DB) — 1/1 passing.
- `pytest -m db` (live Postgres via `docker compose up -d db`) — 3/3
  passing: all 7 tables exist post-migration; a `NAMED` user without a
  `phone_number` is rejected by the `named_requires_phone` CHECK
  constraint; a full downgrade leaves zero schemas and zero enum types
  behind (re-upgraded afterward so the test fixture's own teardown has a
  consistent state to act on).
- Manually ran upgrade → downgrade → upgrade → `alembic check` end to end
  against the same database; `alembic check` reported "No new upgrade
  operations detected" — confirms the models and the migration agree
  exactly, not just that the migration runs without erroring.
- Tore down the local Postgres container and removed all local build
  artifacts (`.venv`, `.env`, caches) afterward.
