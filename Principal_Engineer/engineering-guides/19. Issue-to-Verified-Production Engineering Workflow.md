The central rule is:

> A change is not Done when code has been edited. It is Done when the intended
> behavior is proven in the target staging environment, the exact verified
> artifact is promoted and checked in production, the issue record is accurate,
> and recurrence is prevented by a test, guard, standard, or operational check.

## 1. The Closed-Loop Workflow

Every production issue, regression, or high-risk change follows this sequence:

```text
Discover → Triage → Directive → Root-cause audit → Implement
     ↓                                      ↓
  Log issue                         Regression evidence
     ↓                                      ↓
Staging deploy ← exact commit ← Build once
     ↓
Behavioral verification
     ↓ pass                         ↓ fail
Promote exact artifact       Stop; fix or roll back
     ↓
Production verification
     ↓ pass                         ↓ fail
Merge/approve and close      Roll back; keep main unchanged
     ↓
Update standard/check → review recurring patterns
```

No later stage may be used to compensate for a skipped earlier stage. A green
Docker build does not replace behavioral testing. A successful SSH command does
not prove that the intended container was targeted. A passing HTTP status does
not prove that the business behavior is correct.

## 2. Triage and Issue Logging

Create an issue log as soon as the work is confirmed to be a production defect,
deployment failure, user-impacting regression, data-integrity risk, or repeated
engineering failure. Use `templates/issue-template.md` and include:

- the exact environment and time first observed;
- the user-visible symptom and the underlying system symptom separately;
- the commands, logs, request paths, commit SHAs, and service names used as evidence;
- current status honestly: `Investigating`, `Workaround Applied`, or `Resolved`;
- related issue links when the same pattern has appeared before;
- prevention items that are still open.

Do not mark an issue `Resolved` merely because service restarted or a workaround
was applied. If a prevention item remains essential, use `Workaround Applied`
or `Investigating`, and create a follow-up directive for it.

### 2.1 Classify the failure before assigning work

| Class | First question | Typical control |
|---|---|---|
| Code defect | What behavior violates the contract? | Regression test and pattern search |
| Integration/contract | Which producer and consumer disagree? | Contract test and deployed endpoint check |
| Configuration | Which value differs across environments? | Fail-fast validation and config diff |
| Deployment | What exact commit/image is running? | SHA/digest verification |
| Data | Is state missing, duplicated, or malformed? | Read-only audit, rehearsal, idempotent remediation |
| Infrastructure | Is the service down or only unreachable through the gateway? | Layered health and gateway triage |
| Process | Which gate or handoff allowed this through? | Update directive, checklist, or automation |

Classification is not a final diagnosis. It determines which verification lens
must be applied first.

## 3. Directive and Acceptance Contract

Before implementation, create one concise directive in the project’s Blueprint
or task system. It must contain:

1. **Context:** project, environment, affected services, relevant files, and known history.
2. **Problem:** observed behavior versus expected behavior.
3. **Scope:** what may be changed and what must remain untouched.
4. **Standard references:** the guide, project rules, and previous issue logs.
5. **Acceptance criteria:** observable outcomes, not implementation preferences.
6. **Verification commands:** exact commands and target URLs/scripts.
7. **Definition of Done:** code, tests, staging evidence, artifact identity, production evidence, and documentation.

Bad directive:

```text
Fix the deployment problem and make login work.
```

Useful directive:

```text
Trace the staging admin login 400 from browser request to Django response.
Identify whether the failure is payload, route, authentication configuration,
or deployed-image drift. Add a regression test for the confirmed cause.
Verify with the staging login smoke test and record the deployed image SHA.
Do not change production until staging passes.
```

One task should have one accountable owner, even when several agents assist.
Agents may investigate in parallel, but their findings must be consolidated into
one directive before overlapping edits begin.

## 4. Root-Cause and Pattern Audit

An agent’s first plausible explanation is a hypothesis, not a root cause. Require
the investigator to check four layers:

1. **Source:** inspect the actual implementation, configuration, and generated files.
2. **Runtime:** inspect the running container, environment, route, logs, and dependency state.
3. **History:** inspect blame, recent merges, prior fixes, and related issue logs.
4. **Pattern:** search for the same bad assumption in sibling files, services, environments, and scripts.

The fourth layer prevents the common failure where one copied ORM field, URL,
environment key, route, or migration command is fixed in one place while the
same defect remains elsewhere.

### 4.1 Separate observer failures from subject failures

When a deployment script, health check, or monitoring command fails, first prove
whether the application itself is healthy independently. A broken observer can
hide the real application failure. For cross-shell commands, prefer a checked-in
script inside the target image or host over complex escaped one-liners.

Never use `|| true` around a release-critical step such as migrations, image
selection, health checks, or smoke tests. If a non-critical cleanup is allowed
to fail, log the failure explicitly and state why it cannot block release.

## 5. Implementation and Regression Proof

The implementation must include evidence that would fail before the fix and pass
after it. Choose the strongest applicable proof:

- unit test for deterministic logic;
- integration or contract test for producer/consumer boundaries;
- migration rehearsal against an isolated database;
- real API/UI smoke test against the running staging environment;
- real device test for mobile, webhook, payment, or platform behavior;
- data audit before and after a remediation;
- failure-injection or rollback test for infrastructure changes.

Mocks alone do not prove a deployed integration. A test that checks only `200 OK`
does not prove routing, identity, persistence, content correctness, or user
workflow correctness. Attach the command and meaningful output to the directive,
pull request, or issue log.

## 6. Staging Gate and Artifact Eligibility

Staging is the release candidate environment, not merely a place to see whether
containers start. The staging gate must record:

- source commit SHA;
- image tags and, where available, image digests;
- database migration result;
- container readiness and deep dependency health;
- API and frontend smoke results;
- critical user-journey result;
- relevant error-log scan;
- known deviations from production topology or data.

Only an artifact that passes the staging gate is eligible for production. Guide
18 then governs promotion: copy or pull the exact image tags/digests and do not
rebuild from a different checkout. If staging and production use different
configuration, test the configuration boundary separately; do not call the
application verified merely because the image is identical.

## 7. Production Gate, Rollback, and Merge Order

Production deployment must be readiness-gated and observable. Verify the gateway,
critical endpoints, dependencies, logs, and one or more real user journeys.
Record the production image identity and write the last-known-good marker only
after verification passes.

If production verification fails:

1. stop further promotion;
2. keep the staging branch and `main` unchanged;
3. roll back to the last-known-good artifact when safe;
4. preserve logs, image identity, and failed verification output;
5. update the issue log and create a corrective directive.

Only after production passes may the verified staging commit be merged into
`main`. Prefer fast-forward promotion so the tested commit remains identifiable.
If a merge commit changes the tree, it is a new artifact and must not inherit
the prior verification claim without being rebuilt and tested.

## 8. Multi-Agent and CLI Handoffs

Every handoff must carry the same compact record:

```text
Project / environment:
Issue or directive:
Current hypothesis:
Evidence already collected:
Files and services in scope:
Changes already made:
Commands that passed:
Commands that failed:
Open risks and assumptions:
Next verification required:
```

The receiving agent must verify repository state before editing: branch, commit,
working-tree changes, running environment, and current artifact identity. It
must not trust a previous agent’s “done” statement without rerunning the named
verification. Parallel agents should return findings and patches to a single
integrator; they should not independently deploy competing versions.

## 9. Closure and Institutional Learning

Close the loop only when all of the following are true:

- the root cause is stated in causal terms, not just a symptom;
- the fix is committed and linked to the issue/directive;
- the regression or behavioral proof passes;
- staging and production artifact identities are recorded;
- production verification passes, or an explicit workaround owner and expiry exist;
- data remediation is complete and audited where applicable;
- prevention actions are completed or tracked as separate owned work;
- the issue is linked to related incidents and the relevant standard is updated.

When the same failure class occurs twice, add a checklist or automated guard.
When it occurs three times, make the guard part of the release gate or CI. A
postmortem that does not alter a test, script, standard, alert, or ownership
model is a record, not prevention.

### 9.1 The "Unfinished Pipe" Failure Mode

A feature can have every individual piece built — model, serializer, UI
component, even a passing unit test on each piece in isolation — and still
be completely non-functional in production, because nobody ever exercised
the *connection* between the pieces. This is a distinct failure mode from a
regression: nothing broke, because nothing was ever finished, and no error
proves it because no code path ever runs it. HBEC produced a cluster of
these in one session: a "Project Guide" chat feature that returned a
hardcoded string after a `Future.delayed` because the real streaming
endpoint was never wired up; a template picker reading from a database
table nobody had ever populated end-to-end; a fully built paper-upload
dialog with no route or button anywhere that actually opened it; an admin
API-key vault whose "real" encryption and routing were stubbed with a no-op
receiver and a dead Celery task.

Each of these would pass a component-level test suite and a code review
that checks the diff in isolation. None would survive one real end-to-end
click through the feature as a user would use it — which is exactly why
each was found by someone doing that (a live demo, a direct user request to
use the page, a read-only audit), not by CI.

**Rule:** a feature's Definition of Done (§3) must include *reachability*:
proof that a real user action reaches the real code path end-to-end, not
just that each piece independently compiles, unit-tests green, or renders.
When a feature is scaffolded across more than one layer (model → API → UI,
or producer → replication → consumer), the acceptance criteria must name
the specific action that exercises the full chain, and that action must
actually be performed — clicked, called, or scripted — before the feature is
marked Done.

## Checklist (copy into project's docs when applying)

- [ ] Issue uses `templates/issue-template.md` and records environment, evidence, status, and owner
- [ ] Directive states context, scope, acceptance criteria, standards, and exact verification commands
- [ ] Root cause was checked in source, runtime, history, and sibling patterns
- [ ] Observer/tooling failures were separated from application failures
- [ ] No release-critical command is hidden behind `|| true` or equivalent error suppression
- [ ] Regression proof fails before the fix and passes after it
- [ ] Staging verifies real behavior, dependencies, migrations, and critical user journeys
- [ ] Commit SHA and image tags/digests are recorded before promotion
- [ ] Production uses the exact staging artifact and does not rebuild it
- [ ] Production readiness and live behavior are verified before approval
- [ ] `main` is updated only after production verification succeeds
- [ ] Rollback uses a known-good artifact and preserves failed evidence
- [ ] Every agent handoff includes current state, evidence, risks, and next verification
- [ ] Issue closure is honest about remaining prevention work
- [ ] Repeated failures produce a new automated guard, standard, or release gate
- [ ] Multi-layer features (model → API → UI, or producer → replication → consumer) have a named end-to-end action proving reachability, actually performed — not just each layer's isolated test passing
