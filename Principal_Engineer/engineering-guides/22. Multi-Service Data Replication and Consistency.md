## Why this guide exists

Guide 6 (Database Engineering) covers a single database done well. It says
nothing about what happens when the *same* entity legitimately lives in two
or more databases at once — which is exactly what happens the moment a
system splits into more than one service, each with its own schema, and
something has to keep them in agreement. That gap produced a distinct,
repeating family of incidents at HBEC (Admin CMS ↔ Student Backend ↔ Agentic
Harness) concentrated almost entirely in a single week (2026-09-09 to
2026-09-11) — evidence that this is a structural blind spot, not a run of
bad luck.

## 1. A cross-service id is not a foreign key, and nothing enforces it

When Service A owns entity X and Service B stores `x_id` as a plain integer
or UUID column, no database constraint links them — they're different
databases. Referential integrity across that boundary exists only if
something in application code maintains it. Deleting or archiving `X` in
Service A does nothing to Service B's copy unless a retraction path was
explicitly built for it.

HBEC hit this twice, a day apart, on sibling models with the same shape:

- `2026-09-10`: `ExamPaper` delete/unpublish had a deliberate retraction
  signal (`_handle_content_retraction`) — because an *earlier* bug had let
  an archived syllabus keep being served downstream — but that retraction
  path was scoped to `Content` only; `ExamPaper` shares the same
  dual-replication shape and was never audited at the same time, so it had
  no `post_delete` receiver and no unpublish path of its own.
- `2026-09-11`: student-side `Paper` rows carry `harness_paper_id` as an
  unenforced FK-by-value to the harness's `papers.id`. When a harness paper
  was deleted, nothing on either side retracted or nulled the reference —
  the exact same gap, one day later, on a different model pair.

**Rule:** the first time a delete/unpublish/archive retraction path is built
for *any* entity in a multi-service system, immediately enumerate every
other entity that shares the same "produced here, mirrored there" shape and
give it the same treatment in the same change. Do not wait for each one to
fail independently — that's guide 19's layer-4 pattern audit ("search for
the same bad assumption in sibling files, services, environments"), applied
to data models instead of code.

## 2. Producer and consumer must agree on how permissive the schema is

Admin's `ExamPaper.year` is nullable and legitimately `None` for specimen
papers (they aren't tied to a real exam sitting). Student Backend's mirrored
`practice.Paper.year` is `NOT NULL`. Every specimen paper failed replication
— the consumer had no handling beyond letting the insert fail and silently
dropping the event. No error surfaced, no alert fired; the paper just never
appeared on the student side.

**Rule:** when two services model "the same" entity, the consumer's schema
must be at least as permissive as the producer's for every field the
producer can legitimately send — or the consumer needs an explicit, logged,
alertable path for values it can't represent. A replication event that gets
silently dropped on constraint violation is data loss with no error, which
is worse than a loud failure.

## 3. Replication gaps are invisible until something references the hole

Production's Student Backend was missing 22 subjects that Admin had — a gap
with no error trail, discovered only because a later migration referenced
one of the missing rows (`Subject.DoesNotExist`, found mid-migration).
Separately, production had accumulated 26 duplicate subjects that a
cleanup script had never been run against (see §5) — again invisible until
a migration tried to enforce a constraint the duplicates violated.

**Rule:** don't rely on "something downstream will eventually break loudly"
as the detection mechanism for replication drift. Run a periodic (nightly,
or at minimum pre-promotion) reconciliation job that diffs id sets/row
counts for every entity that's supposed to exist identically in more than
one service, and alerts on drift before a migration or a user does the
diffing for you.

## 4. Async consumers need to be idempotent against their own retries

`generate_ai_paper_via_harness` had no idempotency guard: a queued Celery
retry fired *after* a different invocation of the same logical task had
already succeeded, collided with its own prior success on save, and reset an
already-reviewed paper back to `Draft`. This is the same "at-least-once
delivery requires an idempotent consumer" principle guide 7 already states
for payment webhooks — it applies just as directly to any async task that
mutates a record another service (or another invocation of itself) might
already have finished mutating.

**Rule:** any consumer that can be retried — Celery task, webhook handler,
event subscriber — must check "has this logical operation already
succeeded?" before mutating state, not just "did this specific invocation
complete?" A retry is not evidence that the underlying work is still needed.

## 5. Resolve cross-service references by id, never by name

A real Form 4 Economics batch generated correctly, but "No papers found"
when filtered by Economics + Form 4 in the admin list — the papers had been
filed under a different subject entirely. Root cause: subject resolution
happened by name, which is ambiguous whenever a name repeats across grades;
the frontend already had the disambiguating id and simply wasn't sending
it.

**Rule:** when one service references an entity owned by another, always
carry and use the producer's primary key. Treat "resolve by human-readable
name across a service boundary" as a bug waiting to happen, not a
convenience — names collide, ids don't.

## 6. A data-cleanup script proven on staging proves nothing about production

`merge_duplicate_subjects.py` was written as a prerequisite cleanup step for
migration `0011_subject_family_required` and was run — successfully — against
staging's data. It was never run against production, which had its own,
independently-accumulated set of 26 duplicate subjects. Promoting the
migration crash-looped production's `migrate --noinput` on exactly the
precondition the cleanup script existed to satisfy.

**Rule:** when a data-cleanup script is a precondition for a schema
migration, its success on one environment is not evidence for any other
environment — each one can have accumulated different dirty data
independently. Re-run (or re-verify the precondition against) every
environment the migration will actually touch, in order, before promoting
it there. This is a data-layer instance of guide 19's staging-gate
principle: an artifact's staging pass proves the artifact, not the target
environment's data.

## Checklist (copy into project's docs when applying)

- [ ] Every cross-service reference is an id, never a name, resolved against the owning service's primary key
- [ ] Every entity with a delete/unpublish/archive path in one service has an explicit retraction handler for each of its downstream copies — audited as a full set when the first one is built, not added one incident at a time
- [ ] Consumer schemas are verified at least as permissive as producer schemas for every replicated field, or have an explicit, alertable handling path for values they can't represent
- [ ] A periodic reconciliation job diffs id sets/row counts for every entity mirrored across services and alerts on drift
- [ ] Every retryable async consumer (Celery task, webhook, event handler) checks whether its logical operation already succeeded before mutating shared state
- [ ] A data-cleanup script that's a migration precondition is re-run (or re-verified) independently against every environment before that migration is promoted there
