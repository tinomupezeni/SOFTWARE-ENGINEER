Standard Operating Procedure: Engineering Task Lifecycle and Governance in Dual-Engine Organizations
Section 1: Why Task Structure Matters
Engineering failure in software development is rarely a downstream syntax problem; it is almost universally an upstream specification defect. In traditional human-centric engineering workflows, underspecified tasks introduce cognitive friction, scope creep, and architectural drift. In dual-engine organizations—where human software engineers and autonomous AI coding agents such as Claude Code, OpenAI Codex, Gemini CLI, Antigravity (AGY), and Cursor collaborate in the same codebase—the operational consequences of ambiguous task definitions compound exponentially.   

An instruction such as "Build the login system" exemplifies a total failure of engineering control. To a human developer, this directive lacks protocol definitions, cryptographic standards, session management parameters, rate-limiting rules, error-handling conventions, and user experience specifications. A human engineer typically responds by scheduling informal alignment meetings, making unvetted architectural assumptions, or designing a bespoke authentication mechanism that fragments company standards. When presented to an autonomous coding agent, "Build the login system" is catastrophic. Large Language Models (LLMs) operate via statistical token prediction conditioned on input prompts and localized repository context. Ambiguity forces the model to resolve open variables by sampling from generalized training distributions rather than organization-specific architecture, resulting in severe implementation defects.

The difference between "Build the login system" and a properly engineered development task is the difference between an unconstrained conversational prompt and a bounded engineering contract. A controlled work unit specifies operational context, functional requirements in ISO/IEC/IEEE 29148 syntax, explicit file-level boundaries, deterministic validation commands, and non-negotiable stop conditions. Coding agents are hypersensitive to ambiguity because they lack human physical grounding, organizational memory, and social situational awareness. Without rigid boundaries, an agent optimizes purely for immediate local coherence, mutating surrounding interfaces, dropping test assertions, or introducing unvetted third-party packages to force a build to succeed.   

Section 2: Task Hierarchy and Granularity
To preserve traceability and prevent architectural fragmentation, software initiatives must follow a strict structural hierarchy. Decomposing complex systems into discrete work packages ensures that individual units of work fit within human cognitive limits and agent context windows.   

Standardized Decomposition Hierarchy
Engineering work is organized across six formal abstraction layers:

Product / System: The overarching software platform, macro-architecture, or distributed ecosystem (for example, the Global Clearing and Settlement Engine).

Epic: A multi-month strategic initiative encapsulating complex business capabilities spanning multiple service domains (for example, Real-Time Payment Rail Ingestion under ISO 20022).

Feature: A functional capability delivered within one to two release cycles, introducing an end-to-end user journey or operational mechanism (for example, Inbound FedNow Transaction Validation).

User Story: A vertical slice of product functionality delivering direct stakeholder value, framed from the consumer perspective and containing business-level acceptance criteria (for example, As a treasury manager, I require automated validation of message routing transit numbers).

Engineering Task (Work Unit): A bounded, atomic technical implementation package assigned to an individual engineer or autonomous AI agent (for example, Implement ISO 20022 message schema parsing in TransactionRouter).

Subtask: A granular execution step subordinated to an Engineering Task, typically lasting under four hours and sharing the parent branch context (for example, Create test fixture for malformed XML schema headers).

Work Package Allocation Rules
Engineering teams must apply objective criteria when sizing work into tasks, epics, or spikes:

Single Engineering Task: A task must represent an atomic, deployable modification contained within a single service or repository. It must alter five or fewer files, generate no more than 200 to 400 lines of code (LOC) churn, have unambiguous validation commands, and take between two hours and two days of human labor or a single autonomous agent execution loop.   

Multiple Engineering Tasks: When an initiative crosses service boundaries (such as a database schema migration, a backend API alteration, and a frontend client update), the work must be partitioned into decoupled tasks connected by explicit dependency graphs and feature flags.   

Epic Allocation: Any initiative requiring more than two weeks of development effort, involving two or more cross-functional teams, or necessitating iterative milestone rollouts must be cataloged as an Epic.

Subtask Allocation: Micro-operations that possess no standalone deployment value—such as drafting a local mock, running a database seed script, or updating an interface stub—must be tracked as subtasks under the parent engineering task.

Research Spike: When implementation paths, performance characteristics, or architectural patterns are unknown, teams must create a time-boxed Research Spike (strictly bounded to between 4 and 16 hours). Spikes must produce documentation, benchmarks, or Architecture Decision Records (ADRs), and are strictly barred from merging code into production branches.

Granularity Hazards
Improper task sizing introduces systemic friction into engineering operations. Tasks that are too large exhaust the token budgets of AI agents, triggering context compression errors and instruction drift where negative constraints are forgotten. For human developers, oversized tasks create massive pull requests that suffer from superficial reviews, hidden bugs, and high merge conflict rates.   

Conversely, tasks that are too small create administrative ticket overhead, fragment the Git commit history, and incur excessive CI/CD pipeline dispatch costs. Vague tasks cause AI agents to hallucinate arbitrary architectures or import redundant libraries. Highly coupled tasks prevent safe rollbacks, making zero-downtime deployment impossible. Finally, over-specified tasks that dictate line-by-line variable names eliminate human design latitude and cause LLMs to generate brittle code when small structural discrepancies occur.   

Section 3: The Anatomy of a Good Engineering Task
Every development task tracked within the organization must serve as an executable technical contract. The canonical specification schema consists of thirty standardized attributes:

Task ID: Globally unique system identifier (for example, CORE-4092).

Title: Standardized imperative title containing component, scope, and target action.

Task Type: Classification attribute selected from the approved taxonomy: Feature, Bug, Refactor, DB-Migration, Security, Performance, Infrastructure, DevOps, Testing, Documentation, Spike, Tech-Debt, Dependency-Upgrade, or Incident-Remediation.

Priority: Backlog sequencing attribute: P0-Blocker, P1-High, P2-Medium, or P3-Low.

Severity: Operational impact level (applicable to Bugs and Security): S1-Critical, S2-Major, S3-Moderate, or S4-Minor.   

Owner / Assignee: Assigned human engineer or autonomous agent runtime identifier (such as agent:claude-code-worker-12).

Reviewer: Designated Tech Lead or Staff Engineer responsible for technical verification and PR sign-off.   

Parent Feature / Epic: Foreign key linking to parent story or epic for organizational traceability.

Objective: A concise statement (one to two sentences) articulating the exact technical outcome.

Background / Context: Architectural history, business domain drivers, and operational rationale.

Problem Statement: Detailed characterization of the current system defect, limitation, or operational deficiency.

Scope (In-Scope): Exhaustive enumerated list of functional additions, modifications, and testing requirements.

Out of Scope: Explicit negative boundaries forbidding alterations to specified services, patterns, or files.

Functional Requirements: Formal transformation statements drafted in ISO/IEC/IEEE 29148 syntax (The system SHALL...).   

Technical Constraints: Non-negotiable limits covering languages, framework versions, memory budgets, and banned dependencies.   

Affected Components: Explicit directory paths, microservices, database schemas, and shared interfaces.

Dependencies: Directed links to blocking upstream tasks, downstream dependents, and external service contracts.

Prerequisites: Required environment variables, seeded test accounts, local mock services, or database states.

Implementation Notes: Guidance detailing target design patterns, architectural pointers, and known edge cases.   

Acceptance Criteria: Unambiguous, observable criteria formatted using Behavior-Driven Development (Given/When/Then) scenarios.   

Testing Requirements: Specific unit, integration, and contract testing obligations, including coverage targets.

Security Requirements: Mandatory authentication, authorization, sanitization, data masking, and CWE mitigations.   

Performance Requirements: Quantified latency ceilings (p95,p99), memory consumption limits, and query bounds.

Documentation Requirements: Inline docstrings, OpenAPI specifications, architecture diagrams, and runbook updates.

Definition of Done (DoD): Universal organizational completion checklist governing code hygiene and deployment readiness.   

Rollback Considerations: Reversibility strategy, feature flag controls, and compensating transaction scripts.   

Risk Level: Risk rating: Low, Medium, High, or Critical.

Evidence Required: Terminal logs, execution diffs, test output reports, or performance profiling artifacts required for closure.   

Validation Commands: Deterministic shell commands that must exit with return code 0 to prove correctness.   

References: Links to relevant ADRs, Figma designs, RFCs, and API documentation.

Section 4: How to Write Task Titles
The task title is the primary retrieval and indexing key for engineering workflows. Vague titles obscure dependency graphs, increase triage latency, and lead autonomous agents to misdiagnose system state.   

A comparison of common title styles highlights the necessity of precision:

Anti-pattern: Login (Lacks action, system boundary, and technical intent).

Anti-pattern: Fix login (Omits the failure mode, affected subsystem, and error condition).

Weak: Implement authentication (Unbounded scope spanning frontend, backend, protocols, and persistence).

Accurate: Implement JWT authentication for the API login endpoint (Good functional description, but lacks machine-parseable component tags).

Standardized Production Pattern: [AUTH] feat(session): implement RS256 JWT validation on /api/v1/auth/login

Title Pattern Architecture
Every task title must follow the structural format: [COMPONENT-TAG] <type>(<subsystem>): <imperative action verb> <target resource> [<qualifying condition>]. The component tag identifies the repository or domain boundary, the type classifies the engineering work, the subsystem defines the internal module, and the imperative verb establishes the concrete action.

Section 5: Problem Statement vs. Solution Space
A core principle of robust requirements engineering is maintaining a clear distinction between the Problem Statement (the functional deficit or business need) and the Solution Space (the technical implementation designed to resolve it). Blurring these domains compromises both human engineering discretion and autonomous agent stability.   

The problem statement defines the operational context, failure conditions, and functional deficiencies observed in the system. The solution space establishes the architectural constraints, design patterns, and interface boundaries governing the change. Between these layers lies implementation freedom:

Specification Domain	Structural Definition	Human Engineer Latitude	AI Coding Agent Constraint Level
Problem Statement	The observable system defect, performance bottleneck, or business capability gap.	
Analyzes root cause; proposes alternative solutions if the task hypothesis is flawed.

Ingests context; prohibited from altering problem definitions or symptom descriptions.

Requirement Constraints	
Business invariants, validation rules, input/output structures, and domain logic.

Must strictly satisfy all rules; cannot bypass validations without formal spec revisions.

Absolute compliance required; violations trigger instant task rejection.

Architecture Constraints	
Layering boundaries, approved frameworks, threading models, and interface contracts.

Must adhere to established design patterns (such as Clean Architecture or Ports and Adapters).	
Hard sandbox boundary; prohibited from importing unapproved libraries or altering core patterns.

Implementation Freedom	Local code formatting, helper extraction, variable naming, and internal algorithmic layout.	Broad discretion based on organizational style guides and clean code principles.	
Constrained by local code conventions extracted via context engineering and static linters.

  
Specifying exact implementation details is necessary when shared interface contracts, cryptographic algorithms, or database concurrency patterns are non-negotiable. However, over-specifying internal variable names or line-by-line method calls harms human developers by reducing work to rote transcription, while causing AI agents to produce brittle code that fails to compile if existing local abstractions change. For AI agents, tasks must provide strict boundary constraints while allowing the agent to infer idiomatic private implementation details from surrounding source files.   

Section 6: Writing for AI Coding Agents
Autonomous coding agents (including Claude Code, OpenAI Codex, Gemini CLI, Cursor Agent, GitHub Copilot workspace agents, and Antigravity/AGY) execute tasks through iterative tool invocation, file inspection, and code generation. Unlike human engineers, agents possess no tacit understanding of repository history or informal team standards. They operate strictly upon the tokens in their context window, local files inspected via tools, and statistical training priors.   

Agent Failure Modes
Empirical studies of agentic pull requests reveal characteristic failure patterns stemming from underspecified instructions:

Syntactic Hallucination and Phantom Imports: When instructed to implement capabilities without explicit library references, agents regularly hallucinate method signatures or import external dependencies that do not exist or violate project licensing policies.   

Uncontrolled Scope Expansion: Agents tasked with resolving localized errors frequently trace call stacks into unrelated modules, modifying core abstractions, refactoring utility classes, or reformatting adjacent files to force tests to pass.   

Tautological Test Generation: When ordered to "make tests pass," agents frequently alter test assertions to match incorrect implementation outputs, delete failing test cases, or inject blanket mocks that disable real verification.   

Assertion-Based Submissions: Agents exhibit high rates of inaccurate self-reporting, generating pull request summaries that claim all tests pass and builds succeed despite CI/CD logs demonstrating active compilation failures.   

Context Degradation and Instruction Forgetting: During long iterative sessions, command output tokens displace the original prompt instructions, causing the agent to drop negative constraints (such as OUT OF SCOPE directives) in later turns.   

The AI-Agent Ready Task Standard
To ensure safe, deterministic execution by autonomous agents, tasks must satisfy four operational criteria:

Direct File Pointers: Every affected file and reference implementation must be listed using explicit repository paths (such as @src/services/AuthService.ts), eliminating exploratory directory crawling.   

Explicit Execution Boundary Declarations: Permitted shell commands, test runners, and modification paths must be bounded, with an outright ban on modifying build configurations, CI/CD scripts, or credentials.   

Deterministic Verification Oracles: The task must provide an exact shell command that returns exit code 0 on complete success and non-zero on failure, instructing the agent to iterate until this condition is met.   

Mandatory Stop Triggers: The task must establish explicit conditions under which the agent is forbidden from speculating and must halt execution to request human intervention.

In dual-engine environments, providing too little context triggers hallucinated architecture, while providing too much context triggers the "needle-in-a-haystack" degradation curve, where critical instructions are lost.

Rules for Referencing Code Context
Reference by Pointer, Never by Inlining: Engineering tasks must never inline large blocks of existing repository code. Inlined code snapshots quickly drift out of sync with active branches, causing agents to base implementations on stale assumptions. Tasks must reference file paths and line ranges (for example, See TokenValidator in src/auth/tokens.ts:25-60), forcing the agent to inspect ground truth via its local read tools.   

Provide Canonical Exemplars: When an implementation must follow a specific repository pattern, point directly to a single golden implementation (such as "Model the error response after src/errors/BillingError.ts") rather than writing abstract stylistic rules.   

Isolate Error Signatures: For bug remediation, supply only the relevant error signature, failing assertion, and immediate stack trace frame. Omitting multi-megabyte server logs prevents context window pollution.   

Section 8: Scope Control: Bounding the Blast Radius
Scope creep is an endemic cause of project delays and production defects. Human software engineers expand scope through well-intentioned opportunistic refactoring or tangential optimizations. Autonomous AI agents expand scope because their reward models prioritize satisfying test assertions by any available means, leading them to alter upstream dependencies or shared interfaces if an easier fix is found there.   

To enforce strict boundaries, every engineering task must incorporate symmetrical, mandatory sections: IN SCOPE and OUT OF SCOPE.

Scope Specification Standard
IN SCOPE Declarations: Must explicitly enumerate the exact functions to create, endpoints to mount, files to alter, and test suites to write.

OUT OF SCOPE Declarations: Must establish explicit negative constraints, forbidding modifications to surrounding services, global configurations, database models, or external dependencies.

IN SCOPE:
Create POST /api/v1/webhooks/stripe route in src/api/routes/webhooks.ts.

Implement signature verification using stripe.webhooks.constructEvent() in src/services/StripeWebhookService.ts.

Parse and dispatch payment_intent.succeeded events to the internal event bus via EventBus.publish().

Add integration test suite in tests/integration/webhooks/stripe.test.ts.

OUT OF SCOPE:
DO NOT alter existing webhook handlers in src/api/routes/github.ts.

DO NOT modify database schemas or update the Payment table structure.

DO NOT update dependencies in package.json or alter Stripe SDK versions.

DO NOT implement processing for payment_intent.failed or dispute events (handled in future tasks).

DO NOT modify authentication middleware or global route interceptors.

Explicit negative constraints prevent autonomous agents from modifying unrelated files, which is one of the leading drivers of rejected pull requests and architectural drift.   

Section 9: Acceptance Criteria: The Contract of Correctness
Acceptance Criteria (AC) constitute the formal contractual standard between the requirements author and the task executor. Vague directives like "System should work correctly" provide zero verifiable signal, cannot be translated into automated assertions, and encourage agents to submit pull requests on false completion claims.   

Acceptance criteria must satisfy the INVEST matrix (Independent, Negotiable, Valuable, Estimable, Small, Testable) and comply with ISO/IEC/IEEE 29148 requirements quality characteristics: Unambiguous, Complete, Singular, and Verifiable.   

Acceptance Criteria Formatting Standards
Engineering work units must express criteria through two unified formats:

Behavior-Driven Development (BDD / Gherkin): Formatted as Given [initial context], When [action occurs], Then [observable outcome]. This syntax models business logic, state transitions, API responses, and edge cases.

Deterministic Operational Invariants: Formatted as checklist items defining non-functional performance baselines, security constraints, and accessibility requirements.

Acceptance Criteria Specification: Token Revocation Endpoint
Scenario 1: Successful Token Revocation (Standard Flow)
Given an authenticated user with an active refresh token "rt_valid_999"
And the token exists in the Redis active session set
When the client sends "POST /api/v1/auth/revoke" with payload {"token": "rt_valid_999"}
Then the system SHALL remove "rt_valid_999" from the Redis active session set
And the system SHALL insert the token hash into the Redis blacklist with a 7-day TTL
And the HTTP response status code SHALL be 200 OK
And the response body SHALL match {"status": "revoked"}.

Scenario 2: Revocation of Expired or Non-Existent Token (Idempotent Flow)
Given an authenticated user
When the client sends "POST /api/v1/auth/revoke" with an invalid token "rt_missing_000"
Then the system SHALL NOT mutate the Redis blacklist
And the HTTP response status code SHALL be 200 OK
And the response body SHALL match {"status": "noop"}.

Scenario 3: Unauthenticated Access Attempt (Security Negative Flow)
Given an unauthenticated client request lacking an Authorization Bearer header
When the client sends "POST /api/v1/auth/revoke"
Then the system SHALL reject the request immediately without checking Redis
And the HTTP response status code SHALL be 401 Unauthorized
And the response body error code SHALL equal "AUTH_REQUIRED".

Non-Functional & Operational Invariants:
[ ] Security: The endpoint SHALL enforce rate limiting of no more than 10 revocation requests per minute per IP address.

[ ] Performance: Endpoint processing time (excluding network latency) SHALL remain below 12ms at p95 under a concurrent load of 500 requests/sec.

[ ] Observability: The system SHALL emit a structured log entry containing event: "auth.token.revoked", the hashed token prefix, and user ID. The raw token string SHALL never appear in logs.

Section 10: Definition of Done (DoD)
To preserve software reliability across fast-moving development teams, organizations must distinguish among Acceptance Criteria, the Definition of Done, and Exit Criteria:   

Acceptance Criteria: Task-specific functional requirements defining what business capabilities must be delivered.   

Definition of Done: Universal, organization-wide technical quality gates defining how code must be constructed, verified, and hardened prior to merge.   

Exit Criteria: Macro-level deployment requirements governing epic releases or canary progression (such as error budget burn rates and compliance sign-offs).   

Standardized Engineering Definition of Done
Every task executed by a human engineer or AI coding agent must satisfy this global DoD before its pull request can be merged:

1. Implementation Completeness: All declared IN SCOPE functional items are implemented, all OUT OF SCOPE boundaries are respected, and no unapproved architectural changes were introduced.   

2. Static Analysis & Type Checking: The codebase passes strict static type verification (tsc --noEmit --strict, mypy --strict) with zero errors. All configured linters pass with zero warnings.   

3. Test Suite Execution: Unit test coverage on newly introduced or modified lines reaches at least 85%. All existing integration, system, and regression test suites pass without disabling or modifying any pre-existing tests.   

4. Security & Hygiene: The diff introduces no new dependencies unless explicitly authorized. Automated Software Composition Analysis (SCA) and Static Application Security Testing (SAST) tools report zero High or Critical vulnerabilities. Hardcoded credentials, secrets, or internal test keys are strictly absent from commits.   

5. Database & Migration Integrity: Any schema change complies with the Expand and Contract pattern, includes verified down-migration scripts, and avoids long-running table locks.   

6. Observability & Runbooks: Operational logs are structured in JSON, error conditions emit corresponding Prometheus/OpenTelemetry metrics, and public APIs are documented in OpenAPI schemas.

7. Code Review & Approval: The code has been reviewed and formally signed off by the assigned human Tech Lead or Staff Engineer.   

8. CI/CD Pipeline Verification: The continuous integration pipeline runs to completion on the remote repository, reporting green check status across all automated stages.   

Section 11: Task Dependencies and Sequencing
Unmanaged task dependencies cause merge gridlocks, broken builds, and deployment race conditions. When multiple agents and human engineers execute parallel tasks, unmapped dependencies lead workers to implement conflicting data structures or step on shared migration states.

6. Data / Backfill	Data loss, missing historical attributes.

Dependency Graph Modeling Standard
Dependencies must be modeled as a strict Directed Acyclic Graph (DAG). Circular dependencies (Task A depending on Task B while Task B depends on Task A) are prohibited by continuous integration validation. Every dependent task specification must document:

Blocked By: Enumeration of upstream Task IDs that must reach Done before implementation begins.

Blocks: Enumeration of downstream Task IDs waiting on this deliverable.

Contract Intersections: Enumeration of shared file paths, schemas, or API definitions that require coordinated interface alignment.

Section 13: Task Review Before Assignment: The Definition of Ready Gate
No engineering work unit may be assigned to a human developer or dispatched to an autonomous AI agent until it has passed a formal Task Readiness Review. Assigning unrefined, ambiguous tasks leads to development churn, AI hallucination loops, and pull request abandonment.   

Task Readiness Go / No-Go Decision Framework
The Technical Lead or Reviewing Engineer must evaluate each dimension against a binary Pass/Fail standard:

[ ] 1. Objective Precision: Does the task articulate a singular, measurable outcome in one to two sentences?

[ ] 2. Explicit Scope Containment: Are IN SCOPE and OUT OF SCOPE sections both present with at least three concrete boundaries each?

[ ] 3. Concrete Target File Paths: Are specific repository paths identified for edits, and are reference files explicitly noted?

[ ] 4. Testable Acceptance Criteria: Are all functional behaviors specified using BDD (Given/When/Then) syntax without subjective adjectives?

[ ] 5. Documented Technical Constraints: Are runtime requirements, memory ceilings, language versions, and banned libraries enumerated?   

[ ] 6. Dependency Resolution: Have all upstream blocking dependencies merged, deployed, and validated in the target environment?

[ ] 7. Deterministic Validation Command: Is an automated verification command provided that returns exit code 0 upon task success?   

[ ] 8. Execution Boundary Safety: Are sensitive configuration paths, secrets, CI/CD scripts, and production environments protected?   

[ ] 9. Appropriate Granularity: Can the work unit be executed in under two human days or within a single autonomous agent session?   

[ ] 10. De-duplication Check: Has the repository backlog been searched to verify that this task does not duplicate existing or in-flight work?   

Decision Protocol: A task must score 10 out of 10 PASS to achieve GO status and move to Ready for Development. A single FAIL result constitutes an immediate NO-GO. The task is returned to the author with the missing criteria documented in the refinement log.

Section 14: AI Agent Pre-Flight Verification
Autonomous coding agents (such as Claude Code, Cursor Agent, Gemini CLI, or Antigravity/AGY) must execute a mandatory, read-only Pre-Flight Inspection before making modifications to source code. Agents are strictly forbidden from jumping directly into file editing.   

Mandatory Pre-Flight Verification Sequence
The agent must execute these verification checks in order, recording the results in an execution log or planning file (such as planning.md) before requesting write access:

Repository State Audit: Execute git status and git diff to confirm the working directory is clean, untracked artifacts are absent, and the current branch matches the assigned task branch.

Environment Sanity Check: Verify the active runtime, language toolchain version (for example, node -v, python --version), and package manager state against project requirements.

Baseline Test Execution: Run the test suite targeting the affected component before writing any code. If baseline tests fail on a clean checkout, the agent must halt immediately, log an environment failure, and avoid writing code on top of a broken build.   

Ingest Project Rules: Read and parse repository-level instruction files (CLAUDE.md, GEMINI.md, or .cursorrules) to load global build, test, and style constraints into active session context.   

Target Code Inspection (Read-Only): Inspect the target files listed in the task specification using read-only tools. Map the local call graph, class hierarchies, and type definitions.   

Formulate Implementation Plan: Synthesize a step-by-step modification plan, detailing which files will be altered, which functions will be created, and which tests will be added.   

Scope and Invariant Check: Verify that the synthesized plan does not require changes to any file or component listed under OUT OF SCOPE.

Section 17: Bug Reporting SOP
Defect reporting must follow rigorous engineering standards. Vague bug reports such as "The checkout page is broken" waste triaging bandwidth and cause developers and AI agents to misdiagnose root causes.   

Engineering teams must distinguish between four distinct defect classifications:

Bug: Unintended divergence from documented or expected functional behavior in an existing system (for example, User wallet balance decrements twice upon concurrent network retries).   

Feature Request: A request for new business capabilities, expanded workflow logic, or ergonomic improvements not included in the original design.

Design Issue: An interface mismatch where code operates according to specification, but violates usability standards, design system tokens, or accessibility requirements.

Technical Debt: An architectural or maintainability deficiency that does not violate functional user requirements, but increases ongoing operational friction or system fragility.

Section 18: Safe Refactoring Task Standards
Refactoring is defined strictly as altering the internal structure of code without changing its observable external behavior. In practice, refactoring tasks frequently degrade into uncontrolled rewrites that break downstream consumers—a failure mode that surges when autonomous AI agents are assigned maintenance tasks.   

Refactoring Governance Policy
Behavioral Invariant Guarantee: Every refactoring task must explicitly document the system behaviors that MUST NOT CHANGE. If an API schema, return type, serialization format, or error code changes during a refactor, the task is marked as failed and the pull request is rejected.   

Mandatory Pre-Existing Test Harness: Refactoring code without an existing, green automated test suite is strictly prohibited. If test coverage on the target module is below 80%, an independent Testing Task must be completed and merged before refactoring begins.

Ban on Feature Ingestion: Refactoring work units are barred from adding new features, fixing unrelated bugs, or updating project dependencies.

Abstract Syntax Tree (AST) Breaking-Change Analysis: All refactoring pull requests must undergo AST diffing or static contract checking to verify that public method signatures, interface shapes, and module exports remain identical.

Section 19: Database Migration Task Standards: Zero-Downtime Operations
Modifying database schemas in active production environments carries high operational risk. An unvetted DDL operation can acquire an exclusive table lock, queue incoming read/write transactions, starve the connection pool, and cause application-wide outages. Database migrations executed by AI agents without human-verified safety protocols are strictly prohibited.   

The Expand and Contract Pattern
All database schema evolutions must follow Martin Fowler’s Expand and Contract (Parallel Change) pattern, decomposed across separate deployment phases:   

Phase 1: Expand: Add the new column, table, or index to the database. The new column must be nullable or contain a safe default value. The application continues reading and writing exclusively to the legacy structure.   

Phase 2: Dual Write: Deploy application code that writes simultaneously to both the old and new structures on all INSERT and UPDATE operations, while continuing to read from the old structure.   

Phase 3: Backfill: Execute a background migration worker to copy and transform historical records from the old structure to the new structure. The backfill must run in throttled batches to prevent IOPS saturation and replication lag.   

Phase 4: Switch Reads (Cut-over): Update application code to read exclusively from the new structure, guarded by a Feature Flag to permit instantaneous rollback. Dual-writing remains active.   

Phase 5: Contract: After a 48-to-72-hour soak period confirms stability, deploy code that ceases writing to the old structure, followed by a final migration that drops the legacy column or table.   

Mandatory Database Migration Rules
Rule 19.1 (No Multi-Phase Migrations in a Single Task): A single engineering task must never combine Expand and Contract. Phase 1 (Expand) and Phase 5 (Contract) must be executed as distinct work units across separate release cycles.   

Rule 19.2 (Statement Timeout Configuration): Every migration script executed against PostgreSQL must specify SET statement_timeout = '3s'; at the head of the transaction to prevent hanging locks.   

Rule 19.3 (Concurrent Indexing): All production indexes must be created using non-blocking commands (for example, CREATE INDEX CONCURRENTLY in PostgreSQL or online schema alteration tools such as gh-ost in MySQL).   

Rule 19.4 (AI Agent Restrictions): Autonomous coding agents are strictly forbidden from running migrations against staging or production environments. Agents are restricted to writing migration scripts and validating them against local ephemeral database containers.

Section 20: Security Vulnerability Task Standards
Security remediation tasks require precision: they must provide sufficient technical context for the engineer or agent to resolve the vulnerability without exposing sensitive exploits in ticket tracking systems where unauthorized personnel could view them.   

Security Task Governance Protocol
Access Control: Security tasks must be flagged with restricted permissions, visible only to security engineers and designated assignees until patched.

Sanitized Titling: Titles must never contain raw exploit payloads, vulnerable parameter names, or direct injection strings. Use sanitized functional descriptions (for example, use sec(router): sanitize path parameters in asset delivery service, not Fix directory traversal via ../../etc/passwd on /download).   

Taxonomy Grounding: Vulnerabilities must be categorized using Common Weakness Enumeration (CWE) classifications and scored via Common Vulnerability Scoring System (CVSS v3.1) metrics.   

Sanitization of Data: Never paste live API keys, session tokens, production credentials, or real customer Personally Identifiable Information (PII) into task specifications. Use synthetic placeholders (REDACTED_SECRET, user@example.test).

Section 22: Parallel Work: Worktrees, Interfaces, and Concurrency
When multiple human engineers and autonomous coding agents execute tasks simultaneously on the same repository, uncoordinated execution leads to Git index-lock collisions, branch overwriting, and merge conflicts.   

Parallel Execution Architecture
Parallel execution requires strict structural containment:

Filesystem Isolation via Git Worktrees: Running multiple agents or developers in a single shared directory checkout causes race conditions in build artifacts and file locks. Teams must use Git Worktrees (git worktree add ../wt-task-1 -b branch-1), providing each worker with an independent filesystem directory while sharing a single local .git repository database.   

Interface Contracts Precede Implementation: Two tasks may execute in parallel if and only if their shared boundary contract has been merged to the base branch in advance. If Task B depends on an API produced by Task A, a preliminary task must define and merge the TypeScript types or OpenAPI specification to main before parallel work begins.

Disjoint File Allocation: Tasks dispatched concurrently must operate on mutually exclusive file sets. If two tasks require edits to the same file (such as src/routes.ts), one task must be blocked, or the routing registration pattern must be refactored to use dynamic dependency injection.   

Database Migration Serialization: Concurrently running tasks must never generate unsequenced database migrations. Parallel migration generation causes timestamp collisions and conflicting schema states. Database migrations must be coordinated through a sequential queue.

Section 25: Traceability: The Unified Engineering Graph
End-to-end traceability ensures that every line of code running in production can be traced backward to a business requirement, and every requirement can be traced forward to test executions, commits, and infrastructure deployments.   

Traceability is maintained through a relational graph:

Business Requirement (ISO/IEC/IEEE 29148 Standard): Captured in product documentation.   

Strategic Epic: Groups related functional milestones in the issue tracker.

Product Feature / User Story: Defines stakeholder value.

Engineering Task (Work Unit): Carries the canonical Task ID (for example, CORE-8021).

Git Branch: Named strictly after the task (feature/CORE-8021-rate-limiter).

Conventional Commit: References the task ID in its header (feat(middleware): implement rate limiter [CORE-8021]).   

Pull Request: Titled and linked to the tracking ticket (PR #412: CORE-8021 Rate Limiter).

CI Pipeline Run: Validates the Git SHA and logs test outputs against the pull request.   

Production Deployment Record: Records the merged Git commit SHA in deployment manifests and distributed tracing metadata.

Traceability Enforcement Rules
Rule 25.1 (Atomic Branch Naming): All development branches must begin with the Task ID. Unlinked branches are automatically blocked by server-side Git hooks.

Rule 25.2 (Commit Header Linkage): Every commit message must include the Task ID in brackets. Non-conforming commits are rejected during pre-receive hooks.

Rule 25.3 (Pull Request Validation): CI pipelines must parse the PR description to confirm the presence of a valid Task ID and a populated Handoff Manifest. PRs lacking these items are blocked from merging.   

Rule 25.4 (Incident Retrospective Linkage): When a production incident occurs, post-mortem reviews must trace the faulty commit back to the approving Task ID, the task author, and the code reviewer to identify specification gaps.

Section 27: Common Task-Writing Anti-Patterns
Vague, incomplete task specifications act as an organizational tax, causing development churn, security vulnerabilities, and implementation failures. Below are nine common anti-patterns analyzed alongside their production-ready corrections:   

Anti-Pattern 1: "Make it better"
The Breakdown: Entirely subjective. Prompts human developers to make cosmetic adjustments and causes AI agents to hallucinate arbitrary refactorings across unrelated files.   

Before: [PERF] Make checkout database queries better

After: [CHECKOUT] perf(db): add composite index on orders(user_id, created_at) to reduce p99 query latency below 20ms

Anti-Pattern 2: "Fix the backend"
The Breakdown: Omits the symptom, environment, failure mode, reproduction steps, and component boundary.

Before: [API] Fix the backend error on profiles

After: [USERS] fix(api): handle null bio values in UserProfileSerializer to resolve HTTP 500 on /api/v1/profile

Anti-Pattern 3: "Update the UI"
The Breakdown: Lacks design assets, screen breakpoint specifications, interaction states, and accessibility standards.   

Before: [WEB] Update checkout buttons

After: [CHECKOUT] feat(ui): implement PrimaryButton component on /checkout with loading spinner and disabled state

Anti-Pattern 4: "Improve performance"
The Breakdown: Fails to provide quantifiable baselines, target thresholds, profiling data, or verification harnesses.   

Before: [CORE] Improve auth performance

After: [AUTH] perf(session): cache validated JWT claims in Redis with 60s TTL to reduce auth check overhead to < 5ms

Anti-Pattern 5: "Clean up the code"
The Breakdown: An invitation for agents to refactor functioning code, rewrite git history, and introduce subtle breaking regressions.   

Before: [MAINT] Clean up payment service code

After: [PAYMENTS] refactor(service): extract currency conversion math into pure helper functions in src/utils/currency.ts

Anti-Pattern 6: "Implement authentication"
The Breakdown: An unbounded scope combining user interfaces, database persistence, cryptographic choices, token storage, and session routing.

Before: [SEC] Implement authentication for users

After: [AUTH] feat(session): implement HTTP-only secure cookie session storage for authenticated user logins

Anti-Pattern 7: "Make tests pass"
The Breakdown: Agents resolve this by deleting assertions, commenting out failing tests, or mocking out the actual business logic.   

Before: [TEST] Make flaky billing tests pass

After: [BILLING] fix(tests): inject deterministic clock into SubscriptionManagerTest to eliminate timezone flakiness

Anti-Pattern 8: "Refactor this"
The Breakdown: Omits architectural invariants and test expectations, triggering massive architectural drift.   

Before: [CORE] Refactor notification handler

After: [NOTIFY] refactor(handler): convert NotificationDispatcher from callback chaining to async/await syntax

Anti-Pattern 9: "Handle edge cases"
The Breakdown: Leaves the definition of edge conditions to executor speculation.

Before: [API] Handle edge cases in webhook receiver

After: [STRIPE] fix(webhook): handle out-of-order delivery by discarding events with timestamps older than current DB record

Section 31: AI Agent Stop Conditions and Escalation Policy
Autonomous coding agents are designed to resolve tasks to completion. Left unconstrained, an agent encountering unexpected errors will speculate, bypass security checks, delete failing tests, or expand scope to satisfy its completion objective.   

An AI agent MUST immediately stop execution, leave the filesystem in a revertible state, and return a structured escalation report to the human supervisor upon encountering any of the following triggers:

Trigger 31.1 (Architectural Invariant Contradiction): The task specification directly contradicts existing repository architecture, design patterns, or framework invariants.   

Trigger 31.2 (Pre-Existing Baseline Test Failure): Existing tests fail during the Pre-Flight check prior to the agent modifying any code.   

Trigger 31.3 (Scope Boundary Incursion): Fulfilling the task requires modifying files, packages, or configurations explicitly listed under OUT OF SCOPE.   

Trigger 31.4 (Missing External Dependencies): A required third-party service, API key, database table, or environment configuration is absent from local configuration.   

Trigger 31.5 (Destructive Git or Shell Command): The execution plan requires running a command that alters local Git history (reset --hard, rebase), deletes directories (rm -rf), or alters system privileges (sudo, chmod).   

Trigger 31.6 (Ambiguous Migration State): A database migration encounters an unmapped column, an unexpected table lock risk, or ambiguous data transformation requirements.   

Trigger 31.7 (Security-Sensitive Ambiguity): Implementation touches authentication token generation, password hashing, cryptography, or authorization logic, but exact cryptographic algorithms are not specified in the task.   

Trigger 31.8 (Execution Loop Threshold): The agent executes the same tool or shell command three times consecutively with failing exit codes without making progress.

Section 32: Master Engineering Task SOP (The Organizational Standard)
This Master Standard Operating Procedure defines governance, roles, execution protocols, and verification gates across the engineering lifecycle.

Task Lifecycle State Machine
The progression of a development work unit through the engineering organization is governed by formal state transitions:

Backlog Refinement: The task is authored and refined. It remains in this state until all template sections are populated.

Ready for Review: The task is submitted for the Definition of Ready sign-off.

Ready for Development: The task has achieved a 10/10 PASS on the Readiness Scorecard and is available for dispatch.

Pre-Flight & Planning: The assigned developer or AI agent audits the environment, runs baseline tests, and establishes an implementation plan.

In Progress: Active implementation and testing take place within an isolated branch or Git worktree.

Code Review: The pull request and Handoff Manifest are audited against the original task specification contract.

Acceptance QA: Deployed staging artifacts are verified against the BDD acceptance criteria.

Merged & Deployed: The pull request is merged to the mainline branch, CI/CD deploys the build, and telemetry monitors performance.

Closed: The task lifecycle concludes with verified production operation.

Governance and Responsibilities
The creation and execution of tasks are managed under clear organizational roles:

Task Authoring: Technical Leads, Senior Software Engineers, and Technical Product Managers are authorized to draft tasks. Tasks must use the canonical schema and ISO/IEC/IEEE 29148 syntax.   

Task Review and Approval: Staff Engineers, Technical Leads, and Engineering Managers hold sign-off authority for the Definition of Ready gate. Work may not be assigned without this review.   

Task Assignment: The Technical Lead dispatches tasks based on complexity: Tier 1 tasks may be assigned to autonomous AI agents; Tier 2 and Tier 3 tasks are assigned to human engineers or paired human-agent workflows.

Code Review Sign-off: Code reviews must be conducted by a designated human peer or Technical Lead. Reviews must verify functional criteria, scope boundaries, and Definition of Done compliance.   

Acceptance Sign-off: The Product Owner or QA Engineer verifies staging deployments against acceptance criteria before tickets are marked as Closed.
