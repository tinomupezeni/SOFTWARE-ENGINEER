# Continuous Codebase Simplification, Software Entropy Reduction, and AI-Assisted Maintainability Engineering

**Research date:** October 26, 2026  
**Scope:** Scientific foundations, software-evolution evidence, code-clutter taxonomy, maintainability measurement, current tool landscape, static/dynamic/hybrid analysis, safe removal, AI-assisted workflows, continuous codebase-health engineering, system architecture, MVP feasibility, experimental validation, economics, risks, and implementation handoff.

## Executive synthesis and research method

**Executive Summary.** The central hypothesis is **partly supported, but only in a constrained form**. Software systems do tend to accumulate structural complexity as they evolve; classic software-evolution work, modularity research, technical-debt research, and modern large-scale empirical studies all support the proposition that poorly controlled dependencies, erosion of modular boundaries, maintenance hotspots, and certain structural antipatterns can increase the cost of change. Lehman's work explicitly included increasing complexity among the observed regularities of evolving E-type systems unless work is performed to maintain or reduce it; Parnas's modular-decomposition work showed why information-hiding boundaries matter; and a recent Google study of more than 1,200 C++ and Java projects, combining architectural measures with maintenance activity and 7,200 developer survey responses, found higher propagation cost and structural antipattern prevalence associated with more effort spent on bug-fixing rather than feature work. citeturn1search0turn0search1turn17search2

The stronger proposition—**that periodically lowering generic complexity metrics necessarily makes software better**—is not supported. Empirical maintenance metrics can disagree; code-smell studies have reported both useful associations and weak explanatory power; some refactorings improve structural proxies while others do not; and code that looks redundant may encode availability, compatibility, security, data-retention, operational-recovery, or external-contract requirements. A particularly important study questioning maintenance metrics found that many commonly used metrics were mutually inconsistent in their relationship with maintenance effort, with system size and low cohesion among the stronger associations in that dataset. Small controlled smell studies also have limited external validity: for example, Sjøberg and colleagues' maintenance-effort experiment involved six developers and three maintenance tasks, while Yamashita's study examined twelve smells across four medium-sized systems. citeturn13search5turn2search0turn1search5turn14search2

The most defensible engineering objective is therefore not "minimize complexity." It is:

> **Reduce demonstrably unnecessary complexity where multiple independent sources of evidence indicate low behavioral value and where verification is strong enough to make the change economically and operationally rational.**

That reframing is crucial. The target is **change friction**, not line count; **unnecessary coupling**, not abstraction count; **obsolete capability**, not old code; **unjustified dependencies**, not dependency quantity; and **maintainability outcomes**, not a prettier dashboard score. ISO/IEC 25010:2023 treats maintainability as part of a broader product-quality model rather than as an isolated scalar, reinforcing the need to balance maintainability against reliability, security, performance, functional suitability, compatibility, and other quality properties. citeturn0search2turn0search26

There is also a significant 2026 market finding: **a generic "code health + AI + MCP + refactoring" product is no longer an obvious whitespace opportunity**. CodeScene now combines behavioral analysis, technical-debt prioritization, an MCP server, and a PR Refactoring Agent; SonarQube combines deterministic quality/security analysis with AI-assisted remediation and agent-oriented integrations; jscpd's October 2026 release family has expanded from clone detection into complexity, dead-code analysis for selected languages, history-based health trends, a repository-level health score, SARIF output, and MCP integration; OpenRewrite/Moderne provides semantic transformations and increasingly agent-oriented verified context; RefactoringMiner now exposes refactoring/AST-diff capabilities through MCP; and general coding agents such as GitHub Copilot and Codex can inspect repositories, modify code, run tests, and review changes. citeturn20search1turn11search17turn26search3turn26search5turn21search15turn24search23turn18search9turn18search12

The underserved opportunity is narrower: **evidence fusion and controlled retirement**. Existing tools are strong at individual signals—static findings, dependency hygiene, clones, architectural rules, change hotspots, migration recipes, security reachability, or general-purpose agentic editing—but there remains room for a system whose primary abstraction is a *removal candidate with provenance*, combining static reachability, repository history, runtime observation, test evidence, deployment/configuration data, ownership, public-interface status, and explicit uncertainty into a reviewable retirement case. This is an inference from the competitive landscape rather than an established market fact. citeturn20search0turn20search1turn26search5turn21search8turn19search0turn5search0

**Recommended product decision:** do **not** initially build a new comprehensive code-quality platform, graph database, autonomous cleanup bot, or dashboard. Build and experimentally validate a **read-only, local-first Codebase Health Engine CLI** that orchestrates existing analyzers, constructs evidence-backed simplification candidates, records uncertainty and disqualifying evidence, and produces machine-readable and human-readable reports. Patching should be a later, explicitly authorized stage and should occur in isolated Git branches/worktrees followed by deterministic verification. MCP should be an adapter on top of that engine, not the engine itself.

**Central research questions and conclusions**

| Research question | Evidence-based conclusion |
|---|---|

| Is growing complexity inevitable? | Not strictly. Lehman's "increasing complexity" observation explicitly allows maintenance work to counteract it; refactoring and architectural governance can do so, although their benefit must be measured rather than assumed. citeturn1search0turn0search3turn14search2 |
| Is "software entropy" a rigorous universal quantity? | No. The literature uses entropy in several operational and metaphorical senses; there is no software equivalent of a single thermodynamic state variable accepted across software engineering. citeturn16search0turn16search1turn16search4 |
| Which complexity is most damaging? | High change-propagation cost, low cohesion, cycles and poor boundaries, frequently modified complex hotspots, and architectural antipatterns have stronger practical justification than raw line count or a generic complexity score. citeturn17search2turn13search5 |
| Can dead code be reliably identified? | Some closed-world cases can; public APIs, reflection, plugins, generated registration, configuration-driven entry points, and external consumers make universal proof impossible. | Can duplication be detected? | Syntactic/token and structural duplication can be detected effectively; semantic equivalence is much harder and should remain a review signal rather than an automatic deletion criterion. jscpd now explicitly labels semantic clone analysis experimental. citeturn26search5 |
| Can unnecessary abstractions be detected automatically? | Only weakly. Structural indicators can nominate candidates, but whether an interface, boundary, service, adapter, or indirection is "unnecessary" is context-dependent. |

| Where can AI add value? | Semantic interpretation, candidate investigation, explanation, cross-source synthesis, planning, test suggestions, and patch generation—provided deterministic tooling verifies the resulting claims and edits. |
| Where should AI not be authoritative? | Reachability proof, security policy, permissions, public-contract retirement, persistent-data deletion, destructive production actions, or final risk authorization. Current coding-agent security guidance explicitly emphasizes sandboxing, approvals and least privilege. citeturn18search1turn18search12turn18search19 |
| Is continuous simplification technically feasible? | Yes, as continuous *analysis and decision support*. Fully autonomous continuous deletion is not justified. |
| Is a new broad platform justified? | Not yet. Existing platforms cover much of static quality, behavioral prioritization, dependency maintenance, semantic rewriting, AI review and MCP integration. citeturn20search1turn26search3turn20search0turn21search0 |
| What is the smallest useful MVP? | A local CLI producing evidence-backed cleanup candidates, provenance, risk classification and verification requirements, with no autonomous writes. |
| What evidence would invalidate the concept? | Low precision after evidence fusion, little maintainer acceptance, no measurable reduction in comprehension/change effort, review costs exceeding savings, or existing tools solving the same workflow adequately once configured. |

**Research Questions and Methodology.** This investigation used a targeted literature and implementation review centered on primary sources: original or peer-reviewed ACM/IEEE research where available; ISO standards material; official tool documentation and current repositories; current vendor documentation for commercial capabilities/pricing; and official DORA/Google research for developer and delivery outcomes. Current tool capabilities were checked against sources available on October 26, 2026, including October 2026 releases where relevant. Dynamic documentation should be treated as a point-in-time snapshot because pricing, licensing, supported languages and product packaging can change.

This is not a formal systematic review with preregistered inclusion criteria or a complete meta-analysis. Consequently, effect sizes should not be generalized beyond the studies' populations. The report deliberately gives more weight to replicated concepts, large-sample empirical work, compiler/program-analysis foundations, and deterministic tool behavior than to vendor claims or isolated correlations. In particular, association between a smell or metric and maintenance difficulty does not establish that deleting the corresponding construct will causally improve maintainability. The mixed smell literature and recent large-scale architectural evidence make that distinction necessary. citeturn2search0turn1search5turn1search9turn17search2

## Scientific foundations, clutter taxonomy, and measurement

**Scientific Foundations.** McCabe's 1976 cyclomatic-complexity work introduced a graph-based measure of control-flow complexity intended to support program testing and management; modern tools commonly approximate function complexity as one plus the number of control-flow branches, although language-specific counting rules differ. Cyclomatic complexity therefore primarily describes independent control-flow structure; it is not a direct measurement of human comprehension, architectural quality, business value, or maintenance cost. citeturn0search8turn23search2

Parnas's 1972 modular-decomposition argument remains more directly relevant to simplification architecture: systems should be divided around design decisions likely to change and those decisions should be hidden behind appropriate interfaces. This means that "remove a layer" is not intrinsically a simplification. A boundary that prevents change propagation may add local structural complexity while reducing total system complexity. citeturn0search1turn0search5

Fowler's definition of refactoring similarly constrains the objective: refactoring is restructuring that preserves externally observable behavior. The usefulness of this definition is not that all simplification must literally be a refactoring—feature retirement intentionally changes behavior—but that removal work should explicitly distinguish behavior-preserving transformations from behavior-changing retirement. citeturn0search3turn0search11

Lehman's software-evolution observations provide the strongest conceptual support for a continuous discipline: long-lived systems embedded in real-world processes must continue changing, and their complexity tends to increase unless work is done to maintain or reduce it. That proposition is empirical rather than thermodynamic and does not imply an irreversible law. citeturn1search0turn1search4

Modern large-scale evidence strengthens the case for focusing on *architecture* rather than merely local function metrics. Google's study of more than 1,200 projects measured propagation cost, decoupling level and structural antipatterns, maintenance activity and developer sentiment; it reported that more complex architectures were associated with proportionally more bug-fix work, while developers able to spend more effort on feature work reported less hindrance from complexity and technical debt. Its scale is unusually strong, but its C++/Java and Google-internal context still limits universal generalization, and its correlations do not prove that lowering a given metric will cause an equivalent productivity gain. citeturn17search2

**Forms of complexity**

| Form | What it represents | How it commonly emerges | Why it matters |
|---|---|---|---|
| Control-flow | Number and structure of decision paths | Conditions, loops, exceptions, state handling | Raises test-path and local reasoning demands; cyclomatic complexity is a useful but incomplete proxy. citeturn0search8turn23search2 |
| Cognitive | Estimated human difficulty of following control flow | Nesting, interruptions, deeply composed logic | Sonar's Cognitive Complexity deliberately emphasizes understandability, but it is a designed heuristic rather than a universal scientific construct. citeturn23search2 |
| Structural | Relationships among program elements | Large modules, deep hierarchies, cycles, poor decomposition | Influences local comprehensibility and change propagation. citeturn0search1turn17search2 |
| Architectural | System-wide dependency and responsibility organization | Boundary erosion, inappropriate service decomposition, cross-layer dependencies | Can turn localized changes into multi-component changes; propagation cost is one useful measure. citeturn17search2turn1search3 |
| Dependency | Number and topology of package/module dependencies | Feature addition, library churn, framework accumulation | Raises upgrade, supply-chain, compatibility and comprehension surfaces; count alone is not sufficient because dependencies vary greatly in role and risk. |
| Data-flow | Paths by which values influence state/output | Shared state, aliases, mutation, callbacks, asynchronous flows | Makes impact analysis and security reasoning harder; static analyses approximate it using techniques such as abstract interpretation and slicing. citeturn22search3turn22search38 |
| Configuration | Number and interaction of deploy/runtime choices | Flags, environment variables, manifests, compatibility switches | Expands effective state space and may hide otherwise unreachable behavior. |
| Operational | Runtime topology and operational procedures | Queues, cron jobs, fallbacks, replicas, monitoring, deployment layers | Some apparent redundancy is intentionally present for resilience or recovery. |
| Essential | Complexity imposed by required behavior/constraints | Domain rules, security, distributed consistency, regulatory obligations | Must usually be managed rather than removed. |
| Accidental | Complexity arising from implementation choices rather than current requirements | Obsolete compatibility code, duplication, poor boundaries, premature abstractions | Primary target for simplification, but identifying it requires evidence about current requirements. |

**Software entropy.** "Software entropy" should be treated as a family of metaphors and operational measures, not a literal thermodynamic property. Research has used entropy-like quantities to characterize distributions of changes, structural disorder and evolving software characteristics, but different studies define and calculate "entropy" differently. There is no generally accepted unit or conserved quantity equivalent to physical entropy. citeturn16search0turn16search1turn16search4

Accordingly, a useful engineering definition for this project is descriptive rather than physical:

> **Software structural degradation:** an observed increase over time in the effort or scope required to understand, modify, verify, deploy, or recover a system, attributable partly to deterioration in its implementation or architecture rather than to unavoidable increases in required functionality.

That definition can be operationalized through change propagation, coupling, architecture violations, maintenance hotspots, change effort and developer task outcomes without claiming a universal entropy number.

**Technical debt.** The technical-debt metaphor is economically useful because debt may be rational. Brown and colleagues emphasized managing rather than automatically eliminating debt; Kruchten and colleagues worked toward sharper definitions; empirical work has modeled principal as the cost of remediation and interest as additional future maintenance cost. Architectural debt deserves special attention because the consequences can propagate across many future changes rather than one local component. citeturn14search4turn14search8turn14search12turn14search0

A practical economic decision rule is:

\[
\text{Repay when }E[\text{future avoided maintenance + risk cost}]
>
\text{remediation cost + verification cost + opportunity cost + regression risk}
\]

This is a decision model, not an empirically universal formula. "Principal" and "interest" must be estimated in context. A low-quality component that is never expected to change can be economically cheaper to leave alone than to clean.

A useful debt classification for the engine is: **design debt** (local decomposition and abstraction), **architectural debt** (system boundaries and dependency structures), **dependency debt** (obsolete or problematic third-party packages), **test debt**, **documentation debt**, **infrastructure/operations debt**, **data/schema debt**, and **deliberate versus inadvertent debt** as an orthogonal origin dimension. Reviews of technical-debt literature identify multiple debt types rather than one homogeneous phenomenon. citeturn1search2turn14search28

**Software aging, architecture erosion and change amplification.** Architecture erosion describes divergence between intended and implemented architecture; drift can result from feature pressure and local changes that violate originally intended constraints. Systematic mapping and longitudinal studies show that these are recognized software-evolution phenomena, but measurement techniques and terminology remain heterogeneous. citeturn1search3turn16search3turn16search6

A particularly actionable model is:

```text
Requirement change
      │
      ▼
Affected responsibility
      │
      ├── good modular boundary ─────► small impact set
      │
      └── coupled/eroded boundary ───► dependency fan-out
                                        │
                                        ├─ tests
                                        ├─ APIs
                                        ├─ schemas
                                        ├─ configuration
                                        ├─ deployments
                                        └─ organizational coordination
```

The goal of simplification is therefore not simply to reduce nodes. It is often to **reduce the size and uncertainty of the impact set for future changes**.

**Taxonomy of Codebase Clutter.** The following catalog is designed to translate directly into machine-readable detector definitions. The key distinction throughout is between *candidate evidence* and *proof of dispensability*.

| Category, definition, cause and example | Detection evidence | Removal risks and confidence limits | Remediation, verification and existing tools |
|---|---|---|---|
| **Dead/unreachable code.** Symbols or paths that cannot be invoked within the analyzed execution universe. Causes include abandoned features, refactors and obsolete entry points. Example: `def legacy_export(): ...` with no incoming reference. | Compiler/type information, symbol tables, import/export graph, call graph, CFG reachability, manifest/entry-point analysis. Production non-observation is supporting evidence, **not** static unreachability. | Reflection, dynamic import, framework registration, plugins, generated code, shell invocation and external API consumers can produce false positives. Python tools explicitly acknowledge this limitation. citeturn25search3turn22search4 | Delete only after resolving entry points and public interfaces; compile/type-check; targeted tests; full regression where appropriate. Knip detects unused JS/TS files/dependencies/exports; Vulture detects unused Python code; Ruff handles many unused import/variable cases. citeturn19search0turn25search3turn25search2 |
| **Redundant code.** Multiple implementations substantially implementing the same behavior. Causes include copy/paste, team separation and divergent historical utilities. Example: two independently maintained email-normalization functions. | Token clone detection, AST similarity, normalization, code embeddings/LLM semantic comparison, change history. | Two visually similar blocks may encode intentionally different policy or evolve independently. Semantic duplicate detection has materially lower certainty than exact clones. jscpd labels embedding-based Type-4 detection experimental. citeturn26search5 | Consolidate only after differential/property testing confirms behavioral overlap. jscpd and PMD CPD are mature syntactic-clone options; semantic findings should trigger investigation, not deletion. citeturn26search5turn6search0 |
| **Unnecessary abstraction.** Interfaces, wrappers, factories, inheritance or generic frameworks whose current benefits do not justify indirection. Example: a one-method interface and single implementation that exists only to delegate unchanged arguments. | Fan-in/out, hierarchy depth, delegating-method patterns, implementation count, change coupling, ownership and design-history analysis. AI can explain the pattern. | An abstraction may intentionally protect a volatile dependency, testing seam, platform variation or security boundary. "One implementation" does not prove uselessness. Parnas's information-hiding argument is a direct counterexample to naive layer deletion. citeturn0search1 | Prefer evidence of *change amplification* and low boundary value before collapsing. Require human architectural review unless the transformation is behaviorally trivial. |
| **Dependency clutter.** Direct dependencies that are unused, redundant, unnecessarily heavy, obsolete or replaceable, plus poorly understood transitive dependencies. Example: package declared in `pyproject.toml` but never imported or used by tooling. | Compare manifests, lockfiles, imports, build scripts, plugins, native hooks and runtime loading. Classify runtime/build/dev/optional/transitive role before judgment. | Framework plugins, scripts, dynamic loading and package metadata can make "no source import" incorrect. Removing a direct dependency may alter transitive resolution. | Remove in isolation; regenerate lockfile; build, test and inspect packaged artifact. Knip covers JS/TS; deptry covers Python; Renovate/Dependabot address update hygiene rather than semantic necessity. citeturn19search0turn5search0turn9search2turn9search10 |
| **Architectural clutter.** Excess services, communication hops, cycles, inappropriate module boundaries or infrastructure whose operational cost outweighs required isolation. Example: two services deployed, versioned and changed together with synchronous one-to-one calls. | Dependency graphs, SCC/cycle analysis, architecture rules, distributed traces, deployment topology, co-change analysis and ownership. | Isolation can be essential for independent scaling, security, failure containment, data ownership or team autonomy. Consolidation changes failure domains. | Enforce intended boundaries first; consolidate only with operational evidence. ArchUnit, dependency-cruiser and CodeScene cover complementary architecture/dependency aspects. citeturn25search0turn6search2turn20search7 |
| **Database clutter.** Apparently unused tables, columns, indexes, views, duplicate representations, ORM layers or migrations. Example: column with no application references and no observed reads. | Schema-reference search, SQL/query logs, ORM metadata, BI/report inventory, external-consumer registry, migration history and access auditing. | Absence from application code is especially weak evidence: reporting, audit, legal retention, manual operations, DR and external consumers may depend on the data. | Deprecate before drop; deny new writes; shadow/observe; back up; validate retention obligations; perform schema changes through established migration/recovery mechanisms. Database destruction belongs in the high-risk tier. |
| **Configuration clutter.** Flags, variables, settings, manifests and infrastructure parameters that no longer affect behavior. Example: a flag fixed "on" across all active environments after migration completion. | Static read graph + configuration repositories + deployment inventories + runtime evaluation telemetry + ownership. | Rare environments, customer-specific overrides and rollback paths are commonly missed. | Remove flag logic only after checking every supported environment and rollback policy; deploy staged. |
| **Testing clutter.** Duplicate, obsolete, brittle or excessively mocked tests whose cost exceeds incremental fault-detection value. | Test similarity, coverage overlap, execution history, flakiness data and mutation testing. | Overlapping tests may intentionally provide defense in depth at different levels; high coverage does not imply identical fault-detection capability. Mutation testing has evidence as a useful proxy but is computationally expensive. citeturn15search1turn15search5turn15search9 | Prefer removing demonstrably redundant cases only after mutation/coverage comparison and failure-history review. Preserve contract, security and regression coverage even when overlap appears high. |
| **Documentation clutter.** Outdated, duplicate or contradictory comments, guides, API descriptions or architecture documents. Example: a README instructing developers to use an endpoint removed two years earlier. | Link/reference validation, code/API/spec diffs, Git age, ownership, generated-doc provenance and LLM-assisted contradiction detection. | Documentation may describe external contracts or procedures not visible in source; an LLM cannot establish truth from repository text alone. | Reconcile against authoritative code/config/API contracts; generate where appropriate; require owner review for operational/compliance docs. |
| **Operational clutter.** Obsolete jobs, monitors, alerts, deployment resources, excessive instrumentation or unused fallback paths. Example: scheduled worker still deployed although its feature has retired. | IaC/manifests, scheduler inventory, telemetry, trace data, alert histories, runbooks, cost data and service ownership. | Rare recovery procedures, disaster failover and security/compliance controls are deliberately infrequent. | First disable or quarantine, observe, then remove through operational change control. Recovery capability requires explicit sign-off. |

A machine-readable detector catalog should make those caveats first-class rather than burying them in prose. A candidate schema could begin as:

```yaml
id: dead-export.ts.no-inbound-reference
family: dead_code
targets: [function, class, export]
languages: [typescript, javascript]

detector:
  required_evidence:
    - type: static_symbol_reference_count
      predicate: "== 0"
    - type: public_entrypoint_status
      predicate: "== false"

  supporting_evidence:
    - type: git_last_reference_age
    - type: runtime_observation
    - type: test_reference_count

  disqualifiers:
    - dynamic_import_possible
    - reflection_or_registration
    - declared_package_export
    - external_consumer_unknown
    - generated_code
    - framework_entrypoint

risk_default: medium

verification:
  - typecheck
  - build
  - affected_tests
  - public_api_diff

automation:
  propose: true
  generate_patch: opt_in
  auto_merge: false

provenance_required: true
confidence_model: calibrated_from_adjudicated_findings
```

The critical architectural choice is that a "finding" is not merely `{rule, location}`. It is an **argument** containing affirmative evidence, contradictory evidence, provenance, coverage and the verification required to resolve uncertainty.

**Software Complexity and Maintainability Metrics.** Metrics should be divided into three layers: structural indicators, engineering-process outcomes and human outcomes. Optimizing only the first layer invites Goodhart-like behavior because developers can alter a metric without improving the system experienced by maintainers.

| Metric | Calculation / interpretation | Evidence and limitations | Automated-decision role |
|---|---|---|---|
| **Cyclomatic complexity** | Original graph form \(V(G)=E-N+2P\); often operationalized per routine as `1 + branch points`. citeturn0search8turn23search2 | Useful for control-flow/path structure and testing attention; does not capture naming, data flow, architecture, domain complexity or comprehension. Language implementations differ. | Ranking signal; never sufficient for removal. |
| **Cognitive complexity** | Rule-based score increasing for control-flow structures and nesting. citeturn23search2 | Specifically designed around understandability, but is a Sonar-defined model rather than a universally validated cognitive measurement. | Ranking/PR feedback, not autonomous restructuring. |
| **Maintainability Index** | Common Microsoft variant: `MAX(0,(171 − 5.2 ln(V) − .23 CC − 16.2 ln(LOC))*100/171)`, where `V` is Halstead volume. citeturn23search0turn23search1 | Compresses size, Halstead and CC into one number; formula/threshold variants exist. Empirical evidence does not justify interpreting it as a universal probability of maintainability. | Trend signal only. |
| **Duplication** | Fraction/count of token-, AST- or normalized clone fragments. | Exact duplication is objective under a detector's definition; semantic redundancy is not. Generated code and intentionally parallel implementations distort results. citeturn26search5 | Good candidate generator; not automatic consolidation. |
| **Coupling** | Incoming/outgoing dependency counts, normalized graph measures or class/module-specific formulations. | High coupling can increase propagation but some central abstractions legitimately have high fan-in. Architectural context matters. citeturn17search2 | Stronger when combined with churn/change propagation. |
| **Cohesion** | Family of measures estimating how strongly responsibilities/elements inside a module relate. | There is no single cohesion formula; empirical work has found low cohesion relevant to maintenance effort, but metric variants differ. citeturn13search5 | Useful structural signal. |
| **Dependency graph density** | For a directed graph, typically \(m/[n(n-1)]\) where all node pairs could be connected. | Strongly affected by graph granularity; density can fall merely by adding nodes. | Diagnostic only. |
| **Cycles** | SCC count, SCC size, participating nodes/edges. | Cycles impede independent reasoning and layering but some runtime/component models tolerate them. | Architecture gate where a declared policy prohibits cycles. |
| **Propagation cost** | Fraction of system reachable through direct/transitive dependency relationships under a defined design-structure matrix. | Large-scale Google evidence links higher architectural propagation to maintenance burden; representation granularity remains important. citeturn17search2 | High-value architecture trend/ranking signal. |
| **Change coupling** | Frequency/strength with which files/modules change together in version history. | Captures behavioral architecture invisible in static imports; can be distorted by bulk commits, formatting and release processes. CodeScene operationalizes this class of behavioral analysis. citeturn20search7 | Excellent prioritization evidence when paired with static structure. |
| **Code churn** | Added/deleted/modified lines or change frequency over an interval. | High churn may signal hotspot risk or simply successful active development. | Pair with complexity/defects, never use alone. |
| **Defect density** | Defects per LOC/component/release or another normalized denominator. | Defect discovery/reporting processes vary; LOC normalization penalizes compact representations differently. | Outcome validation, not cleanup trigger. |
| **Change lead time / deployment frequency** | DORA delivery-performance measures of throughput. | System-level outcome; affected by many organizational factors outside code structure. DORA's current framework emphasizes multiple delivery measures rather than one productivity number. citeturn12search0turn12search4 | Evaluate whether interventions improve delivery, not candidate detection. |
| **Failed deployment recovery / change fail / rework rate** | Stability/recovery dimensions in current DORA measurement. citeturn12search0turn12search4 | Useful counterbalance against simplification that makes changes faster but less safe. | Essential outcome guardrail. |
| **Comprehension/task time** | Time required for a developer to correctly answer questions or complete a representative change. | Directly relevant but expensive and noisy; skill and familiarity are confounders. DevEx and SPACE frameworks explicitly recommend multidimensional productivity measurement. citeturn17search0turn17search1 | Primary experimental outcome. |
| **Build/test cost** | Wall-clock time, compute, queue time and monetary execution cost. | Changes may trade maintenance simplicity for more verification, or vice versa. | Direct before/after measure. |
| **Security exposure** | Reachable vulnerabilities, attack surface, privileged pathways and policy violations rather than one universal score. | A dependency count alone is not a security metric. Removing a library may reduce one exposure but introduce custom security-sensitive code. | Separate security analysis; veto where risk increases. |
| **Maintenance effort** | Human time/changes required for corrective and evolutionary work. | Closest to economic outcome but difficult to attribute causally. | Ultimate longitudinal measure. |

**Composite health scores.** A single score is useful for dashboards and prioritization but is scientifically dangerous when interpreted as an intrinsic property of a codebase. A score necessarily embeds weights and value judgments: how many points is a dependency cycle worth relative to a flaky test, an inaccessible module boundary, an unused package or a public API? Research showing disagreement among maintenance metrics is a strong argument against universal weighting. citeturn13search5

Current products nevertheless demonstrate market demand for composites: CodeScene markets CodeHealth, and jscpd's current 2026 implementation includes a repository-level health score alongside duplication, complexity, dead code and history trends. Those are useful competitive facts, not scientific validation that either weighting generalizes to every organization. citeturn20search1turn26search5

The recommended framework is therefore a **multidimensional scorecard**:

```text
Structural risk       ─ coupling / cycles / propagation / duplication
Change pressure       ─ churn / hotspot / change coupling
Evidence of waste     ─ unused references / runtime inactivity / stale config
Verification strength ─ tests / contracts / types / build / telemetry
Operational risk      ─ public API / data / auth / recovery / compliance
Developer outcomes    ─ comprehension / task time / friction / satisfaction
Delivery outcomes     ─ lead time / failure / recovery / rework
```

A scalar may be offered for navigation only after weights are transparent and locally calibrated. It should never be the direct authorization criterion for a deletion.

**Competitive conclusion.** Static code-quality analysis is crowded. Dependency maintenance is crowded. AI code review and patch generation are crowded. Code-health trend dashboards are increasingly crowded. MCP connectivity itself has rapidly commoditized: CodeScene, jscpd, RefactoringMiner and ast-grep now expose or document MCP-oriented capabilities. citeturn20search1turn26search5turn24search23turn26search6

The likely differentiation is therefore not "we use AI to clean code." A defensible product would need to offer at least three capabilities that are not usually integrated coherently:

1. **Cross-domain evidence fusion:** source references + dependencies + tests + Git + runtime + config + infrastructure + ownership + API/data contracts.
2. **Retirement-specific risk modeling:** explicitly distinguish "unused in the analyzed graph" from "safe to remove from the system."
3. **Closed-loop outcome measurement:** verify not merely that a patch passes CI, but whether accepted simplifications later reduce change/comprehension effort without degrading reliability.

That is an architectural inference based on the overlap above, not proof of customer willingness to pay.

**Static, Dynamic, and Hybrid Analysis Techniques.** Static program analysis gives the system its strongest deterministic foundation. ASTs provide syntactic structure; symbol tables associate identifiers with declarations; call graphs approximate invocation relationships; CFGs capture local control flow; data-flow analysis propagates facts; program slicing identifies statements relevant to selected values/behaviors; and abstract interpretation provides a mathematical framework for safely approximating program behavior over abstract domains. Weiser's 1981 slicing work and Cousot & Cousot's 1977 abstract-interpretation framework remain foundational. citeturn22search38turn22search3

Static reachability nevertheless depends on assumptions. Empirical research on call-graph recall shows that modeling dynamic behavior such as reflection, proxies and runtime dispatch remains difficult, and specialized reflection-aware analyses continue to be an active topic. A graph saying "zero callers" therefore means "zero callers under this analyzer's model and entry-point assumptions," not necessarily "impossible to call." citeturn22search4turn22search36

Dynamic analysis supplies a different kind of evidence: observed execution. Function tracing, coverage, API request logs, query logs, feature usage, profiling and distributed traces can demonstrate that something **was** used. Their negative evidence is inherently weaker: "not observed" means only "not observed under these workloads, tenants, platforms and observation periods." Rare recovery logic, annual jobs and unusual regional behavior illustrate why absence of runtime evidence cannot prove deadness.

The correct model is asymmetric:

\[
\text{Observed execution} \Rightarrow \text{strong evidence of liveness}
\]

\[
\text{No observed execution} \nRightarrow \text{proof of deadness}
\]

Negative runtime evidence becomes stronger only as observation coverage becomes more representative and complementary evidence accumulates.

**Difficult cases.** Reflection, dynamic imports, plugins, dependency injection containers, runtime configuration, code generation, externally consumed packages, scheduled tasks, fallback paths, multi-tenant behavior and platform-specific implementations all weaken closed-world assumptions. ## Safe simplification, AI roles, and continuous health engineering

**Safe Code Removal and Refactoring.** The safety principle should be stronger than "tests passed":

> **A simplification is acceptable when its intended behavioral effect is explicit, its impact surface is understood sufficiently for its risk class, its verification is proportionate to potential harm, and rollback remains available.**

Tests are evidence, not a mathematical proof that omitted behavior is unnecessary. The appropriate verification technique depends on the change.

| Verification technique | Best use | Important limitation |
|---|---|---|
| **Characterization tests** | Freeze existing behavior around poorly understood legacy code before restructuring. | May preserve accidental behavior and inherit existing blind spots. |
| **Regression tests** | Detect previously specified behavior changes. | Only as strong as covered assertions. |
| **Property-based testing** | Explore large input spaces around invariants rather than a fixed example set; QuickCheck established the approach. citeturn15search10 | Requires meaningful properties and good generators. |
| **Differential testing** | Compare old and simplified implementations over the same inputs. | Shared bugs survive; equivalence depends on tested domain. |
| **Mutation testing** | Estimate whether tests actually detect injected behavioral changes. Research supports mutants as useful proxies and empirical relationships to real faults, while practical studies also note cost. citeturn15search1turn15search5turn15search28 | Computationally expensive; mutation operators are proxies, not real defects. |
| **Contract testing** | Public/service/provider-consumer interfaces. | Unknown external consumers remain outside the contract set. |
| **Integration/system testing** | Cross-component behavior after architectural/dependency changes. | Slower and harder to localize failures. |
| **Snapshot testing** | Serialized/UI/output changes where intentional deltas can be reviewed. | Easy to approve large snapshots without semantic scrutiny. |
| **Formal verification/static proof** | Narrow critical properties where formal models exist. Abstract interpretation can provide sound guarantees for properties within its model. citeturn22search3turn22search35 | Expensive or infeasible for complete application behavior. |
| **Observability-assisted validation** | Post-deployment verification of feature/API/runtime retirement. | Monitoring can miss unknown dimensions and rare paths. |

**Risk framework**

| Risk | Typical candidate | Required controls | Automated action policy |
|---|---|---|---|
| **Low** | Unused local import, unreachable private branch proven by compiler semantics, redundant local variable | Static proof, formatter/linter, type-check/build, targeted tests | Tool may generate an opt-in patch; merge still via normal SCM controls. |
| **Medium** | Private function/module, direct dependency, duplicate implementation, internal configuration flag | Cross-reference graph, affected tests, integration/build checks, package artifact inspection, reviewer | Generate candidate and possibly patch; explicit approval required. |
| **High** | Public API, database schema/data, auth/security logic, billing/financial behavior, operational recovery, migrations, external integrations | Owner/consumer inventory, contracts, staged retirement, security review, data/rollback plan, integration/system tests, production monitoring | Never destructively modify solely from automated/LLM inference. |

A raw language-model confidence score must **not** be treated as a calibrated probability. Until empirical calibration exists, the system should use ordinal evidence labels such as `strong`, `mixed`, and `insufficient`. Once a sufficiently large adjudicated dataset exists, detector-specific probabilities could be calibrated with standard calibration techniques and evaluated using reliability curves, Brier score or expected calibration error. The LLM's own self-reported confidence should not be the dependent variable.

**Mandatory staged workflow**

1. Identify a candidate without modifying the working tree.
2. Collect supporting and contradictory evidence.
3. Estimate the impact set.
4. Resolve static, runtime, configuration, external and ownership dependencies.
5. Assign a risk class.
6. Propose a change and state exactly what behavior is intended to remain or disappear.
7. Obtain authorization appropriate to the risk class.
8. Apply the change in an isolated branch/worktree/sandbox.
9. Run the candidate-specific verification plan.
10. Review both semantic findings and the resulting diff.
11. Release through the repository's established deployment controls.
12. Monitor relevant runtime and delivery indicators.
13. Roll back or restore the retired capability when acceptance criteria fail.

This workflow deliberately separates *candidate generation* from *modification authority*. Fowler's behavior-preserving refactoring model supports this separation for refactorings, while current agent security guidance independently supports explicit approvals, sandboxing and least-privilege execution. citeturn0search3turn18search12turn18search3

**AI-Assisted Simplification.** Five approaches should be distinguished rather than grouped under "AI analysis."

| Approach | Strength | Weakness | Recommended role |
|---|---|---|---|
| **Traditional static analysis** | Deterministic, reproducible, cheap once configured, clear provenance | Limited by models, language dynamism and unknown external context | Ground-truth-like facts *within declared assumptions*. |
| **LLM-only repository analysis** | Semantic explanation, flexible reasoning, can notice conceptual duplication and design smells | Hallucination, incomplete context, non-reproducibility, poor proof of absence | Brainstorming and investigation only. |
| **Static analysis + LLM** | Facts come from deterministic tools; LLM interprets and explains | LLM can still overstate evidence | Recommended default for semantic investigation. |
| **Agentic workflow with tools** | Can iteratively query graph, run tests, generate/refine patches | Expands tool-execution and prompt-injection attack surface | Useful behind sandbox/approval boundaries. |
| **Hybrid static + runtime + history + AI** | Closest representation of real system use and evolution | Highest integration/coverage complexity; still cannot prove all external behavior | Long-term target for high-value retirement decisions. |

Modern agent tooling demonstrates that repository-scale editing and testing are technically feasible. GitHub describes cloud agents that read files, edit code and run tests, while Codex documentation describes sandbox and approval controls for agent execution. These capabilities make AI a useful *orchestrator* but simultaneously increase the consequence of an incorrect assumption. citeturn18search9turn18search12

The safest high-value AI roles are, in descending order:

**Investigator and explanation engine.** Given deterministic evidence, the model can explain why a candidate exists, summarize call chains/history and identify unresolved questions.

**Refactoring planner.** It can propose a minimal sequence of changes and verification steps while explicitly preserving architectural constraints.

**Verification coordinator.** It can choose among already-authorized deterministic checks, interpret failures and request additional evidence.

**Patch generator.** It can implement an approved plan in a branch or sandbox, where the diff is subject to normal review.

**Semantic candidate generator.** It can nominate conceptual duplication or unnecessary abstraction for review, but the resulting signal should have low initial trust.

The AI should **not** be the authoritative source for "this function has no callers," "this API has no external consumers," "this column is unused," "this fallback is obsolete," or "this security layer can be removed." Those propositions require tool-derived or human evidence.

**AI security.** Repository content itself is untrusted input. GitHub explicitly documents prompt injection as a risk for cloud coding agents; current Copilot documentation warns that agent skills may contain prompt injections or malicious scripts. OWASP's agent and MCP guidance recommends least privilege, per-tool authorization, sandboxing and human approval for sensitive operations. Research published in 2026 has also demonstrated practical prompt-injection attack surfaces in agentic coding environments. citeturn18search5turn18search25turn18search23turn18search34

Therefore the engine must distinguish at least four trust domains:

```text
Trusted control plane
  ├─ engine policy
  ├─ approved detector definitions
  └─ permission model

Untrusted repository content
  ├─ source comments
  ├─ README / AGENTS / instruction files
  ├─ issues / PR text
  └─ generated artifacts

Semi-trusted tools
  ├─ analyzers
  ├─ compilers
  ├─ test commands
  └─ MCP servers

Sensitive environment
  ├─ repository credentials
  ├─ secrets
  ├─ network
  └─ production systems
```

LLM output must be treated as data, not authority. Tool calls should be schema-validated. Repository analysis should default to read-only. Network should be disabled unless needed. Secrets should not enter prompts. Sensitive commands should require explicit approval. Tool descriptions and MCP servers should be pinned and reviewed, consistent with current OWASP MCP guidance. citeturn18search11turn18search23

**Continuous Codebase Health Engineering.** The phrase should remain explicitly provisional. The reviewed literature supports constituent disciplines—software evolution, architecture conformance, technical-debt management, refactoring, static analysis, DevEx and continuous delivery—but does not establish "Continuous Codebase Health Engineering" as a recognized academic field.

It is nevertheless a useful operational discipline if defined as:

> **The continuous collection and evaluation of evidence about a software system's ability to change safely and economically, followed by prioritized interventions whose effects are verified against structural, developer and delivery outcomes.**

That definition avoids equating the discipline with continual cleanup.

The workflow should have several feedback loops:

| Engineering moment | Automated activity | Human activity |
|---|---|---|
| Local development | Fast lint/dependency/architecture delta; explain new complexity | Decide whether local design trade-off is justified |
| Pull request | Compare baseline vs proposed graph, duplication, dependencies and architecture rules | Review only material new risk; approve exceptions |
| Scheduled audit | Recompute hotspots, stale candidates and evidence quality | Prioritize a small number of worthwhile interventions |
| Feature retirement | Collect usage, references, ownership, contracts and config evidence | Product/engineering owner authorizes behavior removal |
| Architecture review | Track cycles, propagation, boundary violations and co-change | Decide whether structure or intended architecture should change |
| Simplification change | Execute authorized patch + verification | Review semantic diff |
| Post-release | Compare regressions, runtime signals and maintenance outcomes | Decide retain/rollback and update rules |

The strongest product principle is **budgeted attention**: a system that produces hundreds of technically true but economically irrelevant findings has failed. CodeScene's emphasis on hotspots and behavioral prioritization illustrates why raw static issue volume is insufficient. citeturn20search7

## System architecture, MVP, and engineering roadmap

**Proposed System Architecture.** Three architectural alternatives are viable.

| Alternative | Design | Advantages | Disadvantages | Verdict |
|---|---|---|---|---|
| **Local evidence orchestrator** | Single CLI process; adapters invoke existing analyzers; normalize findings into SQLite/JSON; in-memory/relational graph queries; optional LLM; Git worktree for approved fixes | Lowest cost, local/privacy friendly, deterministic, easy to benchmark, no service operations, suitable for CPU-only environment | Limited centralized history and organization-wide cross-repo analysis | **Recommended MVP** |
| **Graph-centric repository intelligence service** | Ingestion workers build a persistent property graph; API/query service; analyzers and LLM operate over graph | Strong cross-repository/impact queries; useful for architecture exploration and persistent evidence | Graph schema/versioning complexity, ingestion cost, more infrastructure; graph DB may be unnecessary for modest repositories | Consider only after graph queries demonstrate value that SQL/in-memory structures cannot deliver |
| **Continuous multi-service platform** | Web/API, queue, workers, persistent graph, telemetry ingestion, LLM gateway, policy engine, sandbox runners, Git integrations | Enterprise scalability, centralized governance, scheduled analysis, multi-tenant product capabilities | Highest security/operational burden; risks becoming exactly the unnecessary architecture being studied | **Explicitly reject for initial implementation** |

The key architecture recommendation is to **earn complexity**. There is no technical reason an MVP needs a graph database. A repository graph is a *data model*, not a database requirement. An edge table in SQLite/DuckDB and an in-memory graph implementation can answer reachability, SCC, fan-in/out and impact queries for many repository sizes. A property-graph database should be introduced only when measured cross-repository scale, query latency or graph-query expressiveness becomes a bottleneck.

**Repository ingestion.** Git should be the canonical source of repository content and history. The MVP should support a local checkout first; remote repositories can be cloned by the user's established Git credentials rather than introducing a repository-hosting credential store. Monorepos should be modeled as repositories containing one or more workspaces/components rather than treated as a special architecture.

**Language analysis.** Do not build a universal compiler front end. Use native/high-quality tools where semantics matter: Knip/TypeScript ecosystem for JS/TS dead exports/dependencies, Ruff and deptry for Python, jscpd for clones, dependency-cruiser for JS/TS architecture, language compilers/type checkers for authoritative build/type information, and Tree-sitter/ast-grep for inexpensive common syntax extraction. Tree-sitter is appropriate for syntax trees, while tools such as OpenRewrite demonstrate why type attribution is required for semantics-sensitive transformations. citeturn19search0turn5search0turn25search0turn8search2turn20search8

**Repository knowledge graph.** Use the word "graph" conceptually. Initial node types should be `Repository`, `Component`, `File`, `Symbol`, `Package`, `Test`, `API`, `ConfigKey`, `DatabaseObject`, and `DeploymentArtifact`. Edge types should begin with `DECLARES`, `IMPORTS`, `CALLS`, `DEPENDS_ON`, `TESTS`, `CONFIGURES`, `DEPLOYS`, `OWNS`, `CHANGED_WITH`, and `EXPOSES`. Additional edge kinds should be added only when a detector consumes them.

**Evidence collection.** Each adapter should produce evidence with source/provenance rather than directly deciding deletion. An analyzer's false-positive limitation therefore remains visible. For example, a Vulture finding can be recorded as "static Python analyzer found no recognized use" while the system separately records whether framework/plugin conventions are present. This is materially safer than normalizing everything into `unused=true`. Vulture's own warning about Python dynamism illustrates the importance of preserving this distinction. citeturn25search3

**Risk analysis.** Policy should be deterministic. Suggested defaults:

```text
public interface        -> HIGH
persistent data         -> HIGH
auth/security           -> HIGH
payments/financial      -> HIGH
migration/recovery      -> HIGH
external consumer       -> HIGH
unknown ownership       -> at least MEDIUM
runtime-only evidence   -> never LOW
local private symbol
 + closed-world proof
 + build/test available -> potentially LOW
```

**AI reasoning.** The LLM interface should receive a structured evidence packet, not an unrestricted dump of the repository whenever possible. Its outputs should conform to a schema:

```json
{
  "candidate_id": "...",
  "summary": "...",
  "evidence_interpretation": [],
  "contradictions": [],
  "unknowns": [],
  "proposed_action": "keep|investigate|deprecate|remove",
  "verification_additions": [],
  "rationale": "..."
}
```

The model must not be allowed to change `risk_class`, suppress deterministic vetoes, or label a candidate "proven safe."

**Refactoring planner and verification engine.** Deterministic transformation systems should be preferred when a known rewrite exists. OpenRewrite's type-attributed LST and recipe architecture illustrate the advantage: the transformation can encode known semantics and preserve source formatting rather than relying on unrestricted text generation. ast-grep is a lighter-weight fit for structural rewrites. AI-generated patches should be reserved for changes not expressible through trusted transforms and should pass the same verification pipeline. citeturn21search8turn26search10

**Developer interfaces.** Priority should be:

`CLI → JSON/SARIF → GitHub annotations/PR → MCP → optional web UI`.

This order avoids making the user interface the product. MCP is useful because the same evidence can be exposed to coding agents, but current competition demonstrates that simply adding an MCP server is not differentiation. citeturn20search1turn26search5turn24search23

**Security and governance.** Execution workers should run with repository-scoped filesystem access, network disabled by default, no production credentials, CPU/memory/time limits and explicit command allowlists where feasible. Agent modifications should use disposable worktrees or containers. Every detector, LLM analysis, authorization and patch should be auditable. OWASP's current AI-agent/MCP recommendations and coding-agent product guidance consistently emphasize least privilege, sandboxing and human approval for sensitive operations. citeturn18search3turn18search23turn18search12

**Recommended MVP:** Option A, with architecture intentionally shaped so B and C become adapters.

The first version should support **Python and TypeScript/JavaScript**, because the stated environment already includes both ecosystems and mature reusable analyzers exist. It should initially detect only categories with reasonably observable evidence:

- unused imports/exports/files and direct dependencies;
- syntactic duplication;
- dependency cycles and architecture-rule violations;
- change hotspots and co-change relationships;
- candidate stale configuration references where only static evidence is claimed.

Semantic duplicate detection, database retirement, operational retirement and architectural service consolidation should initially appear as investigation modules rather than automated removal detectors.

| Requirement | MVP behavior |
|---|---|

**Nonfunctional requirements**

The engine should be deterministic when AI is disabled, reproducible from a locked tool configuration, local-first, resilient to an individual analyzer failing, explicit about incomplete evidence, resource bounded, auditable, and usable on CPU-only Linux. No repository source should be transmitted externally without explicit configuration. Output schemas need versioning because downstream agents and CI integrations will depend on them.

**MVP acceptance criteria** should be defined as experimental targets, not claimed performance:

| Criterion | Proposed acceptance target |
|---|---|
| Destructive behavior | **Zero** file/code modifications in default audit mode |
| Evidence provenance | 100% of emitted candidates identify their supporting detector/source |
| Risk transparency | 100% identify risk class and required verification |
| Low-risk precision | Target ≥90% maintainer-confirmed precision in the defined low-risk classes before enabling automated patch generation |
| Regression safety | No auto-merged changes; experimental patches must pass configured verification |
| Offline operation | Core analysis works without an LLM or network |
| Reproducibility | Same commit + config + tool versions produces equivalent deterministic findings |
| Performance | Establish a CPU-only baseline during pilot; set service-level targets only from measured repository distributions rather than inventing one now |
| Suppression burden | Track suppressions and repeated false positives; unacceptable suppression volume is a product-failure signal |
| Usefulness | Maintainers judge a meaningful fraction of prioritized findings worth investigating; measure rather than assume the required rate |

**What should explicitly not be built first**

Do not build a bespoke multi-language parser/type system; universal "AI maintainability score"; graph database; microservice architecture; production telemetry platform; autonomous deletion bot; database-cleanup executor; IDE plugin; web dashboard; all-language support; self-hosted LLM infrastructure; or generic code-generation agent. Existing tools already solve substantial parts of these problems, and many would create exactly the maintenance burden this product is intended to reduce.

**Phased Implementation Roadmap**

**Foundation milestone:** define the evidence schema, candidate taxonomy, CLI contract, configuration format, adapter interface and experiment protocol before substantial product code.

**Deterministic audit milestone:** Python/JS/TS adapters, Git analysis, graph construction, rules, JSON/Markdown output, suppressions and baseline comparison.

**Evidence-fusion milestone:** combine multiple findings into candidates, add contradictory evidence, risk classification and confidence calibration infrastructure.

**Verification milestone:** isolated worktrees, configurable type/build/test checks, before/after evidence and diff review. No autonomous merging.

**Workflow milestone:** GitHub Actions/PR annotations, incremental analysis and machine-readable artifacts.

**Agent-interface milestone:** read-only MCP resources/tools for querying candidates, evidence, impact sets and verification requirements; separate write-capable tools behind explicit authorization.

**Advanced-evidence milestone:** runtime telemetry import, external-consumer registries, database/config/operational adapters, organization-wide historical analysis.

A web dashboard or multi-repository service should become a separate product decision only after the earlier phases demonstrate repeated demand.

## Experimental validation, economics, risks, and open questions

**Experimental Validation Framework.** The validation problem is harder than building the analyzer because "unnecessary code" has no universal ground truth. Static-analysis output must never be relabeled as truth simply because the system generated it.

A robust benchmark should have four complementary ground-truth sources.

**Historical removal commits.** Mine real repositories for commits that removed code, dependencies, configuration or abstractions; use RefactoringMiner and semantic diffs to distinguish refactoring structure from functional edits where applicable. RefactoringMiner can analyze complete repository history and current versions provide AST-aware diffs. citeturn24search2turn24search6

**Synthetic clutter injection.** Insert controlled dead functions, unused dependencies, cycles, clones, stale configuration reads and wrappers into known revisions. Synthetic examples provide exact labels and recall measurement but should not be mistaken for real-world difficulty.

**Maintainer adjudication.** Present candidates to maintainers with evidence hidden/randomized where useful. Record `safe-to-remove`, `useful-but-not-now`, `necessary`, `unknown` and rationale. Inter-rater disagreement is itself valuable because it identifies inherently judgment-heavy detector families.

**Regression corpora.** Defects4J currently contains 854 active reproducible Java bugs plus deprecated cases and verified triggering tests, while BugsInPy provides reproducible real-world Python bugs. These corpora are not ground truth for code clutter, but they are useful for testing whether transformations and verification strategies preserve or expose behaviors. citeturn24search0turn24search1

Repository sampling should be stratified across language, size, architecture, age, test coverage, contributor count, maintenance activity and deployment style. The initial MVP should emphasize Python and JS/TS because those are supported directly; later experiments should add Java or other languages to test portability rather than claiming language independence from the first sample.

**Evaluation measures**

\[
Precision = \frac{\text{true unnecessary candidates}}
{\text{all candidates reported}}
\]

\[
Recall = \frac{\text{unnecessary artifacts detected}}
{\text{all known unnecessary artifacts}}
\]

\[
False\ Positive\ Rate = \frac{FP}{FP + TN}
\]

For risk probabilities, once calibrated labels exist, use calibration metrics as well as classification accuracy. For product utility, measure recommendation acceptance, review time, percentage deferred because evidence is insufficient, suppression rate, patch success, verification failures and regression frequency.

Crucially, structural measures are intermediate outcomes. The experiment should additionally measure:

- time to understand a component sufficiently to answer comprehension questions;
- time and number of files touched for representative change tasks;
- review time;
- build/test execution cost;
- defect/regression outcomes;
- delivery stability and throughput where organizational observation is possible;
- developer-reported friction and confidence.

SPACE argues that developer productivity is multidimensional rather than reducible to activity volume, while DevEx work emphasizes developer feedback alongside system telemetry. DORA similarly measures several dimensions of delivery rather than treating code-output volume as productivity. citeturn17search0turn17search1turn12search0

**Longitudinal design.** A strong validation would compare matched components or repositories before and after accepted simplifications, with pre-intervention baselines and enough observation to capture subsequent real changes. Where teams permit, staggered treatment or matched-control designs can help separate simplification effects from organizational trends. Record team size, contributor familiarity, workload, release cadence, test maturity and simultaneous architecture migrations as confounders. Sample size should be selected through power analysis after pilot variance/effect estimates rather than choosing an impressive arbitrary number.

A particularly valuable test is **prospective change amplification**:

```text
Before simplification:
feature task -> files touched -> modules touched -> tests -> review time

After simplification:
comparable task -> files touched -> modules touched -> tests -> review time
```

If a simplification lowers a structural score but subsequent changes require equal or greater effort, the claimed maintenance benefit has not been demonstrated.

**Failure analysis** must classify at least:

```text
false unused inference
external consumer missed
reflection/plugin registration missed
test gap
semantic duplicate was intentionally different
abstraction removal increased coupling
dependency removal changed packaging/runtime
configuration retirement broke rare environment
schema removal harmed reporting/retention
performance regression
security/control regression
operational recovery path removed
cleanup had no measurable future benefit
```

Failed cleanup experiments should remain in the benchmark. Removing them would bias subsequent confidence estimates upward.

**Economic and Product Feasibility.** Economic value should be modeled directly rather than inferred from lower code-health scores:

\[
\text{Net value}
=
(\Delta\text{engineering time} \times \text{loaded engineering cost})
+
\text{expected avoided incident/rework cost}
-
\text{analysis cost}
-
\text{review cost}
-
\text{remediation cost}
-
\text{regression risk cost}
\]

Technical-debt research supports thinking in terms of principal and future interest, while developer-productivity research warns against equating visible activity with value. citeturn14search12turn17search0

The large Google architectural study gives the concept a plausible economic mechanism: architectures with higher propagation cost and structural antipatterns were associated with more maintenance/bug-fix work. It does **not** tell us the return on investment of a new simplification product. That must be established experimentally. citeturn17search2

Likewise, AI's economic effect is not automatically positive. DORA's current AI research describes AI as an amplifier and reports trade-offs between local developer acceleration and downstream instability/verification burden. A March 2026 analysis of 1,110 open-ended responses from Google software engineers described time saved in generation being reallocated to auditing and verification, while broader DORA results connected higher AI adoption with both increased throughput and increased instability. citeturn17search9turn17search3

That finding strongly favors a product centered on **verification and high-quality evidence** rather than maximizing AI-generated cleanup patches.

Potential users differ considerably:

| User | Likely value | Main adoption blocker |
|---|---|---|
| Individual developer | Free local audit, dead-code/dependency cleanup | Existing free tools already strong |
| Startup/small team | Avoid complexity before it compounds | Limited time for another quality process |
| Enterprise | Cross-team retirement, architecture evidence, auditability | Security, false positives, integration and procurement |
| OSS maintainer | Contributor triage and safe dependency/code cleanup | Maintenance bandwidth; low willingness to pay |
| AI-heavy engineering team | Verification and reduction of AI-generated clutter | Need seamless agent/CI integration rather than another dashboard |

**Commercial model recommendation:** start with an open-source core or at minimum an openly inspectable local analysis engine and evidence schema; commercial value, if validated, can sit in organization-wide history, governance, policy, multi-repository analysis, managed execution and enterprise integrations. This is a product recommendation rather than an empirical finding. An opaque cleanup detector would have a trust disadvantage because maintainers need to understand why code is being classified as removable.

Willingness to pay should be tested separately from usefulness. Relevant evidence would include repeated weekly use, maintainer acceptance, reduced review/comprehension time, requests for centralized governance, teams voluntarily connecting additional repositories, retention after the novelty period, and price experiments. Positive technical results with no workflow adoption should be treated as product invalidation, not rationalized away.

**Risks, Limitations, and Counterarguments**

| Challenge | Assessment | Mitigation | Residual risk |
|---|---|---|---|
| Cleanup introduces more defects than it prevents | Plausible, especially when removing externally visible or rare behavior | Risk tiers, staged retirement, contracts, tests, observability, rollback | Medium; high for data/security/public APIs |
| Recommendation overload | Very likely if every static finding is surfaced | Hotspot/change-pressure ranking, evidence thresholds, budgets, suppression/expiry | Low–medium |
| Metrics incentivize harmful simplification | High risk for single-score gates | Multidimensional scorecard; never reward deletion/LOC reduction directly | Medium |
| Fewer abstractions create tighter coupling | Directly plausible; modularity theory explains why | Measure propagation/boundaries before and after; preserve meaningful information hiding. citeturn0search1 | Medium |
| Dependency removal compromises security/reliability | Possible if custom replacement is worse or runtime use is missed | Build/runtime classification, security review, package verification | Medium |
| Whole-repo analysis is expensive | Tool-specific; sophisticated interprocedural analysis can be costly | Incremental adapters, changed-area analysis, cached graphs, tiered deep analysis | Low–medium |
| LLM recommendations unreliable | Fundamentally unavoidable | Restrict LLM to reasoning over evidence; deterministic checks; human approval | Medium |
| Existing tools solve most of it | **Major strategic risk** in 2026 | Focus on evidence fusion/retirement workflow; benchmark against configured tool stacks, not strawmen | High |
| Simplification becomes unnecessary refactoring | High cultural risk | Require expected-benefit statement and change-pressure evidence | Medium |
| The platform becomes architectural clutter itself | Serious irony and real risk | Local monolith first, adapters, no graph DB/microservices until measured need | Low if discipline maintained |
| Better practices eliminate need for tool | Partly true; architecture tests, good flags/ownership and routine refactoring can prevent many problems | Position engine as evidence integration and discovery, not replacement for engineering practices | Medium |
| Maintenance cost exceeds benefit | Entirely possible | Instrument product's own operating/review costs and stop if ROI is negative | High until validated |

**When doing nothing is correct.** No cleanup should be performed merely because a detector reports complexity. Keeping existing code is often rational when the component is stable and unlikely to change; the expected future maintenance interest is below cleanup cost; behavioral verification is weak; ownership or external-consumer knowledge is missing; the system is near decommissioning; code is generated/vendor-managed; the apparent duplication provides deliberate isolation; a compatibility branch supports contractual customers; a dormant path is required for disaster recovery; or a migration would create more operational risk than expected maintenance savings.

That principle is not a concession. It is necessary to distinguish **engineering** from aesthetic refactoring.

**Recommended Engineering Strategy.**

The most damaging problems to target first are not generic complexity but **high-change areas with structural amplification**: dependency cycles, eroded boundaries, repeated change coupling, duplicated volatile business rules, obsolete public/internal paths whose consumers can be identified, and dependencies/configuration that create recurring maintenance work.

The most reliably detectable problems are syntactically unused imports and locals, many unused direct dependencies, certain unreachable control-flow branches, exact/normalized clones, dependency cycles and explicit architecture-rule violations. The least reliably detectable are external-use absence, semantic redundancy, unnecessary abstractions, unnecessary microservices, database obsolescence and operational/fallback obsolescence.

Safe automation should therefore follow this ladder:

```text
DETECT AUTOMATICALLY
        ↓
COLLECT EVIDENCE AUTOMATICALLY
        ↓
RANK AUTOMATICALLY
        ↓
EXPLAIN WITH AI WHERE USEFUL
        ↓
GENERATE PATCH ONLY WHEN AUTHORIZED
        ↓
VERIFY DETERMINISTICALLY
        ↓
HUMAN / POLICY APPROVAL
        ↓
NORMAL RELEASE PROCESS
```

Do not invert the sequence into:

```text
LLM thinks code looks unused -> delete -> hope tests catch it
```

**Evidence that would invalidate the product concept**

The project should be stopped or substantially narrowed if controlled evaluation finds that: configured existing tools achieve essentially the same candidate quality and workflow value; evidence fusion does not materially improve precision; maintainers reject most high-ranked findings; accepted cleanup produces no measurable reduction in subsequent change/comprehension effort; validation/review cost exceeds saved maintenance effort; required runtime/organizational context is rarely available; false positives remain high enough to create alert fatigue; or customers only value capabilities already supplied by SonarQube, CodeScene, jscpd, OpenRewrite/Moderne or general coding agents.

**Open Research Questions.** Several questions remain empirically unresolved enough that the product should treat them as experiments rather than assumptions: how much additional precision runtime evidence adds over high-quality static analysis; which Git-history signals causally improve retirement ranking versus merely identifying active code; whether semantic duplicate detection saves more review time than it consumes; how to calibrate risk across languages with radically different dynamic semantics; whether an organizational knowledge graph materially outperforms simple relational edge storage; how long a runtime observation period is sufficient for different artifact types; whether LLM explanations actually improve maintainer decisions; whether simplification effects persist over multiple feature cycles; whether AI-generated code changes the rate or type of structural degradation; and whether teams will maintain ownership/external-consumer metadata accurately enough for it to become reliable evidence.

**Implementation Handoff for an AI Coding Agent**

**Problem statement.** Build the smallest system capable of answering, with explicit provenance and uncertainty:

> *Which parts of this repository are plausible candidates for simplification or retirement; what evidence supports and contradicts that conclusion; what is the potential impact and risk; and what verification would be required before changing them?*

The first implementation is **not** a production autonomous refactoring agent. It is a deterministic evidence-collection and recommendation engine with optional AI interpretation.

**Verified findings that should constrain architecture**

1. Generic code-quality, dependency, clone, architectural-analysis and AI-refactoring capabilities already exist in mature tools; the project should orchestrate or integrate them rather than recreate them. citeturn26search3turn20search0turn20search1turn26search5turn21search8
2. Static absence of a recognized reference is not universally equivalent to deadness, especially in dynamic, reflective and externally consumed systems. citeturn25search3turn22search4
3. Runtime non-observation is supporting negative evidence, not proof.
4. Complexity metrics are useful signals but are not scientifically adequate as autonomous change criteria. citeturn13search5turn23search0
5. Architectural complexity/change propagation has stronger modern empirical support as a maintenance-burden indicator than simplistic line-count reduction. citeturn17search2
6. Current coding agents are powerful enough to inspect, edit and test repositories, but prompt injection, tool authority and destructive execution require explicit controls. citeturn18search5turn18search12turn18search23
7. The strongest first product hypothesis is evidence fusion and retirement decision support, not another generic quality dashboard.

**Proposed system boundaries**

The engine **owns** evidence normalization, candidate formation, risk policy, reporting, experiment instrumentation and verification orchestration.

The engine **does not own** language compilers, source control, package managers, CI/CD, production monitoring infrastructure, identity providers or a general-purpose coding model. Those are integrations.

**Architecture decision records**

| ADR | Decision | Rationale |
|---|---|---|
| **Local monolith first** | One Python application/process plus external analyzer subprocesses | Minimizes operational complexity and fits CPU/local requirements. |
| **SQLite first** | Store normalized artifacts/edges/evidence in SQLite; JSON for interchange | Sufficient for MVP graph queries and auditability; avoids unjustified graph DB. |
| **Adapter architecture** | Treat analyzers as isolated plugins/process adapters | Prevents reimplementation and allows language-specific best-of-breed tooling. |
| **Evidence before candidate** | Raw finding never directly equals removal recommendation | Preserves tool assumptions and allows contradiction. |
| **Deterministic policy engine** | Risk/veto logic is normal code/config, not LLM instructions | Security and reproducibility. |
| **Optional LLM boundary** | LLM consumes evidence packets and returns typed advisory output | Maintains offline functionality and prevents AI from becoming factual authority. |
| **Read-only default** | `audit` command cannot mutate repository | Eliminates a major early safety class. |
| **Worktree isolation for writes** | Future patch commands use a new Git worktree/branch | Easy diff, reset and rollback. |
| **No graph DB initially** | Add only after measured query/scale limits | Avoid speculative architecture. |
| **MCP after core API** | MCP maps onto existing query/application services | Prevent interface protocol from dictating core design. |

**Integration requirements**

Each analyzer adapter should implement the conceptual contract:

```python
class AnalyzerAdapter(Protocol):
    name: str

    def probe(self, repo: RepositoryContext) -> ProbeResult:
        """Return whether the analyzer applies and why."""

    def version(self) -> str:
        """Return exact analyzer version."""

    def analyze(
        self,
        repo: RepositoryContext,
        limits: ResourceLimits,
    ) -> AnalyzerResult:
        """Run without modifying repository and return raw + normalized evidence."""
```

Adapters must never hide analyzer errors. A partially successful run should state which evidence classes are unavailable.

**LLM boundary**

```python
class ReasoningProvider(Protocol):
    def investigate(
        self,
        candidate: CandidateEvidencePacket,
    ) -> AdvisoryAnalysis:
        ...
```

`AdvisoryAnalysis` should not contain a field named `safe: bool`. It should contain `supporting_interpretation`, `contradictions`, `unknowns`, `questions_for_owner`, `proposed_plan` and `verification_suggestions`.

**MVP acceptance gate before patch automation**

Patch generation should remain experimental until the audit benchmark demonstrates high precision in explicitly low-risk categories, false-positive reasons are characterized, maintainers confirm the explanations are useful, and the engine can reliably identify important disqualifiers such as public entry points and generated/dynamic registration.

Even after patch generation is enabled, automatic merging should remain out of scope until substantially stronger product-specific safety evidence exists.

**Implementation milestones for the coding agent**

**Initial skeleton**
Create packages for `domain`, `adapters`, `evidence`, `graph`, `candidates`, `policy`, `reporting`, `git`, `config`, and `cli`. Define schemas before implementing detector logic.

**Repository model**
Implement repository discovery, Git metadata, workspace/language detection and SQLite migrations.

**Analyzer protocol**
Implement subprocess safety/timeouts and one minimal deterministic adapter end-to-end. Ruff is a suitable Python starting point; Knip is a suitable JS/TS counterpart. Their current repositories show mature local static-analysis use cases. citeturn25search2turn19search0

**Evidence normalization**
Persist findings with exact provenance and raw-output hashes. Do not implement a "health score."

**Graph**
Add files, packages/imports and relevant symbol relationships. Implement reachability, fan-in/out and SCC/cycle queries.

**Candidate synthesis**
Merge compatible evidence into candidate objects while preserving disagreement.

**Risk policy**
Encode the default high/medium/low rules independently from analyzers.

**Reporting**
Implement terminal, JSON and Markdown reports. Prefer SARIF ingestion/export interoperability where existing tools provide it.

**History**
Add Git churn, age and co-change signals. Ensure automated formatting/vendor commits can be excluded or down-weighted.

**Benchmark harness**
Create synthetic fixtures and repository-run manifests before adding AI.

**Optional AI**
Only after deterministic candidate packets exist, add a provider-neutral explanation interface and adversarial tests for repository prompt injection.

**Verification**
Add isolated worktree creation and read-only configured verification commands; still do not generate general patches by default.

**Workflow integrations**
Add GitHub Actions and subsequently read-only MCP access.

**Known technical risks**

The hardest problems are entry-point discovery across frameworks; dynamic-language semantics; resolving external consumers; normalizing analyzer identifiers across commits; Git rename/history interpretation; co-change noise; schema evolution; generated code; monorepo workspace semantics; package-manager variations; false assumptions created by test coverage; prompt injection; tool version drift; and the temptation to gradually turn every missing capability into custom static-analysis infrastructure.

**Unresolved architecture decisions**

The first implementation exercise should explicitly leave these undecided until benchmarks provide evidence:

```text
Whether SQLite remains sufficient beyond the MVP.
Whether symbol-level cross-language graphs justify custom extraction.
Whether Semgrep or CodeQL should be optional deep-analysis adapters.
Whether runtime evidence should use OpenTelemetry-derived input or
a neutral imported-event format.
Whether semantic clone analysis provides enough precision to ship.
Whether any numerical aggregate "health score" should exist.
Whether local LLM inference has sufficient benefit on CPU-only hardware.
Whether a hosted multi-repository service has enough user demand.
Whether MCP write tools should ever be enabled.
```

**Final recommendation.** The research supports pursuing **continuous codebase health as an engineering practice**, but it does not support indiscriminate continuous cleanup, metric minimization, or autonomous AI deletion. The technically and scientifically defensible model is an evidence loop: observe structure and change; identify plausible unnecessary complexity; combine independent evidence; make uncertainty explicit; prioritize by future maintenance pressure; apply risk-appropriate human authorization; verify changes deterministically; and measure whether future engineering work actually becomes easier.

The product concept is therefore justified only in a narrower form than the initial vision. **Do not build another SonarQube/CodeScene-style universal quality platform. Do not build an LLM cleanup bot. Build the evidence and retirement layer that can sit above existing deterministic tools.** CodeScene, SonarQube, jscpd, Semgrep, OpenRewrite, Knip, deptry, architecture-rule tools and modern coding agents already provide many of the primitives. citeturn20search1turn26search3turn26search5turn20search0turn21search8turn19search0turn5search0

The first experiment should determine whether **combining those primitives produces materially better simplification decisions than using them independently**. If it does not, the correct engineering decision is not to build the platform. If it does—and especially if maintainers can subsequently demonstrate lower comprehension time, smaller change impact, less maintenance effort or reduced delivery friction without increased failure risk—then a continuous Codebase Health Engine would have a defensible technical foundation and a meaningful reason to exist.
