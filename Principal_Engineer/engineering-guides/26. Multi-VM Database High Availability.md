## 1. Executive Summary & The Problem

Containerization and blue-green application deployment protect against **software release failures**, but provide **zero protection against infrastructure host failures**. If both blue and green environments share the same virtual machine or hypervisor, a host reboot, kernel panic, or disk failure causes complete downtime (often 1–2 hours of cold recovery).

True reliability requires distributing database components across independent machines while solving three distinct distributed challenges:
1. **Replication**: Continuously shipping changes from a Primary to a Standby.
2. **Consensus & Failover**: Deciding safely when to promote a Standby without causing **split-brain** (where two nodes both accept writes).
3. **Connection Routing**: Allowing applications (Django, FastAPI, Node, Rails) to stay connected to whichever node is currently the leader without updating `.env` files or restarting containers.

### The 4 Distinct Responsibilities
| Component | What It Does | What It NEVER Does |
| :--- | :--- | :--- |
| **PostgreSQL 15** | Executes queries, enforces transactions, writes WAL. | Does not elect leaders; does not auto-failover. |
| **etcd Cluster (Raft)** | Stores cluster state; provides distributed lock leases. | Does not handle database data or connections. |
| **Patroni** | Supervises PostgreSQL; acquires etcd lease; initiates failover. | Does not route application database traffic. |
| **HAProxy** | Directs application writes to leader and reads to standby. | Does not make promotion or failover decisions. |

## 3. Step-by-Step Implementation Guide

### Step 1: Deploying the 3-Node `etcd` Cluster

> **Critical Rule**: An etcd cluster requires an odd number of members ($\lfloor N/2 \rfloor + 1$ quorum). Never deploy a 2-node etcd cluster; a network partition leaves each node with 50% voting power, causing both nodes to lock up.

Deploy on each VM using Docker Compose (`docker-compose.etcd.yml`):

#### On VM 1 (`10.50.200.35`):
```yaml
services:
  etcd:
    image: quay.io/coreos/etcd:v3.5.15
    container_name: tesc-etcd
    restart: always
    environment:
      - ETCD_NAME=etcd-1
      - ETCD_DATA_DIR=/etcd-data
      - ETCD_LISTEN_PEER_URLS=http://0.0.0.0:2380
      - ETCD_LISTEN_CLIENT_URLS=http://0.0.0.0:2379
      - ETCD_INITIAL_ADVERTISE_PEER_URLS=http://10.50.200.35:2380
      - ETCD_ADVERTISE_CLIENT_URLS=http://10.50.200.35:2379
      - ETCD_INITIAL_CLUSTER_TOKEN=ha-etcd-cluster-1
      - ETCD_INITIAL_CLUSTER=etcd-1=http://10.50.200.35:2380,etcd-2=http://10.50.1.37:2380,etcd-3=http://10.50.14.12:2380
      - ETCD_INITIAL_CLUSTER_STATE=new
    ports:
      - "2379:2379"
      - "2380:2380"
    volumes:
      - etcd-data:/etcd-data

volumes:
  etcd-data:
```

*(Repeat for VM 2 and VM 3, changing `ETCD_NAME` and IP addresses).*

#### Verify Cluster Quorum:
```bash
docker exec tesc-etcd etcdctl endpoint health \
  --endpoints=http://10.50.200.35:2379,http://10.50.1.37:2379,http://10.50.14.12:2379
```

### Step 2: Containerizing Patroni & PostgreSQL

Patroni requires Python, PostgreSQL client binaries, and `psycopg2`.

#### The Dockerfile (`Dockerfile.patroni`):
```dockerfile
FROM postgres:15

RUN apt-get update && apt-get install -y --no-install-recommends \
    python3 \
    python3-pip \
    python3-psycopg2 \
    curl \
    jq \
    && rm -rf /var/lib/apt/lists/*

# Note: Pin urllib3<2 if using etcd3 client libraries for gRPC gateway compatibility
RUN pip3 install --no-cache-dir --break-system-packages "urllib3<2" "patroni[etcd3]"

RUN mkdir -p /etc/patroni /data/patroni && chown -R postgres:postgres /etc/patroni /data/patroni

USER postgres
ENTRYPOINT ["patroni"]
CMD ["/etc/patroni/patroni.yml"]
```

### Step 3: Patroni Configuration (`patroni.yml`)

Save this file on VM 1 as `/etc/patroni/patroni.yml` (and on VM 2 with appropriate node name/IP):

```yaml
scope: app-db-cluster
namespace: /service
name: pg-node-1

etcd3:
  hosts:
    - 10.50.200.35:2379
    - 10.50.1.37:2379
    - 10.50.14.12:2379

restapi:
  listen: 0.0.0.0:8008
  connect_address: 10.50.200.35:8008

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    maximum_lag_on_failover: 1048576
    synchronous_mode: false  # Set true for zero RPO; false for zero write-freeze risk
    postgresql:
      use_pg_rewind: true
      use_slots: true
      parameters:
        max_connections: 200
        max_replication_slots: 10
        max_wal_senders: 10
        wal_level: replica
        hot_standby: "on"
        wal_keep_size: 1024MB

  initdb:
    - encoding: UTF8
    - data-checksums

  pg_hba:
    - host replication replicator 10.50.0.0/16 md5
    - host all all 10.50.0.0/16 md5
    - host all all 127.0.0.1/32 md5
    - host all all all md5

postgresql:
  listen: 0.0.0.0:5433
  connect_address: 10.50.200.35:5433
  data_dir: /data/patroni/pgdata
  bin_dir: /usr/lib/postgresql/15/bin
  pgpass: /data/patroni/.pgpass
  authentication:
    replication:
      username: replicator
      password: SuperReplicationPassword2026!
    superuser:
      username: postgres
      password: SuperAdminPassword2026!

tags:
  nofailover: false
  noloadbalance: false
  nosync: false
```

#### Launching Patroni (`docker-compose.patroni.yml`):
```yaml
services:
  patroni-pg:
    image: my-patroni:15
    container_name: app-ha-db
    restart: always
    network_mode: host
    volumes:
      - /etc/patroni/patroni.yml:/etc/patroni/patroni.yml:ro
      - patroni-data:/data/patroni

volumes:
  patroni-data:
```

### Step 4: Database-Aware Traffic Routing (HAProxy)

Application containers cannot hardcode database node IPs, because the primary role moves dynamically. We place an HAProxy sidecar on each application host listening on:
- **Port 5000**: Write Primary (polls `GET /primary` from Patroni REST API).
- **Port 5001**: Read Replicas (polls `GET /replica` from Patroni REST API).

#### Configuration (`/etc/haproxy/haproxy.cfg`):
```haproxy
global
    maxconn 1000

defaults
    mode tcp
    timeout connect 4s
    timeout client 30m
    timeout server 30m
    timeout check 2s

frontend pg_write_front
    bind 127.0.0.1:5000
    default_backend pg_write_back

backend pg_write_back
    mode tcp
    option httpchk GET /primary
    http-check expect status 200
    default-server inter 3s fall 3 rise 2 on-marked-down shutdown-sessions
    server pg-node-1 10.50.200.35:5433 maxconn 100 check port 8008
    server pg-node-2 10.50.1.37:5433 maxconn 100 check port 8008

frontend pg_read_front
    bind 127.0.0.1:5001
    default_backend pg_read_back

backend pg_read_back
    mode tcp
    option httpchk GET /replica
    http-check expect status 200
    default-server inter 3s fall 3 rise 2
    server pg-node-1 10.50.200.35:5433 maxconn 100 check port 8008
    server pg-node-2 10.50.1.37:5433 maxconn 100 check port 8008
```

#### Application Environment Configuration:
Your applications (Django, FastAPI, Node, Rails) simply connect to:
```env
DB_HOST=127.0.0.1
DB_PORT=5000
DB_USER=postgres
DB_PASSWORD=SuperAdminPassword2026!
```

## 4. Operational Runbook & Verification

### 1. View Live Cluster State
Run from any database node:
```bash
docker exec app-ha-db patronictl -c /etc/patroni/patroni.yml list
```

Example Output:
```text
+ Cluster: app-db-cluster (7711709056100020256) -------+----+-------------+-----+
| Member    | Host              | Role    | State     | TL | Receive LSN | Lag |
+-----------+-------------------+---------+-----------+----+-------------+-----+
| pg-node-1 | 10.50.200.35:5433 | Leader  | running   |  2 |             |     |
| pg-node-2 | 10.50.1.37:5433   | Replica | streaming |  2 |   0/302F438 |   0 |
+-----------+-------------------+---------+-----------+----+-------------+-----+
```

### 2. Performing a Zero-Downtime Maintenance Switchover
When rebooting VM 1 for kernel patches or hypervisor maintenance:
```bash
docker exec -it app-ha-db patronictl -c /etc/patroni/patroni.yml switchover
```
- Patroni gracefully demotes VM 1, flushes WAL, and promotes VM 2.
- HAProxy detects the promotion via `/primary` returning HTTP 200 on VM 2.
- Total connection transition time: **$< 3$ seconds**.

### 3. Simulating Host Failure (Chaos Testing)
To verify automatic failover:
1. Hard-stop the leader: `docker stop app-ha-db` (or pull the network interface on VM 1).
2. Within 10–30 seconds (depending on `ttl` and `loop_wait`), Patroni on VM 2 detects the expired etcd lease and promotes itself.
3. Once VM 1 recovers, Patroni uses `pg_rewind` to automatically roll back any uncommitted transactions and re-attaches as a follower.

## 5. Engineering Pitfalls & Invariants

1. **Replication is NOT a Backup**:
   - If a script or user issues `DROP TABLE students;`, that drop replicates in milliseconds to all nodes.
   - Maintain continuous WAL archiving (e.g., **pgBackRest** or **WAL-G**) to an off-host NFS or S3 bucket for Point-in-Time Recovery (PITR).
2. **Never Use 2-Node Consensus**:
   - Always run 3 etcd nodes. A 2-node cluster cannot survive a single failure.
3. **Database Ports During Migration**:
   - While building the cluster, bind Patroni to a non-standard port (e.g., `5433`) so you do not collide with or disturb the running standalone database on `5432`.
4. **Connection Pooling Behavior**:
   - Ensure the application connection pool (e.g. Django `CONN_MAX_AGE`, SQLAlchemy `pool_pre_ping`) discards dropped connections on failover rather than reusing dead TCP sockets.
