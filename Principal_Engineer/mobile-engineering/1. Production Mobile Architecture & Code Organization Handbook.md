Production Mobile Architecture & Code Organization Handbook
Architectural Foundations & Data Flow
Clean Architecture & Layer Separation
The engineering of modern, enterprise-grade mobile applications requires an architecture that isolates core business rules from volatile user interface frameworks, local persistence engines, and external network services. Modern Clean Architecture addresses this requirement by organizing the codebase into concentric logical layers with a strict dependency rule: dependencies must point inward. Outer layers handle concrete framework implementation details, whereas inner layers encapsulate abstract business definitions and validation states. The system is divided into three distinct layers: the Data Layer, the Domain Layer, and the Presentation Layer.

The Data Layer is the system's boundary to the outside world, coordinating local database drivers, encrypted keychains, network endpoints, and device sensor channels. It contains:   

Data Sources: Separated into local components (such as SQLite engines handled via Drift, key-value stores managed via Hive, and encrypted shared settings) and remote components (such as RESTful services built on Dio or WebSocket streams).   

Data Transfer Objects (DTO Models): Dedicated serialization schemas that represent external systems. DTOs extend or map directly to domain entities but isolate serialization rules—such as JSON parsing, relational table constraints, and payload normalization—from the core domain.   

Repository Implementations: Structural classes that implement the abstract contracts declared in the Domain Layer. These implementations coordinate local caching, execute network write operations, and handle background synchronization queues.   

The Domain Layer is the core business cockpit of the application. It is written in pure Dart and must remain completely decoupled from platform-dependent frameworks, rendering libraries, and external dependency injection setups. This isolation allows developers to verify business operations via fast unit tests without initializing UI engines or hardware simulators. It contains:   

Entities: Statically typed, immutable domain models representing the primary business concepts.

Use Cases: Single-responsibility commands that execute specific business workflows (such as authorizing a payout or synchronizing an offline transaction queue).   

Repository Contracts: Abstract interfaces defining the data operations required by the domain. By defining these contracts inside the domain layer, the business logic remains decoupled from the physical location or retrieval mechanism of the data.   

The Presentation Layer is responsible for rendering the application state on screen and processing user inputs. It contains:   

UI Components: Simple, presentation-focused Flutter widgets and screens designed to display layouts and styles.

Business Logic Components (BLoCs and Cubits): State machines that process user interactions (events), invoke domain Use Cases, handle return values, and expose reactive, immutable states to the UI.

Unidirectional Data Flow (UDF)
To maintain deterministic application states, data must flow in a single direction. The user interface does not modify local databases, change network configurations, or mutate state variables directly. Instead, every state modification follows a unidirectional pipeline:   

┌────────────────────────────────────────────────────────┐
│                        UI Widget                       │
│    Emits Event (e.g., RunPayment)                      │
└───────────────────────────┬────────────────────────────┘
                            │ (Dispatches)
                            ▼
┌────────────────────────────────────────────────────────┐
│                   State Machine (BLoC)                 │
│    Invokes Domain Use Case (e.g., ProcessPayment)     │
└───────────────────────────┬────────────────────────────┘
                            │ (Calls)
                            ▼
┌────────────────────────────────────────────────────────┐
│                     Domain Use Case                    │
│    Coordinates Business Rules via Repository Interface │
└───────────────────────────┬────────────────────────────┘
                            │ (Delegates)
                            ▼
┌────────────────────────────────────────────────────────┐
│                Repository Implementation               │
│    Updates SQLite Cache & Sends Outbound API Request   │
└───────────────────────────┬────────────────────────────┘
                            │ (Returns DTO/Entity Status)
                            ▼
┌────────────────────────────────────────────────────────┐
│                   State Machine (BLoC)                 │
│    Emits New Immutable State (e.g., PaymentSuccess)    │
└───────────────────────────┬────────────────────────────┘

└────────────────────────────────────────────────────────┘
This unidirectional data flow prevents shared mutable state bugs, enforces predictable state transitions, and simplifies debugging.

Domain Modeling, Value Objects, and Entry-Point Validation
Domain validation must execute at the boundaries of the domain layer. Raw structures returned from remote JSON payloads or SQLite rows cannot be trusted. To prevent corrupt data from spreading through the application, input validation is enforced at point-of-entry using specialized Value Objects and fail-fast mapping schemes:   

Dart
// value_objects.dart
import 'package:equatable/equatable.dart';

class AccountNumber extends Equatable {
  final String value;

  private AccountNumber._(this.value);

  static Either<Failure, AccountNumber> create(String input) {
    final sanitized = input.replaceAll(RegExp(r'\s+'), '');
    if (sanitized.length < 10 || sanitized.length > 18) {
      return Left(ValidationFailure('Account number must be between 10 and 18 digits.'));
    }
    if (!RegExp(r'^\d+$').hasMatch(sanitized)) {
      return Left(ValidationFailure('Account number must contain only digits.'));
    }
    return Right(AccountNumber._(sanitized));
  }

  @override
  List<Object?> get props => [value];
}
By encapsulating validation rules inside the constructors of immutable Value Objects, the system guarantees that once a domain entity is instantiated, its state is verified and logically valid.

Project Organization, Modularization, and Code Ownership
Feature-First Package Separation (Monorepo Workspace)
Monolithic projects often suffer from namespace conflicts, tight coupling, and slow compilation times. To scale development across multiple product teams, code is organized in a Feature-First Multi-Package Monorepo managed via Melos. Rather than grouping code by technical type (e.g., placing all screens in a single UI folder and all models in a shared data folder), code is organized into independent packages that encapsulate distinct business features:

Dependency Management & Third-Party Library Decoupling
To prevent third-party library dependencies from leaking across architectural boundaries, external packages must be encapsulated within thin wrapper interfaces in the Core layers. The main application shell and feature modules interface with these abstract wrappers rather than the underlying library APIs:   

Dart
// packages/core/core_network/lib/src/http_client.dart
import 'package:dio/dio.dart';

abstract class HttpClient {
  Future<HttpResponse<T>> post<T>(
    String path, {
    Map<String, dynamic>? data,
    Map<String, String>? headers,
  });
}

class HttpResponse<T> {
  final T? data;
  final int statusCode;

  HttpResponse({this.data, required this.statusCode});
}

// Low-level Dio encapsulation prevents feature modules from importing Dio directly
class DioHttpClientImpl implements HttpClient {
  final Dio _dio;

  DioHttpClientImpl(this._dio);

  @override
  Future<HttpResponse<T>> post<T>(
    String path, {
    Map<String, dynamic>? data,
    Map<String, String>? headers,
  }) async {
    try {
      final response = await _dio.post<T>(
        path,
        data: data,
        options: Options(headers: headers),
      );
      return HttpResponse(data: response.data, statusCode: response.statusCode ?? 500);
    } on DioException catch (e) {
      throw _mapDioError(e);
    }
  }

  Exception _mapDioError(DioException error) {
    // Structural mapping from external library exceptions to domain failure instances
    return NetworkException(message: error.message ?? 'Unknown transmission error');
  }
}

Platform Integration Contracts
When interacting with native iOS or Android hardware features (such as secure keystores or biometric hardware), teams must avoid writing raw, string-based method channels, which are prone to runtime failures. Instead, all platform interactions are defined using Pigeon, which generates type-safe Dart, Kotlin, and Swift interfaces at build time:

Reactive State Management & UI Design Patterns
BLoC and Cubit State Machines
The Presentation Layer isolates rendering elements from raw business rules using state machines powered by package:flutter_bloc. BLoCs accept incoming events, run the corresponding business logic via domain Use Cases, and emit immutable state objects that describe the current state of the user interface. To prevent unnecessary UI rebuilds, all states must enforce value equality by inheriting from Equatable:   

Dart
// payment_state.dart
import 'package:equatable/equatable.dart';
import '../../domain/entities/transaction.dart';

abstract class PaymentState extends Equatable {
  const PaymentState();

  @override
  List<Object?> get props => [];
}

class PaymentInitial extends PaymentState {}

class PaymentInProgress extends PaymentState {}

class PaymentSuccess extends PaymentState {
  final Transaction transaction;

  const PaymentSuccess(this.transaction);

  @override
  List<Object?> get props => [transaction];
}

class PaymentFailure extends PaymentState {
  final String errorCode;
  final String message;

  const PaymentFailure({required this.errorCode, required this.message});

  @override
  List<Object?> get props => [errorCode, message];
}
Dart
// payment_bloc.dart
import 'package:flutter_bloc/flutter_bloc.dart';
import '../usecases/process_payment_usecase.dart';
import 'payment_event.dart';
import 'payment_state.dart';

class PaymentBloc extends Bloc<PaymentEvent, PaymentState> {
  final ProcessPaymentUseCase _processPayment;

  PaymentBloc({required ProcessPaymentUseCase processPayment})
      : _processPayment = processPayment,
        super(PaymentInitial()) {
    on<ExecutePaymentEvent>(_onExecutePayment);
  }

  Future<void> _onExecutePayment(
    ExecutePaymentEvent event,
    Emitter<PaymentState> emit,
  ) async {
    emit(PaymentInProgress());
    final result = await _processPayment(
      amount: event.amount,
      destinationAccount: event.destinationAccount,
    );

    result.fold(
      (failure) => emit(PaymentFailure(
        errorCode: failure.code,
        message: failure.message,
      )),
      (transaction) => emit(PaymentSuccess(transaction)),
    );
  }
}
UI Execution Contracts
Flutter widgets must be kept simple, with their primary responsibility being the observation of state machines and the rendering of user layouts. Developers must enforce clear boundaries between continuous state rebuilds and single-run operational events (such as showing a dialogue box, initiating a native haptic pattern, or executing route navigation):

BlocBuilder: Re-evaluates widget subtrees in response to state transitions. It must be a pure function that returns a widget based on the current state and must never trigger secondary actions or initiate network calls.   

BlocSelector: Enables fine-grained UI rebuilding by selecting a specific property of the state to monitor. This prevents unnecessary parent-child rebuilds when unrelated state fields change.   

BlocListener: Executes one-time side effects (e.g., navigating to a new screen or showing a toast message) in response to state changes.   

BlocConsumer: Combines a listener and a builder into a single unified widget, which is useful when a state change requires both visual updates and functional side effects.   

Dart
// payment_execution_button.dart
import 'package:flutter/material.dart';
import 'package:flutter_bloc/flutter_bloc.dart';
import '../bloc/payment_bloc.dart';
import '../bloc/payment_state.dart';

class PaymentExecutionButton extends StatelessWidget {
  const PaymentExecutionButton({super.key});

  @override
  Widget build(BuildContext context) {
    return BlocConsumer<PaymentBloc, PaymentState>(
      listener: (context, state) {
        if (state is PaymentSuccess) {
          Navigator.of(context).pushReplacementNamed('/receipt', arguments: state.transaction);
        } else if (state is PaymentFailure) {
          showDialog<void>(
            context: context,
            builder: (_) => AlertDialog(
              title: const Text('System Alert'),
              content: Text(state.message),
            ),
          );
        }
      },
      builder: (context, state) {
        if (state is PaymentInProgress) {
          return const CircularProgressIndicator.adaptive();
        }
        return ElevatedButton(
          onPressed: () {
            context.read<PaymentBloc>().add(
              const ExecutePaymentEvent(amount: 150.00, destinationAccount: 'ACC-12345'),
            );
          },
          child: const Text('Submit Authorized Payout'),
        );
      },
    );
  }
}

Local Storage, Offline-First Synchronization, and Error Resolution
Offline-First Sync Mechanics
An enterprise mobile application treats active network connectivity as an optional enhancement rather than an absolute dependency. To ensure reliability on spotty connections, applications implement an Offline-First Synchronization Architecture. In this model, the local database acts as the single source of truth (SSOT) for the UI layer. The application reads and writes directly to local storage, which then synchronizes with backend servers in the background.   

Data entities must be designed to support offline tracking and synchronization. This is achieved by including metadata tracking fields in the data schema, specifically a client-generated UUID as the localId and a nullable remoteId that remains null until the entity is synchronized with the server.   

Dart
// local_database.dart
import 'package:drift/drift.dart';

class LocalPayments extends Table {
  TextColumn get localId => text().withLength(min: 36, max: 36)(); // Client-generated UUID
  TextColumn get remoteId => text().nullable()();                  // Nullable until synchronized
  TextColumn get targetAccountId => text().withLength(min: 8, max: 30)();
  RealColumn get paymentAmount => real()();
  TextColumn get syncStatus => text().withLength(min: 5, max: 20)(); // "draft", "queued", "synced"
  DateTimeColumn get clientTimestamp => dateTime()();

  @override
  Set<Column> get primaryKey => {localId};
}
Synchronization Lifecycle & Change Queuing
When a write operation occurs (e.g., a user submits a payment while offline), the repository inserts the record directly into the local database with a syncStatus of queued. The local database then triggers an update to the active UI streams, rendering the new record instantly with a visual "Pending Sync" indicator.

import 'package:dio/dio.dart';
import 'local_database.dart';

class SyncCoordinator {
  final AppDatabase _database;
  final Dio _httpClient;

  SyncCoordinator(this._database, this._httpClient);

  Future<void> executeSyncCycle() async {
    final pendingRecords = await (_database.select(_database.localPayments)
          ..where((tbl) => tbl.syncStatus.equals('queued')))
        .get();

    for (var record in pendingRecords) {
      try {
        final response = await _httpClient.post<Map<String, dynamic>>(
          '/v1/sync/payments',
          data: {
            'local_id': record.localId,
            'target_account': record.targetAccountId,
            'amount': record.paymentAmount,
            'client_time': record.clientTimestamp.toIso8601String(),
          },
        );

        if (response.statusCode == 200 || response.statusCode == 201) {
          final serverId = response.data?['server_id'] as String;
          await (_database.update(_database.localPayments)
                ..where((tbl) => tbl.localId.equals(record.localId)))

                remoteId: Value(serverId),
                syncStatus: const Value('synced'),

          await _resolveConflict(record, e.response?.data);
        } else {
          // Network errors are treated as transient; halt execution and retry later
          break;
        }
      }
    }
  }

Conflict Resolution and Conflict Algorithms
When synchronizing changes made offline, conflicts can occur if the same data has been modified on another device. The synchronization engine must handle these conflicts using one of several resolution strategies:

Last-Write-Wins (LWW): A deterministic strategy where the timestamp of the latest change determines which update is preserved. This approach is simple to implement but requires highly synchronized client clocks.   

Vector Clocks and Versioning: Each mutation carries an incremental sequence version. If the client version lags behind the server version, the transaction is rejected, and the client must pull the latest state and merge the changes before re-submitting.   

Manual/Structural Merge: The synchronization engine presents both versions to the user or uses application-specific logic to merge the fields, preserving changes on both sides.   

To maintain consistency and prevent duplicate records on the server during retries, all synchronization operations must use unique idempotency keys (e.g., the client-generated localId).   

Error Classification & Functional Error Handling
Errors must be classified into distinct operational categories so the application can respond appropriately:   

Error Class	Operational Type	System Definition	Standard Client Resolution Path
Transient Error	Network Timeout / Connection Lost	
Temporary network issues, infrastructure drops, or DNS failures.

Retain item in the synchronization queue, apply exponential backoff, and retry when a connection is restored.

Permanent Error	Validation Failure / Unauthorized Access	
Invalid data formats or API contract mismatches.

Remove item from the queue, write failure details to the sync log, and notify the user to correct the input.

Conflict Error	Out-of-Sync Data Collision	
Data has been modified elsewhere since the client last pulled.

Apply conflict resolution rules (e.g., Last-Write-Wins) and re-synchronize the resolved record.

  
To maintain code reliability and avoid the use of unhandled exceptions for control flow, error propagation must use functional programming patterns. This is achieved by returning an Either<Failure, Success> union type, which forces the calling function to handle both the failure and success cases at compile time:   

Dart

  const Failure(this.message);

  List<Object?> get props => [message];

  const ValidationFailure(super.message);
}

class ServerFailure extends Failure {
  final int statusCode;
  const ServerFailure(super.message, this.statusCode);

  @override
  List<Object?> get props => [message, statusCode];

// Usage in repository contracts enforces error handling at compile time
abstract class PaymentRepository {
  Future<Either<Failure, Transaction>> executeDirectPayment(double amount);

import 'package:dio/dio.dart';

class BackoffRetryInterceptor extends Interceptor {
  final Dio _dio;
  final int maxRetries;
  final double baseIntervalSeconds;

  BackoffRetryInterceptor(this._dio, {this.maxRetries = 3, this.baseIntervalSeconds = 1.0});

  @override
  Future<void> onError(DioException err, ErrorInterceptorHandler handler) async {
    final options = err.requestOptions;
    var currentAttempts = options.extra['retry_attempts'] ?? 0;

    if (_isTransientNetworkFailure(err) && currentAttempts < maxRetries) {
      currentAttempts++;
      options.extra['retry_attempts'] = currentAttempts;

      // Calculate exponential backoff delay with randomized jitter
      final exponentialDelay = baseIntervalSeconds * pow(2, currentAttempts);
      final jitterFraction = (Random().nextDouble() * 0.4) - 0.2; // +/- 20%
      final totalDelayMs = ((exponentialDelay * (1.0 + jitterFraction)) * 1000).toInt();

      await Future<void>.delayed(Duration(milliseconds: totalDelayMs));

      try {
        final retriedResponse = await _dio.fetch<dynamic>(options);
        return handler.resolve(retriedResponse);
      } on DioException catch (retryError) {
        return handler.next(retryError);
      }
    }
    return handler.next(err);
  }

  bool _isTransientNetworkFailure(DioException error) {
    return error.type == DioExceptionType.connectionTimeout ||
           error.type == DioExceptionType.sendTimeout ||
           error.type == DioExceptionType.receiveTimeout;
  }
}

Largest Contentful Paint (LCP): In a mobile context, LCP measures how long it takes to render the largest visible element on screen (e.g., a hero image or core dashboard card). The target LCP is ≤2.5 seconds from the start of the transition.

Distributed Tracing and Context Propagation
To track requests across distributed boundaries, network calls use distributed tracing context propagation. Every network request includes a standard W3C traceparent header, which contains the unique trace identifier and parent span information:   

traceparent: 00-1e9a84a8c5ae45c30b1305a0f41ed275-215435bcec6efa72-01
This W3C trace header enables APM systems to correlate client-side operations with backend execution logs across database runs, API runs, and queue runs.   

Dart
// trace_payload_interceptor.dart
import 'package:dio/dio.dart';
import 'package:opentelemetry/api.dart' as otel;

class TracePayloadInterceptor extends InterceptorsWrapper {
  final otel.Tracer _tracer;

  TracePayloadInterceptor(this._tracer);

  @override
  void onRequest(RequestOptions options, RequestInterceptorHandler handler) {
    // Start client span for remote API transaction
    final activeSpan = _tracer.spanBuilder('HTTP ${options.method}').startSpan();
    
    // Format W3C traceparent value: version-traceId-spanId-traceFlags
    final traceparent = '00-${activeSpan.context.traceId}-${activeSpan.context.spanId}-01';
    options.headers['traceparent'] = traceparent;

    // Persist active reference within internal properties
    options.extra['active_otel_span'] = activeSpan;
    handler.next(options);
  }

  @override
  void onResponse(Response<dynamic> response, ResponseInterceptorHandler handler) {
    final activeSpan = response.requestOptions.extra['active_otel_span'] as otel.Span?;
    if (activeSpan != null) {
      activeSpan.setStatus(otel.StatusCode.ok);
      activeSpan.end();
    }
    handler.next(response);
  }

  @override
  void onError(DioException err, ErrorInterceptorHandler handler) {
    final activeSpan = err.requestOptions.extra['active_otel_span'] as otel.Span?;
    if (activeSpan != null) {
      activeSpan.setStatus(otel.StatusCode.error, message: err.message);
      activeSpan.recordException(err, stackTrace: err.stackTrace); // Extract failure trace metadata
      activeSpan.end();
    }
    handler.next(err);
  }
}
Performance Calculations (Little’s Law & Amdahl’s Law)
Optimizing database read/write connections and background synchronization queues requires applying queuing theory and performance models.   

To calculate the expected database queue depth and connection limits, the application applies Little’s Law:

L=λ×W[cite:26,27]
where L is the average number of concurrent active operations, λ is the write transactional arrival rate, and W represents the average latency of a single database write transaction. For example, if a background synchronization cycle receives 150 write transactions/second (λ=150) and each local database write takes an average of 8 ms (W=0.008 seconds), the average database queue concurrency requirements are:

L=150×0.008=1.2 concurrent connections in flight[cite:27]
If connection allocations are misconfigured below this requirement, tasks will queue, degrading responsiveness.

Testing Boundaries, QA Validation, and Compliance Lifecycles
Testing Matrix & Test Pyramids
A robust quality assurance strategy relies on automated tests distributed across a standardized testing pyramid:   

                  / \
                 /   \
                /     \
               /  E2E  \
              /─────────\
             /   WIDGET  \
            /─────────────\
           /     UNIT      \

Unit Tests: Validate individual classes, domain entities, value validation models, and state controllers. These tests are fast because they execute in isolation from the UI layout engine, hardware modules, and remote servers.

Widget Tests: Target the layout rendering level, verifying that components render correctly and handle user interactions based on pre-configured state profiles.   

Integration/E2E Tests: Run the compiled app shell on live emulators or devices, verifying the end-to-end flow of the application from local storage up to remote APIs.

Pact Contract Verification
To prevent client-side failures when back-end server microservices modify API endpoints or response schemas, teams implement Consumer-Driven Contract Testing using Pact. Contract verification runs in the CI/CD pipeline to ensure that client and server APIs remain compatible.   

                API CONTRACT VERIFICATION PIPELINE

The contract generated by the mobile client is uploaded to a central Pact broker. When the backend team builds their API, Pact executes tests to verify that their service supports the API format expected by the mobile client, catching breaking API changes before they reach production.   

Mutation Testing Standards
To verify the quality and effectiveness of the test suite, teams integrate Mutation Testing (using tools like Stryker or Pitest) into their testing pipeline. Traditional code coverage only tracks which lines of code were executed during a test run, but cannot verify whether the tests actually assert correct behaviors.   

Mutation testing addresses this gap by injecting small code changes—such as replacing an addition operator with subtraction or changing a comparison sign from > to <—into the codebase. If the test suite passes despite these intentional modifications, the mutant has "survived," exposing a gap in the test coverage where assertions are missing. If the tests fail, the mutant is "killed," verifying that the assertions are effective at catching bugs.

AI-Assisted Development Practices and System Governance
Specification-First AI Coding Workflows
The adoption of automated developer agents (such as Claude Code or Gemini CLI) requires strict project governance and quality control. Allowing agents to write code without strict guardrails can introduce design flaws and architectural drift.   

To control code quality, engineering teams enforce a Specification-First AI Coding Workflow. In this workflow, developers do not use AI agents to generate code directly from descriptions. Instead, the human developer writes and refines the test specifications and assertions first, then tasks the AI agent with writing the minimal implementation needed to make those tests pass.   

               SPECIFICATION-FIRST DEVELOPMENT
┌─────────────────────────┐               ┌─────────────────────────┐
│     HUMAN DEVELOPER     │               │        AI AGENT         │
│                         │               │                         │
│  Writes Pure Unit Tests │               │  Parses specifications  │
│  Defines Test Contracts ├──────────────►│  Writes implementation  │
│  Sets Assertions First  │  Inject Specs │  Runs validation loop  │
└─────────────────────────┘               └─────────────────────────┘
This workflow ensures that all generated code is validated by a rigorous, human-authored test suite, preventing subtle bugs and keeping the implementation aligned with architectural guidelines.   

Progressive Context Disclosure & AGENTS.md Configurations
To prevent AI developer agents from overloading their LLM context windows—which can cause "context rot" and degraded reasoning—teams must enforce Progressive Context Disclosure. This is done by organizing instructions and project documentation into lightweight, modular indices. The AI agent can then query these indices to load only the specific instructions it needs for its current task, keeping the context window focused.   

To enforce project standards, the root directory of the project contains an AGENTS.md file. This file acts as a structured system prompt that defines the architectural rules, coding standards, and project constraints that the AI agent must follow:   

Agent Execution Rules & Workspace Boundaries
This document defines the architectural standards and constraints for all code generation, refactoring, and directory parsing operations.

Architectural Boundaries & Constraints
Every new feature must be isolated inside its own module: packages/features/feature_name.   

Code inside the Domain layer must be written in pure Dart and must never import platform packages like Flutter, Drift, or local data sources.   

Repositories must define an abstract interface contract in the Domain layer and their concrete implementation in the Data layer.   

State Management Rules
All Cubits and BLoCs must use Equatable or Freezed to declare value equality, preventing redundant state updates and layout rebuilds.   

UI screens must listen for side-effects (like navigation or alerts) using BlocListener, and build layout frames using BlocSelector or BlocBuilder.   

Observability & Quality Assurance
Every network call and external service request must include a W3C traceparent context propagation header.   

Unit tests must use mocktail to mock dependencies, and must verify that all expected repository calls are executed.   

By presenting this structured context directly to local agent processes, teams can prevent architectural drift, reduce instruction bloat, and maintain consistent quality across large workspaces.
