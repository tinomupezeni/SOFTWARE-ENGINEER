# Non-UUID sentinel/guest ids crashed two internal context endpoints with raw 500s

**Date:** 2026-10-05
**Project:** HBEC
**Environment:** Production (Student Backend, endpoints called internally by the Agentic Harness)
**Severity:** Medium
**Status:** Resolved

## Summary
Two internal endpoints the Harness calls to build student/project context
(`StudentContextView`, `SBPProjectContextView`) only caught `DoesNotExist` on
their primary-key lookup, not the `ValidationError`/`ValueError` Django raises
when the id string isn't a valid UUID at all. Two different legitimate,
by-design non-UUID ids reach these endpoints: a guest chat session's id
(`guest-<hex>`, minted by `apps.ai_gateway.views._generate_guest_id` for
unauthenticated chat) and the student frontend's `"default"` sentinel for
"no SBP project selected yet". Both crashed with an uncaught 500 instead of
degrading to the same "not found" shape already used for a genuinely missing
record.

## Symptoms
- `GET /api/internal/student-context/guest-1be5f9033810dffb/` → `500
  ValidationError: ['"guest-1be5f9033810dffb" is not a valid UUID.']`
- `GET /api/internal/sbp/projects/default/` → `500 ValidationError: ['"default"
  is not a valid UUID.']`, 3 occurrences

## Environment Details
- **Server/Host:** `hbca-vps`, `/opt/hbec`
- **Services Affected:** `hbec-student-backend`
- **Related Components:** `apps/internal/views.py` (`StudentContextView._build_context`,
  `SBPProjectContextView.get`)
- **Time First Observed:** found via `system_error_logs` triage 2026-10-05; errors date back to 2026-09-28/10-02

## Investigation Steps

### 1. Initial Diagnosis
Both errors are the identical Django `ValidationError` shape, from two
different views, both doing `Model.objects.get(id=<non-uuid-string>)`.

### 2. Root Cause Analysis
- `guest-<hex>` is **not a caller bug** — it's generated by the student
  backend itself (`apps/ai_gateway/views.py::_generate_guest_id`) and
  embedded as the JWT `sub` for unauthenticated "guest mode" chat, by design.
  The Harness forwards it unmodified to `get_student_context()` with no
  guest special-casing anywhere in the call chain.
- `"default"` **is primarily a frontend caller gap** —
  `STUDENT/Frontend/.../ProjectGuidePage.tsx` sends
  `projectId: selectedProjectId || 'default'` into project-scoped calls even
  when no real project exists yet (e.g. a student with zero SBP projects).
  The Harness's own `project_guide/nodes.py` wraps this in a broad
  `try/except` and degrades to a stub template, so chat doesn't visibly
  break for the student — but the backend still 500s and logs an error on
  every such call. Fixed defensively on the backend regardless, since
  "no project selected" is a real UI state this endpoint should handle
  without depending on every caller getting it right.

## Root Cause
Neither view caught the exception class Django raises for a UUID field's
failed `to_python()` coercion (`ValueError`/`django.core.exceptions.
ValidationError`) — only `DoesNotExist`, which doesn't fire until *after* a
valid-looking UUID successfully queries and finds nothing.

## Prevention / Rule
**Guardrail:** new tests assert both endpoints return their existing
"not found" shape for these exact inputs rather than 500ing —
`test_student_context.py::test_guest_session_id_degrades_gracefully_instead_of_500`
and `test_sbp_project_context.py::test_default_sentinel_degrades_to_404_instead_of_500`
(a new test file; this view had zero coverage before).

## Solution

### Immediate Fix
- `StudentContextView._build_context`: `except (User.DoesNotExist, ValueError,
  ValidationError)` — matches the pattern already used elsewhere in the same
  file (lines 626, 1288, 1697 at time of fix).
- `SBPProjectContextView.get`: `except (SBPProject.DoesNotExist, ValueError,
  ValidationError)` — same degrade-to-404 shape as a genuinely missing
  project.
- `apps/sbp/views.py`'s `SBPProjectViewSet` (the student-facing
  `/api/projects/projects/<id>/` ModelViewSet, a sibling endpoint on the same
  model) got the equivalent defensive `get_object()` override, converting the
  same `ValidationError` into `Http404`, even though it wasn't the endpoint in
  the actual production traceback — same root cause, same fix, applied
  proactively.

### Long-term Fix
The frontend sending a literal `"default"` string instead of omitting the
project-scoped call (or passing `null`) when no project is selected remains
unfixed — tracked as a follow-up; today's backend fix is what stops the 500,
the frontend gap is a separate, lower-urgency cleanup.
